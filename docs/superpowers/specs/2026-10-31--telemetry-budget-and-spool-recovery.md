# 采集事务内存生命周期与缓存恢复设计

日期：2026-10-31。状态：用户已批准方案B，2026-11-01开始实施；真实迁移仍受本文验证及正常停机门槛约束。普通启动A已完成，不再等待其批准。本设计不代替整体企业/生产优化目标。

## 1. 已确认的问题

恢复本机服务后，网站和身份可用，模拟采集缓存仍满，整体就绪503。独立只读复演取得两类证据：

1. 当前旧接收调用`TelemetryService.receive → mutate → readEntities/tenantWorkspace → workspacePayload → PostImageVerifier`。较长审计历史经SQL封装行、事务前镜像、可变工作区及规范输出反复计量；当前模拟库约7.5万条审计。读取及工作区准备约497MiB后，申请写后校验索引触发原512MiB任务预算的`MEMORY_BUDGET`。读取、摘要、审计链、当前registry和纯治理决策均已通过；故障发生在一致性索引准入。隔离诊断进程没有执行企业DML或发报，内存租约最终归零且进程已退出。
2. 完整扫描现有10000条PENDING缓存，签名、原摘要、来源和事件结构全部匹配；总线报文约4.1MB，序号为1至10000。同来源数据库已经提交到75118：10000个序号全部冲突，原eventId+digest精确回执匹配为0。仅本机序号游标为10000。当前序号与持久回执不一致已证实，但造成这种状态的历史操作尚未查明，不能认定为某次恢复或复制所致。

依照原规则，该批消息需要`SEQUENCE_CONFLICT`的已提交拒绝回执，不是重复成功数据。只修内存也不能承诺变绿：拒绝记录仍需保留和处置，后续序号不能继续从落后的游标分配。不得清库、改旧报文序号、重签、恢复默认权限或提高容量来绕过这些事实。

私密证据保留于`work/existing-platform-20261031/intake-readonly-902c2d72fb84.json`、`intake-workspace-estimate.json`和`spool-sequence-cross-check.json`。公开说明不包含报文、HMAC、企业实体、原始错误堆栈或数据库路径。

## 3. 修正资源生命周期，保留校验

为全量实体读取器明确封装行的临时所有权：流读取仍逐行准入并排空失败；读取完成后，SQL行封装、分组和排序容器退休，预算转移到实际仍存活的TenantPayload。不是在Task结束前把已经退休的封装永久累计，又为保留内容再次计量。

事务前镜像、真正的可变克隆、规范化后镜像及紧凑校验索引仍分别计量。必须先核对实际引用生命周期及异常路径，不能提前释放仍被事务、回调、缓存或SQL流持有的对象。转移/失败为同步且完整的所有权交接，不留下跨await的未计量窗口；没有上下文时保持原维护调用语义。

维持现有512MiB及总预算，不删审计，不跳过完整原始来源、TenantPayload摘要、审计链、表/文件/行及写后校验。读取取消、错误、失败排空、克隆失败、后镜像构造失败和索引失败均只释放自己拥有的租约，其他并发任务仍被计量。

## 4. 接收与ACK诊断

接收继续使用现有企业队列和MQTT背压，点、回执及审计同一数据库事务提交后才签发业务ACK。未知COMMIT不能作为成功或确定失败；只按原事件及摘要进行回执解析，不能制造新事件来重试。无效签名不产生有效业务ACK。

维护详情沿用既有回环、Bearer、无Origin/Cookie及有界响应保护；增加固定字段的阶段/失败码/计数，不输出租户名、eventId、报文、密钥、SQL或原始异常。至少区分容量拒绝、完整性拒绝、提交结果未确认、签名/协议拒绝、队列满和隔离待处理。状态查询只读当前缓存，不触发接收、重试或修复。

当内存准入失败时，原报文仍留在边缘，给出明确处理代码；不默默吞掉所有原因而只留下一个不可定位的事务失败。失败计数和日志有界，不为每条失败写无限增长的本地日志。

## 5. 边缘恢复与非破坏性隔离

本批新增显式边缘维护入口，普通启动仍不执行DDL、修游标或改配置。维护顺序：

1. 精确核对源身份、原SQLite文件、PG部署/同来源回执、当前配置/原HMAC摘要、拥有的进程及停写条件；先输出只读提案，不能从路径或最新mtime自动选库。
2. 取得一致的边缘备份，保存完整原消息/摘要/元数据和关联回执基线；用本次拥有的独立SQLite及PG夹具验证可恢复后才允许实际迁移。备份和密钥不上传仓库，不复制实际大库作压力测试。
3. 正常停止本次已核对的捕获/发布及相关接收过程，验证实际终态；只有原实例失去写入能力后才进行迁移。不得强杀、按超时重启、杀PID复用者或结束复用的数据库/身份服务。当前旧进程没有新控制钩子，Windows正常交接方法必须先在相同启动方式的自有小进程上验证；不能证实正常停止时，保留原服务与隔离验证结果，不执行真实迁移。
4. 在原边缘库中显式升级到版本化结构，新增拒绝隔离存储。原PENDING报文的字节、eventId、sequenceNo、摘要和签名保持原样。单独校准以后新分配的游标：不小于原游标、全部已缓存/隔离序号以及已核对同来源的最高持久成功序号；下一条取其后继。记录前后游标及依据，不改写旧事件。
5. 只有收到原密钥验证通过、相同eventId/digest且数据库已提交的REJECTED业务ACK，才把完整原报文、原摘要、拒绝原因和ACK原字节原子移入拒绝隔离区。转移前后总记录/字节和摘要守恒；它不是删除或重新批准。STORED仍按原成功ACK规则归档确认；伪造、错误摘要、未知提交不移走原PENDING。
6. 每个来源的隔离区上限10000条、128MiB原报文/ACK/字段UTF-8逻辑字节，任一先到即拒绝进一步转移，原PENDING保留。报文和ACK均沿用8192字节接收上限，故最坏大小可能先触及字节限额，不能为了凑足10000条突破预算。迁移提案还需显示实际数据库页及WAL大小；数据库达到256MiB或WAL达到64MiB时暂停捕获/自动转移并报告，不声称逻辑预算就是磁盘硬限制。备份/迁移前至少有1GiB可用空间，否则拒绝。实际固定版本的磁盘/事务边界须在隔离库验证。达到限制不自动删旧记录、改签名、延长保存授权、VACUUM清理或无限扩容。普通启动只验证已有结构及迁移收据，不建表。

提供只读隔离摘要、完整受保护导出及独立校验入口，不新增一级菜单或公共消息浏览接口。隔离中的原事件不自动修改、重发、批准或删除；人工处理、保存期限和跨服务恢复仍需明确业务规则。未处置的隔离错误继续出现在运行详情/巡检中，不通过把它搬离pending就宣称无错误或生产就绪。真实10000条处理结果以实际提交的回执为准，不能仅凭扫描推测后批消息全部完成。

升级运行描述为显式维护操作：保留原描述和迁移收据，只更新经允许变化的构建/边缘结构绑定；原PG身份、账号、HMAC、会话密钥及其他配置摘要不变。重复维护返回同一收据；未知/部分结果须核对原操作，不重做迁移。普通启动遇到旧/未完成版本明确拒绝，不自动重新登记。
