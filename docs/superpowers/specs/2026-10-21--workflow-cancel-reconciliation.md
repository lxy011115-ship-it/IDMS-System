# 已取消预测建单的外部对账边界

本工作继续已授权的方案 A 待办。旧 SDK 可以在流程请求发出后记录原生 CANCELLED，现有接管明确拒绝将这种历史当作安全取消。需要完整的人工对账、独立复核、原操作人明确确认和网页入口；不能删除取消历史、换新命令重复创建或把不存在的一次查询当作不会再创建的证明。

## 分层实施

1. 流程服务先提供持久、幂等的对账边界。后端接收原建单信封及固定控制编号，在与原创建相同的实体事务锁内判断：已存在相同命令回执则返回 CREATED；回执和实体均不存在则持久保留 BLOCKED，数据库触发器拒绝原命令和计划实体的迟到创建。冲突、畸形回执、同实体不同命令或不同摘要均拒绝。不存在的 GET 不能充当 BLOCKED。
2. 领域对账保留原 CANCELLED、原计划及取消回执，另记对账状态及审计；由另一位当前有权限的用户独立复核，原操作人重新明确授权。已创建时仅在原业务证据仍一致、没有后续意图或工单时关联原计划工单；不一致则保留外部已创建且待处理，不假定完成。未创建时须有持久 BLOCKED 才能关闭不明状态。
3. 持久 HTTP 作业、身份/范围/CSRF、原编号查询恢复及网页对账入口接入统一主站，并验证真实双人操作、断网/撤权/迟到响应。

本次先实现并验证第 1 层，它是完整人工对账的必要边界，不代表第 2、3 层或整站已完成。其余原方案 A 工作与最终图文/实际操作视频保持原顺序。

## 第 1 层架构

新增独立控制器、SQL 协议、目录见证与 Node 传输证明。旧 Java 控制器和运行 jar 不改。新控制器仅在显式设置私密对账配置后启用，使用专属认证 token 和仅能调用对账函数的数据库角色；配置绑定 tenant、authority、数据库 OID、角色 OID及完整目录摘要。启动时还必须与原工作流私密配置的同租户 JDBC 地址一致，并拒绝复用原服务 token 或原数据库运行角色，避免对另一个库签发无效阻断。SQL 由显式安装器安装到隔离目标，不在控制器启动时自动迁移。

对账函数所有者为 NOLOGIN 角色。应用角色无账本/阻断记录直接写权限。账本和阻断记录禁止 UPDATE/DELETE/TRUNCATE；原流程角色仅通过既有创建事务触发阻断检查。对账与原创建均使用 pg_advisory_xact_lock(hashtext(entityId))，使两种竞争结果互斥。触发器的异常回滚整个 Flowable/业务/命令回执事务，不能留下孤立流程。目录见证包含关系、字段、约束、权限、函数定义及属性、触发器定义和启用状态，每次操作前后核对。

POST /v1/cancel-reconciliations 接收严格的 controlId、envelope。GET /v1/cancel-reconciliations/{controlId} 仅查询已持久决定。响应绑定格式、租户、authority、控制编号、原命令、原请求摘要及计划实体。CREATED 带原创建回执；BLOCKED 不含创建结果。Node 证明使用私有构造品牌，只能由实际受认证请求、受限响应解析和完整绑定校验产生，不能由普通 JSON 伪造。

同控制编号不同信封冲突；不同控制对同一原信封可返回同一事实。BLOCKED 与 CREATED 不可相互重写。已建单且后来进入维修状态仍返回原创建回执，不把当前状态当作原始创建结果。不同数据库/租户相同 UUID 相互隔离。

## 验证

隔离新建数据库及最小角色，隔离离线构建新 jar，启动实际 Flowable。验证已创建后对账、先阻断后迟到创建、实体锁两种竞争顺序、重复控制/回复丢失后 GET 恢复、冲突摘要/实体、畸形信封和回执、错误 token/租户/OID/角色/目录漂移、直接篡改/截断拒绝；逐条核对真实流程、cases、commands、账本数量和重启后的阻断效果。原 Java 源/jar/活动服务及旧 pins 保持，专用目标按 OID 和自有句柄清理。没有真实验证的层次保留为未完成。
