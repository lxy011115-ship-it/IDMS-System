# 企业运行日历与计划采样覆盖

延续用户“按当前待办补齐功能”的授权，沿完整方案A实现企业日历和计划采样覆盖；上一轮采集质量交付是已验证进展，不能替代完整目标。本轮保持原数据/会话/根证明/只读设备/独立人工终审。

采用现有模板治理的 operation-calendar 用途，绑定一台已批准且授权设备。一台设备仅有一个日历编码族；明确ISO带时区起止，最多366天与512个连续无重叠RUN/STOP区间，区间必须覆盖声明范围。IANA时区用于展示，时间点由显式偏移决定，不推测夏令时重复/不存在的本地钟点。禁止脚本、继承、隐式工作周或未声明日期当作停产。新版本替换当前发布版，旧版/审计不改写。编辑、导入、发布、列表/导出和幂等重放均检查当前批准设备范围。

比较：新增上传第八类型会影响全部领域DDL和历史批次证明；外部本地配置不能独立审批或跨实例事务；采用现有business_templates及事务/审计/幂等最一致，不新增依赖或DDL。仍需专门校验日历schema、设备绑定和治理审计来源。

分别提供上传/采集计划覆盖接口，要求指定设备，窗口最多31天、左闭右开。只有当前批准测点定义声明间隔、有效发布日历且查询窗口完全在日历范围内，才给出完整计划覆盖率。无定义/间隔/日历、日历外时段、零计划槽均明确未知/不适用，绝不以100%填补。

RUN段按原段起点和声明间隔划槽；与查询窗口相交的部分槽计一个，STOP和日历外样本不填计划槽。一个槽多条记录只计一个；同时单列重复记录、非GOOD、运行外样本。全部收到/批准槽覆盖与GOOD有效槽覆盖分开；GOOD有效需有限非空值、批准单位（采集还需当前点表与持久接收来源绑定一致），不将覆盖率称健康分或模型精度。明确显示部分槽/区间和使用当前批准定义/日历版本，历史查询不是历史当时配置的重放。

上传沿现有已验证只读工作区和有效更正记录；采集沿独立只读RR、完整业务证明、受限公共点表、候选当前定义和全窗口SQL聚合，不拉取全量遥测。有限区间数据/计数需要预算、严格完整性/取消和失败关闭。原observedGapCount仍是观测内部缺口，不静默改成日历指标；计划覆盖单列，保留原始质量异常。

企业模板页可创建日历JSON，沿原独立提交审批/版本复制/导出；质量工作台可切换计划覆盖，选择上传/采集，显示计划时长/槽、实际覆盖和未知原因及依据。身份/来源变更/迟到响应/失败不得保留旧结果，所有文本转义、桌面及320/390无横向溢出。

验收：严格日期/间隙/重叠/边界、独立终审/同族设备不可改、租户/范围与导出/幂等、当前更正/版本替换、跨停产重复/非GOOD/未知/部分槽；真实PG/OIDC采集与上传独立统计、同RR并发、失败/预算/取消、真实浏览器创建发布与覆盖页。原平台升级仅在全旧回归/备份恢复/旧SID游标及专用不可覆盖基线验证后进行，未达条件则保存可审查开发结果并明确原站点版本。完整商用目标ACTIVE。
