# 多设备数据管理底座：数据库迁移与运行权限分离

日期：2026-10-15。状态：用户已回复“确认”；设计已实施并完成本机真实升级验证。下文现状段保留为实施前核查快照，当前结果与限制见`docs/database-role-separation-guide.md`及`outputs/live-database-roles-verification.json`。沿用已批准方案 A；首期面向多类型设备，优先手动数据管理及上传接口，不以新增预测模型为本批目标。

## 1. 已核实的现状

本轮通过代码和实际数据库只读检查核对，不依据历史文档推断实现状态：

- 4010 健康接口返回 UP、OIDC、独立企业 PostgreSQL、SQL 数据查询和已发布字段映射。
- acme 保持 6 批上传、0 张工单；sandbox 的模拟采集与实际企业数据分离。
- 两个业务账号均不是超级用户，也无创建数据库、创建角色或 BYPASSRLS 权限，但均拥有 public 的 CREATE 权限及本企业全部公共表。acme 当前 10 张公共表，sandbox 12 张。
- `postgres-repository.ts` 启动时建表、创建函数、重建审计触发器、回填审计与设备投影；`data-projection.ts` 也包含启动 DDL。
- `telemetry.ts`、`workflow.ts`、`ai-import-review.ts` 各自在启动时创建采集表或 outbox。只移走主表 DDL 会导致其他模块启动失败。
- 当前部署配置同时包含 bootstrap 与业务凭据，核心服务从同一路径读取配置；启动脚本每次运行 bootstrap。备份及隔离恢复工具也依赖此配置。

风险：应用账号作为所有者可以禁用触发器或修改表结构，因此当前追加式保护不能阻止该账号执行 DDL。数据库权限分离完成前，不得宣传绝对不可篡改。

## 2. 方案比较与建议

| 方案 | 优点 | 代价与限制 |
|---|---|---|
| 独立迁移，业务低权限运行（推荐） | 明确结构变更边界，保留现有系统与事务，便于 SaaS/私有化复用 | 需拆出全部启动 DDL，调整部署、备份及 QA 工具 |
| 每次启动临时提权后降权 | 表面改动较少 | 运行链路仍可取得高权限凭据，不能解决本次核心风险，不采用 |
| 同时更换容器/数据库部署结构 | 可进一步做进程与主机隔离 | 范围更大，不能替代数据库授权；本批不做整体重部署 |

推荐范围为企业业务数据库的版本迁移、权限、启动校验和备份兼容。Keycloak、Flowable 引擎自身数据库、AI 回执及边缘 SQLite 的分权另行验收，本批不宣称它们已完成。

## 3. 账号与凭据边界

每企业配置独立身份，不共享跨企业表所有者：

- owner：NOLOGIN，持有本企业数据库、schema、表、序列、函数及迁移账本；禁止业务账号成为其成员。
- migrator：独立 LOGIN、NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOINHERIT/NOBYPASSRLS，仅迁移进程可以显式 SET ROLE 到本企业 owner。完成迁移后退出，不留在业务连接池。
- app：现有业务身份及密码原则上保留，只授予表级必要 DML。无 owner/migrator 成员关系、无 CREATE/TEMP/DDL/TRIGGER/授权转授能力，不可 SET ROLE 提权。
- backup：每企业独立只读 LOGIN，获得备份所需表与序列读取权限；不能写业务或运行迁移。恢复继续使用受控部署管理员，仅允许新建随机隔离库。
- bootstrap：仅部署管理使用；不出现在业务运行配置或子进程环境中。

保留现有 `.local/postgres-runtime.json` 为部署管理配置，避免覆盖既有凭据与服务绑定；名称含 runtime 不表示它可继续交给业务核心。新增独立的业务、迁移、备份配置文件，以显式字段白名单生成，分别受 ACL 保护，不以展开整个配置对象的方式复制。核心 `IDMS_POSTGRES_CONFIG` 改指向仅含业务连接的配置。

不同文件的 ACL 若仍授权同一 Windows 用户，并不能阻止该用户下的恶意代码读取其他文件。本批证明 PostgreSQL 身份的能力边界，不声称已有主机级秘密隔离；生产仍需分离服务/部署身份或使用秘密管理服务。

## 4. 最小权限矩阵

除下表外，不授予 app 对数据库对象的额外权限。撤销 PUBLIC 的数据库 CONNECT/CREATE/TEMP 和 public schema CREATE，再显式授予对应账号所需权限；保留 schema USAGE。不得影响不属于本批目标的其他数据库。

| 对象 | app 权限 | 说明 |
|---|---|---|
| runtime_state | SELECT、UPDATE | 新企业初始行由迁移初始化，业务不删行 |
| audit_ledger | SELECT、INSERT | 保留追加触发器，禁止 UPDATE/DELETE/TRUNCATE |
| audit_ledger 序列 | USAGE | 不授予 UPDATE，不能 setval 重置 |
| managed_import_rows/assets/point_definitions/measurements | SELECT、INSERT | 保留事实表不可修改触发器及外键 |
| managed_projection_state | SELECT、UPDATE | 初始行由迁移建立，批准事务推进计数/摘要 |
| work_orders | SELECT、INSERT、UPDATE | 保持现有工单投影 upsert |
| workflow_outbox、ai_review_outbox | SELECT、INSERT、UPDATE | 保持现有重试/确认事务，不授予 DELETE |
| telemetry_points、telemetry_receipts | SELECT、INSERT | 仅启用该模块的企业安装，acme 不新增模拟采集表 |
| idms_schema_migrations | SELECT | 仅迁移账号写版本/摘要，不混同业务快照 schema_version |

backup 对本企业所有纳入备份的公共表和序列只读；迁移显式维护新对象授权，禁止笼统授予 app 对未来所有表的写权限。schema 与函数默认权限必须收紧，不引入可由 app 调用并任意提权的 SECURITY DEFINER 函数。

## 5. 迁移与启动流程

部署：核对目标与备份 → 停止业务写入及后台消费者 → 部署管理员检查角色/所有权 → migrator 获取企业级迁移锁 → 事务内迁移/校验/授权 → 记录版本及脚本摘要 → 退出迁移连接 → app 校验版本与权限 → 启动业务及消费者。

迁移代码统一承载当前业务表、领域表、触发器、outbox 和按模块启用的采集表 DDL。已有业务数据、原文件、映射绑定、审批人、审计事件、幂等记录和业务快照摘要不得改写。首次从旧快照回填时沿用当前跨企业、审计及投影核对；异常即回滚，不自动修复历史。新企业初始化使用现有种子契约，不向已有企业补造业务记录。

`idms_schema_migrations` 记录版本、迁移内容 SHA-256、执行时间和模块集合。已执行脚本摘要不一致、缺迁移、版本超前、模块缺表或权限过宽均阻断启动。DDL 与数据迁移对单个企业尽量在同一事务执行；创建角色/数据库等部署步骤单独记录，不伪称所有企业及配置文件能跨库原子提交。

业务启动移除全部 DDL 与自动历史回填，仅加载并核对快照、SQL 审计链、领域投影、字段映射审计锚点和迁移版本。不能在缺表时退回 app 自动建表，也不允许以旧高权限配置继续运行。后续正常批准仍在原业务/审计/幂等/领域表同一事务内追加。

平台启动器可以协调部署阶段，但必须在派生业务子进程之前关闭迁移连接，并显式传递纯业务配置；反复 bootstrap 不得把数据库/表所有权还给 app。所有日志、错误、文档及交付包不得包含凭据。

## 6. 备份、升级与失败处理

- 备份使用独立只读身份，继续一致性快照、认证加密、完整公共表校验及逐表内容比对；迁移账本纳入备份。备份清单可以增加权限布局版本，但不能改写旧备份内容。
- 旧备份仍能在现有随机隔离目标中恢复。`--no-owner --no-acl` 不恢复生产分权，因此恢复成功不等于目标可以直接投入运行；仍保持 ISOLATED_BUSINESS_ONLY。未来如允许业务切换，必须另行重新施加角色布局并验证。
- 先在随机合成 QA 企业执行旧库升级、新库初始化、重复迁移与重启，再触碰实际企业库；故障注入只在本次 QA 目标实施。
- 实际升级前核对运行进程并备份两个企业；不删除旧配置、密钥或备份。迁移每企业独立，若任何企业失败，业务核心不得以部分升级状态恢复写入。
- 数据库事务失败回滚；账号/数据库创建、文件切换等外部步骤有明确检查点，重试不得更换既有密码。遇到未知所有者、意外授权或角色成员关系时失败关闭，不执行全局 REASSIGN OWNED 或自动清空角色权限。
- 升级失败保持停服，保留诊断与加密备份，优先修正迁移后重试。不能自动恢复 app 所有权以换取旧代码启动，也不能覆盖现有企业库；隔离恢复仅用于验证与排障。

## 7. 验证及退出条件

1. 隔离库以 app 执行上传、中文映射发布、批准、幂等重放、查询及工单业务；真实 OIDC/Flowable/AI 和 sandbox 采集路径正常。SQL 失败仍整批回滚。
2. app 对审计/事实表执行 UPDATE/DELETE/TRUNCATE、禁用触发器、ALTER/DROP TABLE、CREATE TABLE/FUNCTION、SET ROLE 到 owner/migrator/其他企业身份、setval 和角色管理均被拒绝。负例不得在实际企业数据上尝试。
3. 校验所有权、有效权限、PUBLIC 授权及角色成员关系，而不只检查用户名。跨企业 CONNECT 被拒绝；应用无超级用户/BYPASSRLS/创建角色等能力。
4. 迁移并发、重跑、摘要不符、缺版本/表/权限、模块变化、投影损坏及映射绑定删除均失败关闭或按契约幂等完成；缺迁移时 app 不产生任何 DDL。
5. 既有 QA 中用于故障注入的 DDL 改用仅测试可用的迁移/管理连接，不能为测试重新扩大 app 权限。旧功能测试继续执行。
6. 独立只读账号能够导出并隔离恢复新备份，旧备份仍可验证；只读账号不能写业务。角色/授权本身不作为 `--no-acl` dump 已恢复的证据。
7. 实际升级后核对 acme 原 6 批/0 工单及 imports/business 规范化摘要不变；核对原文件、全部既存表、映射、审计、Flowable/AI 及采集状态。保留证据，不向企业库造数据演示。
8. `NODE_ENV=production` 门禁保留；文档准确标注“业务数据库账号分离已验证”与尚未完成的安全边界，不能标记完整商用交付。

## 8. 不在本批范围

数据更正版本、完整设备类型继承、工厂/设备细粒度授权、对象存储与 TimescaleDB、全领域写入/多实例、不可变外部审计归档、生产 TLS/MFA、全服务一致性恢复、PITR/RPO/RTO、许可证/计费和现场预测验证仍待后续完成。

本批不会提升 AI 自动审核权限。AI 仍为真实模型 SHADOW 抽样审阅；最终责任动作仍由独立人工批准。数据库管理员仍有管理能力，哈希链与最小权限不能代替独立审计保管或不可变归档。
