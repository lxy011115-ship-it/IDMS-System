# 恢复审核的独立只读 Flowable 服务

目标是让当前根恢复审批读取完整且真实的 Flowable 状态，同时保持业务身份封闭。现有普通服务会创建表并部署流程；已有 recovery HTTP 端点虽使用只读 RR 事务，仍依赖普通服务，不能直接用于封闭目标。

采用独立应用和专用只读 SQL 身份。应用没有命令、取消、部署或安装路由，不接受普通服务 token、bootstrap 账户或业务 writer 账户。启动先核专用角色、数据库 OID、无角色成员关系、无对象所有权、无 DML/DDL/序列写权限、无用户函数及大型对象入口执行权，再用 schemaUpdate=false、禁用异步执行的 Flowable 引擎读取已有流程。所有恢复状态查询共享同一 JDBC 数据源和 REPEATABLE READ READ ONLY 事务，保留完整流程、任务历史、变量、命令摘要与本地维修工单逐项核对契约。

替代方案中，提前启动普通服务不满足封闭约束；仅用自制 SQL JSON 不能替代真实引擎核验；bootstrap 认证后模拟 reader 也不构成独立只读 SQL 身份。因此采用单独入口。此为原正式恢复只读上下文待办中的实现，不改变最终审批或现场激活权限。

专用 reader 必须在受控源安装阶段建立、纳入捕获的访问契约，并被新的恢复策略显式约束。旧 cold V1 会封闭全部原角色和数据库连接，不能在旧 RESTORED/FIELD_REVIEW_V1 目标上临时 GRANT/开启 reader 或重定 catalog 来接入。本模块先验证真实引擎是否能够在严格只读权限下运行；源安装/新捕获契约和恢复接入是必需后续工作。单独编译或正向读取均不等于整个恢复审批完成。

与完整当前根扫描组合时，还需要实际自有 reader JVM 与其原始 SQL 连接的受控能力证明。现有维护 V4 只允许原恢复锁连接，不能仅按角色、application_name 或调用方提供的 PID 清单把 reader 当作白名单。必须由实际生命周期产生并持续核验受控连接身份，或在不放宽外态复读要求的协调顺序中证明 reader 退役；此组合尚未实现。

验证必须包含已有非空 Flowable 数据的真实读取、两个职责 token 与企业边界、写权限与普通路由拒绝、角色/定义漂移拒绝、快照前后数据一致和原始 JVM 正常退出。本轮先实现并独立构建；原生演练尚未完成时明确标注。保留旧 Java 源及所有已有冻结清单。
