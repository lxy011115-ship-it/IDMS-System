# 企业工作区隔离与写入复制容量

继续完整商用方案A的容量/多实例工作。已验证的v4租约、v3领域实体、共享认证及独立SQL读保持；本批落实每企业命令工作区与调度边界，随后继续冷校验/原文件按需、增量写入及更大规模验收，完整目标不收窄。

现状：mutate在锁前克隆全部企业，锁后applyTenant克隆目标payload，再克隆全部企业作回滚；成功又通过聚合快照检查跨企业修改。跨企业请求共用进程queue，等待外部服务也阻塞无关企业。仅缩减克隆次数仍保留共享可变对象；AsyncLocalStorage代理可隐藏改动但使依赖隐式。选择显式Workspace{store,imports}作为读写回调参数，领域函数继续接收普通Store/ImportData，避免隐式全局切换。

PostgreSQL模式启动加载保留不可变bootstrap供服务绑定和历史配置检查，不作为后续业务数据源。每次写入在企业business_state独占锁后读取最新数据库payload，仅克隆该企业一次形成命令工作区。回调、职责/范围/幂等复核、Flowable/AI/采集回调都显式使用该工作区。成功校验同企业数据并原子保存；失败丢弃工作区，不恢复/覆盖共享对象。外部响应也不持有工作区之外可变引用。

每个根Store有独立调度器，数据库模式按企业键排序；同企业读取与写入仍顺序执行，不同企业可并行。数据库业务锁继续跨核心排序。独立SQL数据中心路线保持现状。waitForWrites等待全部已排队任务，失败不会毒化队列，空闲键及时移除。嵌套同企业命令不支持，应明确失败，避免自等待。

普通GET以一致快照校验后的冻结企业工作区执行。缓存按根Store/企业隔离且保留数据库MVCC证明，写入开始/结束仅使目标企业失效。Map的set/delete/clear同样不可写。读回调不能改变共享缓存；存储中断或变化必须重校验。对响应对象引用冻结/提交隔离，不能因调用方持有返回值而篡改下一次工作区。

file Demo保持原快照语义，领域业务接口/历史摘要/迁移记录不改。原聚合payload_digest、完整文件/审计/事实校验保留，SQL失败/冲突仍不允许部分审计/回执/任务提交。跨企业污染即使在隔离工作区中也必须拒绝，不得依靠过滤而静默丢弃。

验证包括单元调度/工作区隔离/Map只读/污染拒绝，实际双企业阻塞测试（A网络/SQL锁等待期间B提交）、同企业排序与幂等、跨实例版本竞争/回滚/读取、返回引用/异常回调/权限复核、真实Flowable/AI/采集与原七类上传回归。以2万记录/大原文件对比写入进程的SQL字节、时延/内存和克隆范围，保留冷态成本，不作生产容量承诺。原平台部署前备份/隔离恢复、受控重启、同SID及原业务保值。

完整冷启动仍读企业全payload，写入仍完整校验目标企业且受既有摘要影响。分段/按需正文、全量摘要成本、对象存储/时序、数据库HA/网络分区/长时负载、安全/跨服务恢复/现场/模型/商业化继续；本批不宣称完成这些要求。用户已授权按当前待办继续开发，沿用授权执行。
