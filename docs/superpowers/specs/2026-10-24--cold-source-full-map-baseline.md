# 冷恢复审核的原环境完整数据依据

同时固定全部已登记数据库的存储表、序列和大对象摘要，包含维护控制关系。每库均在同一个原事务中采集，恢复后逐项核对；不能只覆盖有 StateMap 的企业库。SQL 编码设置使用独立 savepoint，返回前恢复原会话设置，避免影响原 catalog 的解释。

沿用已授权的完整方案A待办。本阶段为真实人工审核提供可追溯的数据依据：在原维护 CLOSED、原业务及只读工作流 JVM 已正常停止、全部连接排空后，在原数据库捕获每家企业完整 StateMap 数据根、全部叶子、SQL 回执链、领域数据和审计证据。原证据文件摘要、完整事实和源端 profile 随新 SOURCE_V3 正文固定，由 trust/sourceHash 及完整加密归档共同绑定。

恢复目标不得生成自己的原始基线。目标在原 bootstrap 事务内暂存原角色/库属性，通过原 catalog 核验后，重新捕获并离线重建完整数据根和领域/审计。除了环境 profile 与证据流自身摘要外，所有原事实必须逐项相同，包括全部关系摘要、完整 head、叶子数量、回执链和领域/审计摘要。整个检查事务回滚，不写业务数据或推进围栏代次。所有重复准备和状态查询仍重验原证据文件和完整目标事实。

推荐保留原完整事实捕获和独立验证器，新增原环境可信绑定及恢复侧语义比较。仅在目标建立基线无法证明原数据，予以排除；单纯增加 SQL 导出差异也不能代替数据根、回执链和领域重建，因此继续保留整库归档及 SQL 摘要作为补充证据。

新 source/trust 协议与旧 V2 明确分离；归档仍使用已经验证的 reader 专用 V2 图像格式，以 sourceHash 绑定新增事实。旧控制器拒绝 V3 trust。源证据严格置于控制目录外置私密子目录，拒绝符号链接、硬链接、越界路径、遗漏企业和重复企业。客户原始内容不发布到 Git。

这不授予人审批准、业务 LOGIN、现场租约或最终激活。真实 owned reader SQL 能力与当前身份审核、完整迁移和最终用户交付继续保留。当前 SQL 证据提供完整关系摘要；离线验证独立重建数据根、回执链及领域/审计，不能声称离线重新计算未导出的所有 SQL 原始行。

验收需覆盖真实完整 R4 原环境和异目录整库恢复、额外未知 namespace 全覆盖、原证据叶子篡改拒绝、目标根/回执/关系漂移拒绝、同意图及新 CLI 重入、两类提交中断、原进程正常退出，以及 Windows/Linux 和独立核验。既有有效版本和失败证据保留。
