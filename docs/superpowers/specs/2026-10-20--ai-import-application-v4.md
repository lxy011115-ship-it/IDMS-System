# AI 导入原子发布与结果应用 v4

在已归档的 AI 传输层上接通实际治理导入和结果业务应用。全部代码采用新模块/新建隔离 schema，旧发布源及原站点不变。用户已授权按现有待办持续开发。

## 协议

1. 受信治理 worker 注入固定服务器 AI 配置。IMPORT_CREATE 仍运行原解析/校验/映射/更正/设备类型规则；仅有效且无疑似指令的批次进入 AI_PENDING。批次 gateway 元数据、冻结原生 intent 和 IMPORT_AI_QUEUED 审计包含在同一个完整候选根。无效/可疑材料继续原人工路径。
2. 新 publish_ai_console SQL 调用旧受保护 console 发布，然后从新根读取 intent 并严格匹配传入 header/摘要。批次根、治理 COMMITTED 和 SQL AI 入队同事务。旧 prepare/publish_console 及独立原生 enqueue 权限撤销；新函数由同 NOLOGIN owner 转调用原函数。APP 仍是受信服务账号，不声称抵御已取得该账号的任意恶意代码。
3. 传输 worker 调用前读取当前租户与原生 AI policy。签名结果/本地人工回退持久化时，同事务创建独立应用任务。RESULT_READY 与 APPLIED 分开；原 result_v4 直调撤销。旧传输 API 保持冻结，通过继承适配新 result 函数。
4. 应用任务有独立 30 秒 DB 租约、10 秒线程续租和递增 fence。受信应用证明从实际数据库任务、密文、HMAC、模型清单和原生 intent 产生；JSON 或用户命令不能充当证明。内部 AI_IMPORT_APPLY 不进入公开六动作入口。
5. 应用沿用已验证的完整 payload/分组 branch 维护管线，核对当前租户/配置和批次版本/快照，生成 HUMAN_REVIEW、version+1、证据及旧格式审计，完整重建治理/读/console 投影。冲突只记录人工冲突，不采纳模型输出、不修改已批准批次。根发布、唯一业务应用回执和 APPLIED 同 COMMIT；未知提交查持久根与任务恢复。
6. 只有独立人工用户携带当前权限、版本/快照及复核依据才能批准，AI 结果不授予权限。治理/AI 竞争同维护控制时延后；推理不持维护围栏。配置轮换、挂起租户和大规模配额/保留仍需要后续独立治理。

## 验证范围

实际 PG 导入→原子待办→真实本地模型→人工复核→独立批准；原件 SHA、行/映射/更正、旧审计链及所有投影一致。独立进程/丢 COMMIT 回复/过期 fence、旧 SDK/假内部命令/无效签名、版本冲突、当前租户挂起与重复应用。HTTP/控制台与真实 Keycloak 接线按现有 auth-audit 新入口派生，保持最小角色、CSRF/PKCE/范围和原件下载。先完整隔离验证再讨论原站点切换，不以窄单测代替整项完成。
