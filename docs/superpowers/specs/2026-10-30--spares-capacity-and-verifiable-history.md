# 备件容量与可验证历史改造设计

日期：2026-10-30。状态：用户已于2026-10-30明确选择“按推荐方案实施”，开始分阶段实施。

对应持续目标：`docs/enterprise-optimization-plan-2026-10-30.md`。首批B方案及后续权限、历史查询已经实现；本设计继续关闭其中的备件增长问题，不将整个企业交付目标缩小为本阶段。

## 1. 已核实的问题

- `server/spares-db.ts`的`load`将全部实体装入内存，超过10000条拒绝；`verifyEvents`装入全部事件，超过20000条拒绝。正常读取、写入和备份核验都受影响。
- `sparesView`为同工厂全部“备件 × 仓库”组合生成余额，每个组合两次调用`stock`扫描全部实体。供应商、采购票款和设备更换也通过数组反复查找。
- `public/spares-ui.js`下载全部档案和流水再筛选；表单使用全量下拉框。工作台、审批及工单使用同一全量返回，不能仅给列表加一页后继续把这一页当作全部事实。
- 主站备件路由先持有原业务一致性工作区连接，再为备件借出另一个连接；不能在有限连接池中无界增加这种嵌套。
- 新操作历史页已分批读取，但每页仍遍历全部审计链。它的内存更小，不等于整个库存读写容量问题解决。

只读SQL确认acme、sandbox当前备件实体和事件均为0，版本均为0。应用账号可读取/追加事件，没有UPDATE、DELETE、TRUNCATE事件权限。核对没有写入企业业务数据。

独立合成诊断仅调用现有领域函数：50备件/5仓库/500流水返回250余额，用时约2.19ms；100/10/2000返回1000余额，约25.79ms；200/20/6000返回4000余额，约306.28ms。最后一项约4976万次实体条件检查。这是当前代码的单次本机诊断，不是生产吞吐或SLA。证据：`work/enterprise-optimization-20261030/capacity-{readonly,domain}-baseline.json`。

## 2. 三个方案

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| B 按业务查询与写入，推荐 | 保留现有独立schema、领域规则、事件格式和岗位；SQL聚合/分页、按命令加载必要资料、可失效的审计分段验证证明；保留完整备份档案 | 修改面包含服务端、现有备件界面和备份核验，需要迁移索引及回归，但直接解决真实路径 |
| A 仅流式读审计 | 用游标替换事件数组；原实体数组和前端全量下载保留 | 改动小，但10000实体、笛卡尔组合和业务写入成本仍在，不能作为完整容量改造验收 |
| C 拆出全新库存服务与账本 | 新服务、消息同步、库存投影和双写迁移 | 增加服务、部署和数据一致性职责；当前阶段收益不足，暂不推荐 |

推荐B，分为可单独验证的实现步骤，全部通过后才替换主站路径。六大菜单和现有九个备件页签沿用现有视觉，不增加账号或“扮演岗位”的开关。

## 3. 业务读写与一致性

### 一次事务只取必要的事实

保留`spareCommand`作为数量、状态、独立审批及职责校验的单一领域规则来源。增加显式的命令事实接口，存放数据库聚合结果和已加载实体标识；不把聚合伪装成虚构流水混入`entities`或审计。

| 命令 | 必需事实 |
| --- | --- |
| 档案创建/编辑 | 目标档案、同企业同类型编码冲突；编码大小写规则与现状一致，停用档案也不能重复占码 |
| 采购编制/编辑/提交 | 目标采购、供应商、仓库、至多50行实际引用备件及当前启用状态 |
| 采购审批/下单/关闭/取消 | 目标采购、版本、编制/提交/参与者、当前状态及所需关联资料 |
| 分批收货/退供 | 原采购及行、原收货、相关库存、该收货累计退供量 |
| 领料/退料/调拨 | 目标备件与仓库、当前授权设备/工单、原领料、累计退回和实际安装量、相关库存及流水版本 |
| 盘点/期初/报损 | 目标备件与仓库、库存数量和流水条数基准；审批再次核对最新基准 |
| 设备关联/实际更换 | 实际设备、位置关系重复检查、原领料及累计退/装数量、位置最近更换日 |
| 票款登记 | 目标采购、同企业同类型凭证号是否重复、该采购该类型累计金额 |

SQL聚合使用整数/数值精确求和，转换为领域整数前检查安全范围。不能因只读到当前页或当前设备的流水而少算仓库库存、已退量或票款。仓库库存仍为该备件在该授权仓库的全部有效流水之和，不是某个维修员看到的领料之和。

同企业写入继续串行锁定`idms_spares.state`，在同一连接、同一事务内取得必要的当前已批准设备和工单事实、验证备件历史、执行业务、追加事件、保存幂等回执并递增版本。锁顺序固定为原业务状态共享锁→备件状态写锁，避免新旧业务反向获取锁。设备事实使用现有`currentQuery/current_assets`及当前工作单的规范关系；不能直接读已被修订的原始`managed_assets`，也不能从前端传入角色或范围。

使用可重复读事务时，遇到并发更新导致的40001/死锁，仅在事务已确认回滚且还未尝试提交时，用同一幂等键执行至多一次完整重试；提交结果不明时不生成新键。每次重试都重新取当前范围。幂等回执读取前继续核对本次当前权限及关联设备/工单，撤权后不能借旧回执读取旧结果。

命令完成后仅保存真实新增/改变的实体，不重新写入无关历史。完整回执、列表刷新失败和未知提交原键核对沿用已完成的UI语义。

### 有界查询与页面

增加以下只读API职责，接口参数统一严格校验，拒绝未知/重复参数和无效游标：

- summary：当前范围的库存风险、个人可独立审批、采购逾期、到期更换及票款待核对计数；不以列表一页代替总量。
- list：按库存、备件、仓库、供应商、采购、流水、适用位置、更换、调整、凭证分别查询；默认30条、最大100条，SQL完成搜索和排序。
- detail：按授权记录ID读取采购及其必要关联信息；采购行数仍为最多50行，收货/流水另有分页。
- options：表单档案、设备和工单的搜索与分页，允许带入并验证既有选中项。界面明确“还有更多，请搜索”，不能只给前30项却伪装成全部。
- workorder-usage：指定当前授权工单的库存净领用聚合；不下载该企业全部流水。

现有根备件接口保留为明确的兼容入口，主站、工作台、审批及工单全部切换到新接口。任何仍依赖全量数组的调用必须列入改造清单，不能静默返回截断数据。

列表以记录创建时间及ID（库存以备件/仓库标识）稳定排序；分页游标绑定企业、当前权限范围、查询条件及备件版本。翻页期间数据或范围变化则要求重新查询，避免把不同状态的一页拼成“同一快照”。数据库使用原始完整标识，`ctid/xmin`不作为业务ID或页面游标。

库存保留现有同工厂全部备件/仓库组合的零余额语义；SQL仅返回当前页。低库存及汇总使用分组流水与档案集合计算，避免应用层生成所有组合。页面保留“按备件档案单位”的数量，不将不同单位合并成一个库存总数量。

## 4. 完整审计与分段验证证明

第一步将现有业务/备份核验替换为有界流式核验，去除20000事件数组门槛，仍从GENESIS验证序号、企业、快照边界、哈希链和版本数量。每批最多128条，客户端取消、SQL失败或超时必须回滚并释放连接；不信任“已有历史数量”等于完整链正确。

随后启用可失效的分段验证证明以减少重复解析：

1. 事件按序号分为每段256条。一次读取在同一可重复读快照中分批取得每段的行版本指纹、数量、首末序号以及表/数据库代际信息，内存同时持有有限段摘要。
2. 只有此前完整核验过、指纹和边界完全相同的段才可复用其已核验首前哈希和末哈希。新段、改变段、被逐出的段或代际变化必须读取原文逐条重验。分段前后哈希必须连续，最终事件数量及尾部与状态版本一致。隐藏工厂中的段变化也会触发重验。
3. 行版本指纹用于判定是否可复用已验证内容，不能被称为外部签名。指纹包括顺序中的序号、tableoid/xmin/ctid，且绑定数据库OID、服务器启动代际、事务ID周期及关系/文件代际。它不能仅依赖revision或缓存时间。VACUUM FULL、恢复、关系替换和周期变化使证明失效。
4. 缓存仅驻内存，最多保留1024段证明；使用现有内存准入计量并可逐出。重启后重新核验，不从未经认证的JSON文件恢复“可信检查点”。失败的或未完成的事务不发布新证明。
5. 即便正文可复用，每次仍检查完整段集合的元数据和当前范围。该方案减少应用内存、正文传输及重复哈希，数据库元数据扫描仍随事件数增长；不能据此承诺无限数据或恒定延迟。
6. 缓存证明模式必须通过旧段改动/删尾/改序号/隐藏事件篡改、重启/恢复/表重写、并发读写及回滚场景；未通过时保留完整流式校验，不能以“优化性能”为由跳过核验。

查询结果仍只返回必要摘要。原before/after、请求内容与供应商联系方式不因容量改造增加对外披露。

## 5. 数据迁移、索引与归档

保留既有实体/事件格式和`idms_spares`独立schema。专用迁移角色添加命令事实、关联ID、档案编码、采购状态/时间、流水组合及凭证唯一性所需索引；业务账号继续使用现有最小权限，不授予DDL、事件UPDATE/DELETE/TRUNCATE或越过人工责任的新权限。

迁移先只读核对已有资料、审计、重复编码/凭证及关联边界；如有冲突即停止并给出受限诊断，不能自动合并或删除。所有DDL在维护流程下事务执行，失败回滚；记录迁移版本和运行代码最低版本。回退应用前确认其容量和schema兼容条件；备份恢复只在隔离库验证，不能以恢复旧库覆盖新业务作为默认回退。

归档采用保留完整原文的加密备份档案，manifest增加备件版本、事件首末锚、数量和逐表摘要，使用已有私密备份密钥与授权备份角色。先在隔离库恢复，再核对全部事实、库存、关联业务与审计锚。保留旧备份格式读取能力，超出既有备份体积预算的任务应明确拒绝或使用流式档案实现，不能将超大dump一次装入内存。

本阶段不自动清除热库记录。保留期未由企业确认时保留所有历史；加密完整备份不等于已经完成冷热查询分层。迁出、清理和跨服务灾备继续在正式交付清单独立验收。

## 6. 改动模块边界

- `spares.ts`：保持领域校验，加入显式聚合事实接口，原纯领域全状态测试作为对照。
- 命令事实SQL模块：只读取当前动作所需实体/聚合，负责参数绑定及必要索引计划。
- 分页查询模块：summary/list/detail/options/workorder-usage及严格分页，负责当前范围、数据新旧版本及必要字段。
- 引用范围模块：复用现有已批准资产与当前工单语义，在同一连接快照核对，不加载整个旧工作区。
- 审计验证模块：完整流式验证、分段证明及代际失效、取消与缓存预算；与可见结果筛选分开。
- 迁移及备份模块：迁移版本、索引/唯一性核对、归档锚、完整备份和隔离恢复。
- 现有原生网页：保持九页签布局；列表、详情、选择器分开加载；工作台用汇总，工单用净用量接口；切换身份、范围、条件或记录时丢弃迟到结果。

## 7. 验收证据

1. 同一组真实领域命令在完整内存参考模型和隔离PostgreSQL新路径中结果一致，覆盖建档、采购退回/重新提交/独立批准、分批收货/退供/关闭、领退/调拨/更换、期初/盘点/报损及票款。
2. 通过应用账号执行并核验超过原门槛的实际业务：至少10001实体、20001事件后仍能分页、查询旧记录、提交采购/收货/领退/审批及读取净用量；不是只给纯函数喂数组。
3. 验证只加载动作需要的实体/聚合；页面最多100行，选择器可搜索末尾档案。读写均不能退回原全实体数组，也不能把记录上限简单提高后称作解决。
4. 验证重复收货、争抢最后库存、同键不同内容、过期版本、本人审批、撤权后的旧回执、跨工厂/设备/工单、停用和重复凭证；并发失败没有部分流水、回执或版本推进。
5. 完整审计及分段证明的所有失效/篡改场景通过，含隐藏记录；对已验证旧段的变更不能仅因版本未改而被放过。
6. 在当前实际数据库版本做取消/连接池耗尽/超时/串行化失败/进程重启及隔离备份恢复；结束后无占用连接、未清事务或遗留QA库。
7. 真实既有账号只读复核桌面及390px列表/筛选/详情；合成数据只进隔离环境。数量、金额、单位、全范围汇总与当前页数区分明确。
8. 记录本机条件、SQL返回行数、应用峰值持有量、响应字节及耗时。给出实测范围与剩余线性数据库扫描成本，不能将定向通过称为生产SLA或全站无限容量。

## 8. 实施顺序与发布条件

先实施命令聚合事实和流式审计，在隔离库与完整模型对照；再实现SQL分页及所有页面消费者；之后加入有界分段证明与归档恢复，最后进行超过旧门槛的联合验证。实现期间保留现有主站，隔离验证通过后在明确本地维护窗口切换，不向当前企业造单。

任何不变量失败则维持旧主站和审计完整校验，明确未完成项。只有上述验收均通过后，才把本阶段标记为完成。企业多岗位签收、同版Git发布/云端部署、备案/TLS、跨服务灾备及最终培训视频仍保留在总目标，不因本设计通过而关闭。

## 9. 官方依据和设计自查

- PostgreSQL 16 [系统列](https://www.postgresql.org/docs/16/ddl-system-columns.html)：行版本可用于短期复用判断，ctid不是长期逻辑身份，事务ID有周期。因此本设计绑定代际并允许重验，不将其作为业务标识。
- PostgreSQL 16 [事务隔离](https://www.postgresql.org/docs/16/transaction-iso.html)与[显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)：快照、并发更新和锁次序需共同设计，不能把RR等同于没有重试需求。
- PostgreSQL 16 [DECLARE](https://www.postgresql.org/docs/16/sql-declare.html)：事务内游标可分批读取；本设计不使用跨事务WITH HOLD保留大量结果。

以上是根据官方行为和本工程现状作出的设计选择，尚非新实现已通过验证的结论。自查：没有删除历史、扩张账号权限、冒充实际支付、跳过当前范围、把一页当总量、虚构生产容量或恢复旧Native大型项目。数据库私密连接配置、企业记录及密码不写入方案和公开材料。当前根目录无Git元数据，本设计保存在既有项目内，未伪造提交或自动公开推送。
