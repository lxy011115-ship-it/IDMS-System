# 增量运行入口与备件业务整合设计（待评审）

日期：2026-11-05。此文件是下一阶段设计，不表示代码已实施或本机已换版。当前已批准的采集恢复方案B继续有效，不重复请求其批准。

## 要解决的问题

当前本机运行`server/index.ts`。遥测接收先经过`mutate`加载企业工作区、校验原业务及审计，再处理回执；历史增长仍增加单次事务成本。此前75k/85k合成验证已证明默认512MiB任务预算内可提交和回滚，但不能据此承诺持续增长或生产吞吐。

仓库已存在增量映射、遥测领域、治理、预测、维修、共享认证、统一站点及冷备恢复模块。这些是应复用的工程资产；历史独立验证、旧统一入口和当前运行版本之间仍有差距。尤其2026-10-29以后新增的备件采购、用料计划、分页及分段证明不能被旧控制台替换掉。

当前网站和登录在线，原10000条消息在逐条恢复；序号冲突拒绝保留在隔离区。此阶段保持原服务及源码绑定，不以重启、清缓存、改签名或提高预算缩短恢复。

## 已核对的关键依赖

| 当前能力 | 源码依据 | 整合约束 |
| --- | --- | --- |
| 主站路由、上传及原业务写入 | `server/index.ts`、`server/import-api.ts`、`server/postgres-repository.ts` | 必须逐个清点全部HTTP和后台写者，不能只替换MQTT接收者 |
| 原采集接收 | `server/telemetry.ts`的`receive` | 保留治理决定、原键去重、冲突原因、点/回执/审计同事务及提交后ACK |
| 增量遥测 | `server/telemetry-map-v4.ts`、`server/domain-map-v4.ts` | 重用既有受保护根、成员证明、CAS及未知提交解析；先验证与当前信封语义相容 |
| 统一站点与共享认证 | `server/site-console-runtime-v4*.ts` | 保留真实OIDC、当前账号范围、会话撤销及独立终审，不因整合重新初始化账号 |
| 备件的当前设备和工单引用 | `server/spares-current-refs.ts`、`server/spares-query-scope.ts` | 当前引用依赖原业务投影；必须改为与实际生效的业务版本相符的读取及授权 |
| 备件并发和一致性 | `server/spares-transaction.ts` | 当前写事务先锁`public.business_state`再处理库存；新根不能绕过此锁产生陈旧授权或引用 |
| 备件审计与归档 | `server/spares-audit-proof.ts`、`scripts/backup-support.mjs` | 保留完整采购/库存/回执、分段审计、备件锚和同一快照归档，不只复制可见页面 |
| 就绪、资源及正常停止 | `server/runtime-readiness.ts`、`services/runtime-stop.ts`及现有启动器 | 新入口必须提供等价的就绪/资源契约并等待全部实际任务收尾 |

上表是初步依赖清单，实施第一步须从实际导入图核对准确模块名、每条路由和每类写者，形成逐项可执行矩阵。没有在本轮重跑全部历史v4验证，也不声称所有资产当前可直接部署。

## 方案比较

| 方案 | 做法 | 收益与代价 |
| --- | --- | --- |
| A（推荐） | 在独立开发目录中整合现有增量运行模块与当前备件能力，先建立兼容边界，再完成全部读写及恢复验证 | 直接处理历史线性成本，并保留新业务；工作量较大，按下述阶段推进 |
| B | 继续保留全历史主站，先完成真实岗位UAT及运行规程 | 可先取得业务反馈，但采集CPU及增长成本仍未解决，不能将其当作容量优化完成 |
| C（不推荐） | 只把MQTT接收替换成增量实现，其他入口继续使用旧全量状态 | 表面改动较少，但会产生两套写入权威、陈旧工作区和不一致备份，不满足交付目标 |

## 推荐方案A的分阶段实施

### 第一阶段：当前业务依赖闭包与备件兼容层

建立独立Git工作目录及独立合成数据库，不复制`.local`、原生运行时、企业密钥或真实业务数据；依赖按锁文件安装，不共享可变构建输出。不修改当前运行目录中的`server`、`services`、`public`或依赖。

以当前完整路由和写者为基准，列出原业务事务、治理、上传/审批、工单、预测、AI/工作流outbox、采集、备件及认证审计的权威来源、锁顺序和未知提交恢复方式。已存在的模块逐项复用；缺口逐项补齐，不并行复制另一套规则。

首先解决备件“当前设备/工单引用＋同事务授权”边界：同一租户、同一已验证生效版本中读取必要引用，保持原可见范围、独立终审、引用存在性及禁止越权规则。公共业务更改与备件命令存在共同同步边界；必须实际证明设备移出范围、工单撤销/变更与领用并发时不会使用陈旧许可。库存、采购及其审计仍保持同事务提交。

如果所选增量模型不能提供这个同步边界，整合保持禁用并修正实现；不通过“双写旧根和新根”或定时复制投影掩盖不一致。

### 第二阶段：全部入口接线及有界事务

完成矩阵中所有当前接口、后台写者及页面消费者的接线。业务规则使用已有领域函数，保留当前六个一级入口和备件采购全流程。主站不因兼容而退回读取整个历史；读取范围、映射键/字节、SQL行数、队列及内存由现有预算计量。

未知COMMIT只以原请求键、摘要和当前权威回执解析；观察超时不认作未提交，不另起替代任务。所有外部效果（工作流、AI和ACK）使用各自既有幂等/回执协议；同一业务动作在重试、重连或重启后仍只产生一次实际结果。

### 第三阶段：隔离迁移、备份恢复与联合验收

在合成旧库中验证完整原件、旧业务摘要、审计、备件及所有辅助表迁移。所有旧写者经过实际持久围栏后才启用新权威，任何混合或遗漏写者均拒绝。原文件、旧根、迁移锚和失败记录保留。

业务库、认证/会话、工作流、AI网关与边缘缓存分别声明一致性范围。已有“企业业务库档案”明确不覆盖独立服务，不能据此宣称平台灾备完成；完整恢复必须验证每个跨服务动作和外部回执关联。

### 第四阶段：受控换版候选

形成可审查的版本、运行摘要、配置差异、迁移及回退步骤，先在隔离完整平台实演。当前本机换版、企业岗位业务签收、阿里云部署、域名备案/TLS分别保留为后续门槛；本设计不直接执行这些动作。若未来换版前出现新的停机或权限影响，先呈现该次具体候选及影响。

## 验收依据

| 要求 | 必须取得的证据 |
| --- | --- |
| 当前功能无丢失 | 完整路由/写者/页面矩阵，无遗漏；上传审批、设备、治理、预测、工单、备件与权限均走实际接口 |
| 备件与当前业务一致 | 新权限/范围及设备/工单变更与库存命令真实并发；旧引用或越权明确拒绝，余额与审计一致 |
| 增长不回到全量历史事务 | 至少在75171与85171条合成审计下，对同类读写记录实际读行/键/字节及计量峰值；固定逻辑工作集不随全历史规模线性重读；耗时只作为本机观测 |
| 现有备件容量能力保留 | 超过10000实体、20000事件时的分页、命令、完整审计、用料计算、并发与加密归档恢复继续通过 |
| 正确去重与未知结果恢复 | 真实COMMIT结果丢失、断ACK、进程正常退出及重新连接；原键/原字节保持，无重复库存、工单、测点或审计 |
| 权威与完整性 | 旧写者持久围栏、租户/角色/根/节点篡改、跨范围和过期游标负例；既有原件/签名/锚保持 |
| 平台恢复与退出 | 所有已准入任务、连接池、MQTT/OPC和外部效果均有真实终态；一致备份及隔离还原后重复验证业务关联 |
| 用户可用 | 真实OIDC登录、撤权、独立终审及桌面/窄屏业务流程；隔离合成账号的结果与企业岗位签收分别记录 |

不将512MiB逻辑任务预算当作RSS硬上限，不把本机耗时当作生产SLA，不通过清空历史、提高限额或删检查获取绿色结果。
