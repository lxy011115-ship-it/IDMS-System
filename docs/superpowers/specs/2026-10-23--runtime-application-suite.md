# 恢复后应用进程的正式登记与管理

## 目标

接续已批准的完整系统整合计划，将恢复后的网站入口、各企业对账后台，以及治理、维修、预测后台交给正式管理入口。既有原生恢复、身份权威、SQL 门和业务 worker 保持原字节。第一步覆盖应用进程登记；PostgreSQL、身份 JVM、工作流 JVM、设备通道和原 owner 的可信移交仍属于完整目标，不因本步骤完成而取消。

## 方案选择

沿用验证脚本逐个 fork 无法形成可部署的完整应用清单；按已有 PID 补登记不能建立可信的创建/退出关系。采用由管理器自行创建全部应用子进程、固定私密配置图和 SQLite 持久事件的方式。管理器不接受外部 PID、可执行文件或任意脚本。既有进程的移交不通过此入口猜测完成。

## 清单和身份

清单显式声明恢复 control ID、source SHA、当前 authority SHA、企业集合和组件。每个企业必须恰有 GOVERNANCE、MAINTENANCE、PREDICTIVE、RECONCILIATION；全站恰有一个 SITE。组件 ID 唯一，SITE 的实际企业集合必须与清单一致。每个启动结果须匹配真实 child handle PID、本次随机挑战、清单摘要、组件配置摘要及实际恢复/权威绑定。

私密 JSON 图按指向 JSON 的 File/Files 引用固定原始字节，限制文件数和大小，拒绝符号链接、多硬链接、读取期间变化和别名入口。活动 SQLite 存储及非 JSON 服务制品继续由原恢复/权威/业务加载器检查，不把可变存储当静态配置。每次业务迭代/HTTP 请求前检查原配置及恢复权威。密钥、SQL 密码、Cookie 和原配置正文不进入事件输出。

## 生命周期

新管理目录只能创建一次。SQLite WAL/FULL 保存清单、源码/配置摘要和按序哈希关联事件；子进程启动前提交意图。此版本不将重新打开旧目录解释为接管或恢复成功；后续可信 resumer 须以此记录继续实现。

先启动企业后台，全部 READY 后再启动网站。READY 只证明当前管理清单完整就绪，不承诺业务原子启动或长期健康。启动部分失败或任一成员异常退出时，先关闭网站入口，再停止后台并等待在途任务排空；业务幂等和租约继续由原协议约束。

停止请求具备本次 request ID，DRAINING/CLOSED 经同一父子 IPC 回传并绑定原组件挑战。完成必须同时具备正常关闭回执和管理器实际持有的 child close(code0, signalnull)。不得以观察超时或单行 CLOSED 冒充退出，不向未知 PID 发信号。父 IPC 断开时子进程自行关闭。未能取得终态时保留未完成状态和证据。

## 验证与边界

先验证清单缺项、重复、错误企业、注入 PID/程序、配置变化与事件篡改拒绝，再在新的完整恢复环境启动两企业九个实际应用进程，执行真实治理/分析/独立复核/维修与对账读取，验证正常排空和失败关闭。证明来源和清理记录须覆盖新增组件，不重用历史成功报告冒充新执行。

不切换原 Windows 或云端运行实例，不修改已经冻结的应用、QA、原件或 JAR，不启用未备案域名。完整故障矩阵、跨主机/原 owner 移交、全部生产组件、容量/HA/PITR、真实设备及最终图文视频交付保持待办。

## 当前入口与证据要求

当前候选应用入口为 `scripts/runtime-application-suite-v2.mjs`（管理器与子入口均 V2）。V1 文件保留失败案例的可复核字节，不作为推荐启动入口。本机 V4 原生 QA 实际 25 项及独立清理均通过，Linux 结论须读取对应提交的实际 CI；应用登记不覆盖 PG/JVM/MQTT 等全部生产依赖或旧 owner 移交。

对新 QA 自有 fork，终态同时要求实际 exit、两条输出管道关闭和 IPC 断开。不能仅凭目录中的 GROUP_CLOSED、PID 不存在、观察超时或任意形状对象推定管理器零码退出。Windows 最小复现揭示的 ChildProcess close 事件缺失不降低以上事实要求。
