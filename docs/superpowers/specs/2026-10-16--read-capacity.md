# 数据读取容量：独立一致读与变更校验

延续完整商用方案A和已授权待办。首先消除数据中心及两个完整筛选导出在SQL分页外层仍读取完整企业工作区的问题；其余领域的增量工作区、写容量、worker/HA仍继续，不以这一批替代全部性能目标。

比较三种路径：仅按business_state.revision缓存会漏掉绕过业务事务的SQL更改，拒绝；每次把原文件/输入/全审计传到Node后哈希保留现状但成本随历史增长；采用同一REPEATABLE READ READ ONLY快照中的MVCC行版本指纹，变化时完整校验，未变化时复用已证实结果。

指纹绑定pool/tenant、数据库OID/服务器启动时刻、64位snapshot高32位epoch、关系OID/relfilenode/pg_class版本、全部依赖关系当前可见行的tableoid/xmin/ctid摘要及runtime_state视图定义。它不是业务标识，也不替代内容摘要；其含义仅是同一PostgreSQL代际中当前SQL可见行版本未变。正常UPDATE/INSERT/DELETE、表重写、DB重启及XID代际变化触发完整校验。磁盘字节损坏/绕过PostgreSQL物理篡改仍属于数据库校验和、备份及生产存储验收，不宣称由此缓存保证。

复用证明只保存少量指纹与企业状态，不保存文件/记录/审计数组。冷校验必须成功验证原v3内容摘要、原文件/冻结映射/设备类型、审计链、work_orders镜像、全部事实/类型投影与更正账本；失败不缓存。并发相同指纹校验合并，防止相同快照被多个读连接反复重建。缓存命中仍每次查询数据库指纹，无TTL或内存降级。每个请求仍独立使用可信身份和SQL设备范围，不能缓存用户查询结果或权限。

四个数据路由直接进入这个独立只读事务，不走全局写队列、不更新全局Store或importData，不占第二个业务连接。计数/分页/选项/导出与校验保持同一快照；允许与企业写事务并行，读到提交前或提交后的完整状态。其他GET保持业务SHARE锁及本机队列，使用相同指纹判断是否重建工作区；工作副本递归冻结，任何写操作（包括失败）使应用标记失效。SHARE锁在REPEATABLE READ事务内获取，因并发提交导致的40001只在进入业务回调前有限重试；不能在已经输出响应后重试。写操作继续独占锁/全校验，业务schema3与认证schema1不更改。

验证：真实隔离PostgreSQL/Keycloak/两个核心、数万记录和多MB原文件；旧外层完整校验与新SQL结果逐字段相同，热路径无完整payload传输，记录SQL响应字节及p50/p95而不把单机时延当商用SLA。证明缓存不按revision盲信：同revision篡改、回滚、原文件/投影/审计损坏、VACUUM FULL、跨租户/工厂/用户、重启/存储中断必须失败关闭或重新校验。锁住写事务时读应返回完整旧快照，提交后重新校验新数据，未提交内容不得出现。保留10,000行导出边界、更正版本与独立审批/共享会话。原库只读核验/备份和受控升级后再更新记忆。

执行顺序：1) 指纹和有限校验证明；2) 同事务SQL守卫与主路由；3) 真实容量/并发/故障/契约专项；4) 相关回归；5) 原平台备份/受控重启/只读验证；6) 文档和项目记忆。既有用户继续开发授权适用，不增加重复确认或改变完整目标。

容量实测发现测点结果重复连接有效记录，导致2万条记录时超时。进一步让类型CTE直接携带来源/有效版本/正文，去掉冗余自连接；设备点数和记录数按设备一次汇总。冻结输入与validRows通过有序匹配索引拆分，保留重复行对应与有效行顺序，避免逐行重复扫描/序列化。全部新查询结果以文件领域契约逐字段比较；旧基线若在大数据下超时如实记录，不把失败伪装成相同结果。
