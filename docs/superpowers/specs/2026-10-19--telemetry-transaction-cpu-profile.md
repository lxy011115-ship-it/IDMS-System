# 采集完整事务CPU定位

沿用已授权容量与完整商用方案A开发。上轮原链路约300秒消耗约299秒核心CPU，仅新增178点；本项需要定位当前实现成本，再决定优化，不能把静态相关性当热点证明。

采用独立QA库、最小应用角色、原完整迁移/schema和原TelemetryService.receive。QA启动轻运行bootstrap与真实registry，保留mutate/企业锁/readEntities/审计校验/workspace/写后核对/canonical全过程。直接调用接收方法并捕获真实签名ACK，当前范围为接收事务，不重复宣称MQTT/OPC链路性能。原运行进程不附加调试器、不改配置，不注入原库。

审计历史按1000、10000、45000逐步增加；使用原appendAudit从准确tip生成有效链，追加时读取QA当前完整payload，保留前一阶段实际接收事实。每阶段独立新child加载当前轻bootstrap，预热一个新事件，然后分别对三个新事件、三个同字节重放采集Node inspector CPU样本和实际process.cpuUsage/内存/调用时长。采样仅针对自身进程，不启用网络调试端口；不调大默认预算。

采样堆栈按函数/文件归集self与inclusive时间，分别统计idle/GC，公开汇总不包含报文/凭据/SQL参数。SQL包装只在QA记录查询分类次数和包含驱动/JS行处理的壁钟时长，不能称作服务器SQL执行时间。独立连接核对点/回执/审计增量、完整payload根和审计链，重放没有新点/回执/审计；前一阶段历史完整保留。

所有子进程观察真实close，清理仅针对随机独占QA库/角色与精确OID；保留私密原profile用于证据核验，凭据和临时数据库清理。原始profile不公开，公共结果只包括归一化函数摘要、源码pin与验证结论。完整源/角色/进程与采集队列后验保持，结果用于选择下一个实质优化，不构成已优化或容量验收。
