# 平台依赖控制器设计

承接原方案 A 的整套管理与原运行迁移要求。现有应用组已登记业务后台和网站入口，PG、Keycloak、Flowable 已有独立正常生命周期。此设计把这些实际入口连接到同一个控制器；原设备、模型、容量、灾备、商业与最终材料要求继续保留。

## 方式选择

采用固定组件类型调用已有生命周期模块：能复用已经验证的实际句柄、绑定与正常关闭证明，并直接连接现有应用组。全量迁往容器/操作系统服务需要另做现有私密资料及数据目录迁移，当前不作为本步骤替代方案。接受外部 PID 或任意回调的通用编排器无法证明组件归属，不采用。

## 输入与归属

控制器只接受显式的私密配置和已验证工具句柄，不读取旧 `.local` 账户或调用旧 `start-platform.mjs`。清单登记每个 PG 的独立 ID、目录、system identifier、端口与账户；身份/工作流必须声明所依赖的 PG ID。服务端点须与已登记 PG 的回环地址和端口一致，拒绝未登记依赖、重复目录、重复端口、环形依赖和 PID 字段。

不隐式创建、迁移或重置数据库。首次配置生成、数据库角色建立和原数据受控迁移是独立阶段；只有经过对应验证的干净离线目录才可进入启动控制器。身份权威、运行配置和应用恢复准入继续沿用既有校验。Windows 控制器要求非管理员运行；若要提供正式受限 token 启动入口，应单独固定程序和配置摘要并验证，不能复用任意程序启动器。

## 启动与就绪

控制器 API 必须先把自己的句柄返回调用方，再异步启动，避免后续启动失败丢失已创建子进程。按 PG → 身份/工作流 → 业务后台 → 网站入口顺序运行。每个实际生命周期句柄创建后立即保留并记录；就绪不能只凭端口可连接，需要原 PG SQL 身份、身份 JVM 绑定与 OIDC discovery、工作流 JVM 绑定与各租户认证 status、最后应用组的原权威检查。

启动取消先阻止后续创建，再等待当前创建操作取得实际句柄，最后只关闭本次已经创建的组件。不能把部分启动记录为整组 READY。意外退出或固定配置漂移先撤销入口，再排空仍由本控制器持有的组件。

应用组入口使用固定 `runtime-application-suite-v2.mjs` 的实际 fork 适配层，创建后立即返回根进程句柄；保留原组内管理器的实际子进程所有权和启动取消机制。就绪时核根 PID、清单摘要、登记 owner 与 GROUP_READY；停止使用同一 IPC request ID，正常证明还须核根实际退出、管道和 IPC 关闭、登记中每个已创建成员的停止/关闭/退出，以及 GROUP_CLOSED 或明确的部分启动取消。不能仅因根进程退出就声称所有成员已正常退出。

## 停止与持久证据

先停止网站接入与应用后台并等待实际业务排空，再正常关闭工作流和身份服务，最后核 PG 客户端与 prepared transactions 排空后执行 smart stop。依赖未正常退出时，不能把下游数据库宣布正常停止。每次停止有固定 request ID，重复请求复用同一操作；不以超时或连接断开冒称退出，不使用未知 PID、删除 PID 文件或通用强制关闭。

控制器私密目录存启动意图、组件创建/就绪、停止意图、实际退出和各生命周期证明的摘要。凭据和原始日志不输出。写入证据失败必须保留实际句柄并报告未确认状态，不能创建第二组来掩盖第一次。中断后仅凭历史记录不能重建 ChildProcess；后续接管协议须另有明确证据。

## 完整依赖与可选模块

手动上传优先模式仍成立。需要设备采集或模型时，其 broker、边缘、预测服务、AI 网关与模型服务也必须显式登记，并验证各自正常关闭；不能把原服务当成已归属的新依赖。可选能力未配置时要明确停用，并保留规则/人工路径。模拟器只用于沙箱。完成核心四类接线不等于全部生产依赖登记完成。

## 验证与交付界限

使用全新隔离资料，实际覆盖 PG、身份、工作流、两租户应用和网站共同启动及逆序排空；真实 OIDC、上传/审批/维修流跨重启保持，启动取消、重复停止、故障/配置漂移和第三方客户端阻止数据库停机。独立检查所有实际自有进程终态、JDBC 清空、PG 干净关闭及原资料保持。Windows 与 Linux 分别给证据；单元测试、单独 PG13 或旧应用25不能代替该组合验证。

原 Windows owner、云运行版本、公开域名均不因实现此控制器自动切换。原 owner 缺少部分正常关闭通道，需要明确迁移协议与排空证据；网站 ICP 未完成，公网仍不激活。最终手册、真实截图及演示视频应针对最终完成并验证的版本制作。
