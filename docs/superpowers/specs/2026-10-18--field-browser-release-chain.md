# 现场浏览器批准与最终发布证据联合验证

沿用已授权现场通道第6/7项。当前正式源→归档→新目标→当前OIDC独立CLI审批→激活→新流→导出→清理后离线校验已验证，但浏览器独立审批是另一轮证据。需要在相同实际恢复目标上证明浏览器批准的准确plan/facts就是正式激活消费的计划，然后由相同设备/配置的新流产生可离线重算的证据。

不改生产授权、流程或激活规则。仅扩展自有QA组合：浏览器原有提交/批准、PKCE/CSRF/Origin、限域/外租户/系统写、自审、reader退休/新cookie、配置与staging漂移检查保留。在明确combined模式下，将会改变真实Flowable的浏览器漂移负例留给独立UI测试运行，组合内由正式激活recover在采集与导出后执行真实Flowable推进及拒绝。两个范围分开报告，不能声称组合内测试了浏览器漂移拒绝。

组合中维护reader完全关闭、浏览器上下文退出后才恢复自有PKCE callback listener，供后续正式CLI及auditor真实登录。不得并发争用原端口；恢复listener的IPC只能在明确combined模式、先前listener已关闭且所有组合旗标成立时调用。正式activate初始核对实际当前planId/facts与浏览器批准视图相等，不能再提交替代计划。

发布前保留旧13组相关回归。catalog原测试默认会覆盖运行中的旧workflow jar，因此只在显式release QA preload中对该测试的workflow-local导入使用隔离Maven输出/启动适配；原生产launcher、旧两jar和已有recovery-build不变。此适配不替换目录业务断言。另补独立机器HTTP OpenAPI说明，结构/SDK模型与真实HTTP证据分开。

源码与公开证据冻结为明确的开发审阅快照，排除运行配置/凭据、客户原件、raw日志和二进制依赖。新只读CLI按外部清单及可选可信预期manifest SHA检查路径、文件集合、字节和SHA，拒绝缺失/多余/重复/穿越/符号链接和超限；失败保留输入。清单自报SHA不提供外部真实性、时间或防回滚证明，也不授予部署/现场准入。发布前需要两处快照独立逐文件校验，旧十轮清单与66契约保持。

验证先用完整联合旗标运行同源真实peer全链并保留准确终态，再单独运行原浏览器真实Flowable漂移负例；两组不并行修改角色/authority。新冻结快照只能在必要实际证据、源码SHA、旧66契约/十轮双份与原运行数据核验齐备后生成，清单明确自有回环协议测试/人类core路由demo等范围，不将开发快照或单一绿灯当完整商用验收。原正式FIELD仍未部署，跨服务灾备/容量/跨宿主/Linux/OS隔离/外部时间与防回滚等商用缺口仍继续。
