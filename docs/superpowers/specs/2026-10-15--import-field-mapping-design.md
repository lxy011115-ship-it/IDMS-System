# 企业上传字段映射设计

日期：2026-10-15。状态：按后续继续开发指令实施，本机与隔离验证通过，非商用验收。承接“多类型设备，先做数据管理”与统一上传方案。本规格仅覆盖字段映射，不代表整体商用目标完成。实施记录见../plans/2026-10-15--import-field-mapping.md，使用见../../import-field-mapping-guide.md。

## 1. 现状与最小目标

目前七类CSV/XLSX/JSON上传共用校验、批次、独立人工终审与来源追溯。CSV/XLSX要求标准英文字段名，客户必须先手动改表头；JSON接口仍使用标准机器字段。已有模板中心具备草稿、修订摘要、提交冻结、独立发布、导入导出和历史版本。

本批目标：让企业选择已发布映射，把“设备编号”等原表头显式对应到标准字段，复用原批次与规则；设备台账、测点定义、测点记录和其余四类文件都遵守相同边界。不能用映射绕过设备编码、单位、时间、权限、去重或人工终审。

本批不包括值转换、单位换算、日期猜测、数据更正、AI自动发布映射、工作表合并、任意脚本或JSON自定义字段映射。设备名称值含中文可以，标准编码值仍须满足现有规则；客户应提供编码对照而不是由系统猜测。

## 2. 三种实现路线

1. 推荐：复用模板中心治理，增加独立的import-mapping用途。复用贡献者不可自审、版本冻结和导入导出，避免两套发布流程；需要向后兼容原维修模板schema及页面。
2. 新建独立映射中心与发布流程。领域更独立，但重复权限、版本、审批和审计机制，当前收益不抵成本。
3. 上传时临时映射、直接生效。演示最快，但难约束企业标准和复核变更，不能满足本方案的独立发布与历史追溯要求。

字段映射只改变标准化输入，不改变数据管理和预测模块边界。

## 3. 模型与兼容

模板manifest新增purpose字段，可取maintenance-form或import-mapping。现有schemaVersion=1、未带purpose的合法维修模板仍走原校验，不增补字段或改写旧摘要，维修运行绑定仍限定原maintenance-form编码。新映射模板使用独立编码，例如import-map-pump-register，不与maintenance-form竞争。模板校验按用途分别执行：维修模板保持原要求；映射模板schemaVersion仍为1，新增importMapping配置而不允许maintenance配置，modules必须包含新增data-import模块并保留原安全策略；不因此放宽其他未知字段。

映射配置包含：数据类型、精确来源系统编码、标准模板版本1.0.0，以及sourceColumn/targetField一对一条目。继承使用现有父版本引用，仅表示来源关系；不声称已完成自动差异合并。包的发布和跨企业导入继续走现有模板流程，导入只创建草稿，接收企业必须重新独立审批。

配置结构约定为manifest.importMapping中的dataType、sourceSystem、templateVersion和columns数组；columns元素仅允许sourceColumn和targetField。模板外层templateKey、version、industry、parent以及idms-template-v1包格式保持原契约。purpose/importMapping参与内容摘要；不能通过更换用途覆盖同一版本。

示例映射关系：

| 企业原表头 | 标准字段 |
| --- | --- |
| 原始记录编号 | source_record_id |
| 设备编号 | device_code |
| 设备名称 | device_name |
| 工厂编码 | site_code |
| 产线编码 | line_code |
| 设备类型 | equipment_type |

此示例为设计说明，不向企业库插入演示设备或发布模板。

发布前校验：

- targetField必须属于该数据类型现有白名单，不得指向tenant_id、actor_id、审批、审计、状态或原型链等保留字段。
- 每个来源表头与目标字段只能出现一次，必填标准字段必须完整覆盖；条件必填字段仍由行校验判定。
- sourceColumn长度1–120字符，不含控制字符、双向控制符或零宽混淆字符，必须已去除首尾空白；拒绝__proto__、prototype、constructor等保留名称，不进行模糊匹配、拼音匹配或Unicode同形替换。
- 条目数量不超过当前数据类型允许字段数；不允许脚本、表达式、默认常量、字段拼接、静默忽略列或改变安全策略。
- 模板绑定精确sourceSystem和dataType，不得跨来源系统、跨数据类型使用。

## 4. 上传、冻结与错误处理

未选择映射时，保持原标准CSV/XLSX行为。选择映射时，multipart新增mappingRef字段，内容为templateId、version、contentDigest；字段仅允许出现一次。服务端从真实身份得到租户，在原写事务中解析并核对发布版、用途、类型、来源、版本和摘要，不接受调用方提交的映射规则本体。

只允许新批次引用当前PUBLISHED版。旧版退役后不能创建新批次；已经冻结的旧批次继续按原映射完成审批，不从最新模板重算。当前不存在紧急吊销模型，因此本批不把退役等同吊销；如需禁止待审批次，应由独立终审人退回或驳回并保留理由。

文件解析先保留原表头和物理行号。用于匹配的表头采用既有首尾空白修整规则；修整后重复、空表头、不可见混淆、超长表头均拒绝。映射模式允许中文普通表头，输出只包含白名单标准字段。标准模式仍严格要求原标准表头，不能为了支持中文而放宽所有入口。

每个已出现列必须被明确映射，未知列拒绝；必填列缺失拒绝；未出现的可选映射列允许省略，不自动补值。错误报告同时显示原表头、标准字段和物理行号，缺列错误列为表头级，不假造数据行。原始文件继续原样归档，不用规范化后的CSV代替原文件。现有宏、公式、外部链接、展开容量、编码与文件限额检查必须保留。

JSON /data-imports/records保持标准字段协议，本批继续拒绝mappingRef，向第三方明确返回不支持，防止同一字段双重转换。第三方若需使用企业表头可调用文件上传接口。公开OpenAPI明确这一区别，并继续保留后续JSON映射扩展边界。

## 5. 批次、审批与数据血缘

新批次固定保存mappingBinding：模板ID、编码、版本、内容摘要、用途、数据类型、来源、映射规则副本及绑定摘要，并保存原表头序列；snapshotDigest在原规则/模板/来源/规范化行摘要基础上加入这些冻结信息。无映射的新批次和全部历史批次继续原摘要路径，不回填或改写旧数据。

审批前核对绑定摘要、映射规则、类型/来源和批次快照；核对失败停止审批，不从当前模板静默修复。领域表只接收同一冻结标准化输入，错误、审批、审计、幂等和领域表继续在原租户事务内提交，失败整体回滚。来源查询通过批次定位到映射版本与原表头，不能只显示最新配置。

上传幂等摘要必须包括mappingRef。同一幂等键与不同映射引用返回409；重试已成功请求返回原批次，即使映射已退役也不重复创建。已过期引用只有创建新批次时被拒绝，不能破坏原请求的幂等回放。

模板发布与数据入库是两次独立审批：发布模板不自动批准批次；批准批次不授予映射发布权。创建、编辑或提交模板者均不能发布本人版本；上传者叠加角色也不能审批本人数据；AI与接口身份不能执行人工终审。

## 6. 页面与接口边界

上传页增加标准模板/已发布企业映射选择，按数据类型和来源过滤。显示映射编码、版本、来源与字段对应预览；用户选择来源变化时清除不兼容映射。批次详情和终审包显示原字段到标准字段的对应及冻结版本，历史无映射批次继续显示标准模板来源。

模板中心增加用途筛选、映射草稿编辑和预览；继续使用现有创建、修改、提交、独立审批与导入导出接口。只对明确声明支持的用途显示runtimeApplicable，不能把维修模板或未验证模板当成上传映射。

旧模板、旧上传样例、原JSON接口、维修工单绑定和数据中心查询必须保持兼容；不以隐藏旧功能回避回归。

## 7. 测试与交付门槛

- 单元测试：七类字段白名单、必填/可选/条件字段、重复来源/目标、保留字段、原型污染、中文/不可见表头、缺列/多列、非法映射包。
- 解析测试：CSV引号/跨行/空白行保留原物理行号；XLSX原表头保留，公式/宏/外部链接/超限拒绝；标准模式不被放宽。
- 集成测试：真实OIDC/PostgreSQL的模板独立发布、贡献者自审阻断、跨租户引用、类型/来源/摘要不匹配、退役及幂等回放、旧批次冻结与新版本并行。
- 事务测试：领域表或SQL审计故障下，映射批次、审批、业务、幂等与来源索引整体回滚；只在本次随机隔离QA库注入故障。
- UI测试：中文字段文件预览、终审包及追溯、XSS/CSV错误导出注入、桌面与320/390手机、维修模板及标准上传回归。
- 迁移测试：重启后绑定完整；无映射历史批次与业务摘要保持不变；损坏绑定阻断使用，不静默修复。
- 部署前先备份，再受控重启本机服务；实际4010只读核对acme原6批/0工单及imports/business摘要，不创建假企业数据。保留production门禁。
