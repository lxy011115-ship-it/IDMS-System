# 认证数据库程序权限矩阵扩展

这是完整方案A的每角色职责核对步骤，不另建范围。新增认证组件先在自有隔离数据库验证所有角色的有效权限，再接入完整原SOURCE/HELD。

固定可信策略来自实际`auth-store-schema.ts`权限定义及原认证审计安装器，不接受调用方权限描述来批准SQL。会话应用只拥有原三张会话表的既定权限，备份只读；认证审计应用与投递者分别拥有各自实际函数入口。所有其他注册角色在这两个schema上的表、序列、函数及授权选项均须逐对象比较。元数据中的owner/app/delivery与实际SOURCE职责、配置身份必须一致。每列不得出现额外显式授权。实际owner全局函数默认授权必须去除PUBLIC执行；其他相关显式默认授权拒绝，不授未来对象创建或迁移权。

实际组件已覆盖正确安装、应用/投递职责互换、跨用途函数执行、函数授权选项、缺必需入口、备份读取审计原表、外来角色读取会话、TRUNCATE/DELETE/列级写入、额外schema使用或创建、序列推进、未来默认授权和对象owner变化。原数据库防写守卫已阻止直接修改审计元数据，测试应证明原值不变，不能关闭守卫以制造通过。

完整接入时，在原核心认证SQL的同一个ORIGINAL-profile事务内，保留原逐行解密与完整SQL facts比较，追加本组件实际权限检查。新认证证据保留原V1摘要，独立检查器应分别重建实际权限和原证据绑定。不得增加普通角色连接、执行业务函数、COMMIT、延长原30秒或改变正在运行的Native9输入。

当前23项实际SQL组件及6项纯策略回归、旧两分支29角色SOURCE的纯描述绑定不等于新的完整材料验证。下一次完整任务应合并剩余工作流、公共维护schema及退休owner/migrator等矩阵缺口后验证，避免逐小项反复运行全套。最终仍须同案例独立核验、精确Linux验证和同版发布。
