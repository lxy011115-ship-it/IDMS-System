# 平台依赖控制器实施顺序

1. 从现有实际生命周期接口导出严格的核心依赖清单校验，固定 PG/身份/工作流/应用类型和回环端点映射；与凭据分开记录公开错误。保留原受管文件，不改失败案例。
2. 实现先返回句柄的控制器，绑定实际创建/就绪、启动取消、故障撤入口和逆序正常关闭；私密持久事件只记录实际事实，不从 PID 重建所有权。
3. 建立隔离组合验证准备过程：生成新数据库/角色和两租户资料，完成身份权威及恢复准入，全部正常关闭，作为新控制器显式离线输入。生产模块不能导入此准备夹具。
4. 真实运行核心组合，验证 OIDC 与业务状态保留、正常排空、启动取消、重复请求、依赖异常和未排空阻止 PG 停止。取得 Windows/Linux 原生及独立清理证据后再公开相应结论。
5. 完成 broker/边缘/预测/AI 与模型服务按启用配置的实际登记和正常关闭，补旧 owner 受控移交，再推进全系统故障/密钥/容量/灾备与现场、商业验收；最终制作同一版本的中文图文和演示视频。

当前已实现清单预检、应用组适配层和核心控制器 API。清单 5 项检查、适配层 3 项检查通过；核心控制器通过创建服务前取消和私密配置图错误脱敏的检查。核心控制器的实际 PG/身份/工作流/应用共同启停尚未完成原生验证，不能因 API 已存在或零服务取消测试通过便视为整套运行验收。

清单根字段固定为 `format:1`、`purpose:PLATFORM_DEPENDENCIES_V1`、`workDirectory`、`postgres`、`identity`、`workflows` 和 `applicationManifestFile`。PG 账户字段沿用正式模块；identity 声明 `postgresId`，workflow 声明 `postgresIds`。JDK 用 `javaHome` 显式指定，生命周期工具由控制器固定构建，不接受调用方提供任意程序。工作流 `cancelFile`/`reservationFile` 用显式 null 表示未启用。详细字段以纯校验器为准。文件检查仅固定工作流配置和应用清单摘要；实际工具/目录/SQL/身份权威检查仍由后续生命周期与应用入口完成，不能把预检当成就绪证明。

应用组适配层 `scripts/application-lifecycle-v1.mjs` 的 Windows 完整原生案例 `696583d04c18` 实际通过 27 项检查，其中新增完整九组件 READY、两租户 HTTP 上下文、重复停止一致性、正常退出及部分启动取消。独立核验实际通过：三个 PG 干净离线、四个工作流正常停机/20 池关闭/JDBC 归零、39 个应用成员和19个根 Node 退役，860 个执行输入及原607受管文件保持。此为公共批准模板、显式后台会话验证，不冒充浏览器或原私有数据的整站切换；新控制器 API 未被该案例调用。
