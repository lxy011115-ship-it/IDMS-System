# 当前部署正式准入审查：新用途、启动程序和 MQTT 应用 ACL

前置里程碑：Native13 的58项完整 Windows 原生检查及同案例独立核验已通过。实际两企业、7库、29角色及全部原权限/进程证据保留；四流中两条真空、两条 pending，真实身份三类轮换、旧历史材料、两份 SOURCE 与原 HELD 均已消费。它仍是只读恢复审查，不授予正式启动、MQTT 应用 ACL、业务写入或最终准入。

## 现有边界

- `cold-review-plan-journal-v1-request-file-v1.mjs` 严格使用 `RESTORE_ORIGINAL_SYSTEM_READ_ONLY_SUBMISSION`，旧批准不能用于正式启用。
- `cold-field-current-materials-v6.mjs` 的 MQTT 观察只完成 TLS，明确 `brokerTopicAclVerified=false`、`actualStartupProgramsApproved=false`。不能修改旧标志代替新证据。
- `mqttBrokerFilesV1` 生成固定的证书用户名、客户端标识和方向 ACL；`use_username_as_clientid true` 意味着随意换 MQTT 客户端标识不能避免顶掉同证书身份的正常连接。
- 原源码、案例、SOURCE、首次 review 意图/结果、计划与批准日志保持。任何新动作必须有新版本、新用途绑定和自己的原进程/会话证据。

## 一、先建立新用途的可信上下文

在原控制库和 identity authority 锁内增加独立的当前部署审查意图/日志。新用途引用原可信 SOURCE 与 fullFacts，重新核对完整当前目标、7库事实、两完整根、角色与 HBA、当前身份及工作流。使用新的 intent/recovery 绑定、凭据、原持有者和短窗口，不能借已关闭或过期的旧 HELD 能力，不能改旧 review 的时间或首次结果。

新请求只接受固定用途、稳定操作 ID、预期来源/计划摘要和用户当前认证意图；配置由可信构造侧固定。拒绝调用者提供 SOURCE 正文、任意路径、actor/approved 布尔值、任意 SQL/命令、授权回调或已拼好的材料结论。不同用途的会话能力、签名域、日志及批准必须互相拒绝。

先实现用途/能力/持久边界及拒绝旧用途的合同，再接网络动作。原 source/intent、完整贡献者沿革和旧批准继续可认证；旧批准不计入新正式用途。

## 二、绑定实际启动程序

从可信固定部署配置及原 SOURCE 图生成完整程序清单，涵盖该次真实使用的程序、入口、依赖和配置摘要；不接受调用者给出的已批准标志。将实际文件身份/字节、受控启动参数和原拥有进程链绑定到新审查意图。

新审查要区分受控诊断启动与正式业务启动。诊断所需的 broker/只读工具须得到新用途允许的明确程序授权，原业务仍保持 CLOSED。实际启动、READY、输入保持和正常退休必须由原 ChildProcess/生命周期能力证明；读取磁盘摘要或观察一个 PID 不代表程序已批准且实际运行。

## 三、在独立受控 broker 上检查应用 ACL

先证明原管理器、边缘端及 broker 的真实正常停止，并取得维护锁下的新受控 broker 所有权。使用原 SOURCE 固定的配置、证书、客户端标识、主题和已批准程序；broker 独占监听失败或无法确认旧正常客户端退休时拒绝继续。不得在旧只读 TLS 观察器中加入 MQTT CONNECT，也不得通过正常客户端标识去试探一个仍运行的业务 broker。

使用新的受控客户端原句柄检查真实 CONNACK、SUBACK、QoS1 PUBACK、关联投递及拒绝结果。覆盖 EDGE 只写 telemetry/只读 ack、PLATFORM 相反方向、跨企业/边缘、错误方向、通配符不得越权接收及不合法证书身份。具体返回码和通配符订阅行为须按实际 broker 版本及官方合同验证，不能把客户端自身拒绝当作服务器 ACL 证据。

探测消息使用新的无业务含义随机值，受控 broker 上不启动普通 intake 或边缘运行器；不重放原 pending，不伪造 STORED/ACK，不产生业务 SQL 写入。固定所有消息与结果的关联、实际 TLS 身份、broker 原所有权和程序清单摘要，分别记录允许、拒绝和未观察到的结果。任何不确定结果均不授予 ACL 通过。全部会话须按原拥有链正常关闭。

## 四、独立批准、候选和最终启用另行完成

将新用途、当前完整材料、实际程序授权和 ACL 证据绑定到新的计划与持久候选。按企业以当前真实用户明确批准，排除完整实际贡献者沿革中的全部作者；旧只读用途批准、仅历史身份及观察到有效令牌都不代表本用途的批准意图。

最终多库准入必须再次核对当前权限、准确计划/全部批准、完整事实及所有原资源，保持原观察窗口。需要唯一审计、真实最终 SQL 提交、实际 COMMIT 回复未知后的同 ID 恢复及随后正常业务。候选、诊断成功和批准记录都不自动开启 ACTIVE。HTTP/UI 的用户会话、CSRF、确切摘要展示与显式确认也在最终范围内。

## 验证顺序与交付

1. 新用途/会话能力/签名日志合同及旧用途拒绝；保留全部原 SOURCE/意图/日志的不可变性。
2. 新程序清单与原拥有启动/退出，随后在固定 broker 上实际运行允许和越权拒绝案例。
3. 在新的完整来源案例中接原两企业/7库/29角色、四流、原 HELD、所有 SQL/身份/工作流和进程检查；原30秒观察时限保持。
4. 同案例独立核验从原字节、当前根、实际包/结果、拥有链和程序摘要重建结论；不重放业务或代填批准。
5. 再接新用途计划、全部独立批准、候选和最终事务/真实 COMMIT 未知及后续业务；Windows 和确切 Git 版本 Linux 通过后发布。
