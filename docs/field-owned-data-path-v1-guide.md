# 边缘进程与真实事务数据链路

本阶段延续平台依赖计划第 5 步与现场边缘生命周期实施计划。新增循环 V3 和进程适配器 V2，旧循环、适配器及既有验证入口保持原字节。V3 在空闲采集间隔保留仍有效的 MQTT 连接，在续租或失效时等待正常关闭；实际业务确认和当前租约共同决定就绪状态。

## 实际验证路径

`scripts/verify-field-owned-data-path-v1.mjs` 只接受明确的 PostgreSQL 和 broker 工具目录，在 D 盘工作目录创建全新隔离集群、两企业数据库和独立角色。它用固定摘要的公开父版本清单核对原 864 份受管文件，不读取原 `.local/postgres-runtime.json` 或接触原 45432 实例。

独立 worker 使用现有生产 `FieldPlatformService` 与 `FieldIntakeService`，真实只读 OPC UA 服务、自有 mTLS broker 和实际边缘子进程。租约签发、当前核对、事务接收、回执去重及签名业务确认均由生产模块完成；测试只控制可见的网络响应、确认丢失和提交前等待点。两名不同审批人的公开 QA 模板作为隔离数据种子，不冒称本阶段重新验证了 OIDC 登录或真实人工 UI 审批。

检查覆盖：

- 实际提交和签名 STORED 确认后就绪，空闲期间持续可探测。
- 原生读取被持有时，子进程确认停机后取消读取，数据库和队列序列保持不变。
- 数据已 COMMIT 但业务确认丢失时，正常停机保留准确的待确认事件；PUBACK 不清队列。
- 重启补传复用原事务回执，不重复写入测点。
- SQL 提交前被持有时，接收/签发关闭尚不能完成；自有 QA PostgreSQL 的正常停机守卫拒绝仍有客户连接的停止请求。取消后事务回滚，未确认事件仍保留。
- 边缘、接收、OPC UA、broker、worker、池和 PostgreSQL 依次实际退役，不使用通用强杀。

`scripts/verify-field-owned-data-cleanup-v1.mjs <nonce>` 独立读取实际退出记录、相关联停机意图及来源摘要，检查 broker 正常关闭、PostgreSQL 干净离线、SQLite 完整性和状态 MAC、待确认事件签名。它不会重新启动数据库或从历史 PID 重建所有权。

## 证明边界与后续工作

Windows 的原生结果及独立核验见对应 validation 摘要；Linux 必须以新工作流实际结果为准。首次 QA 健康客户端 ID 过短、Windows 工具路径别名及持有读取过早释放的三次失败均保留，生产校验未因此放宽。

本阶段证明新边缘适配器与实际签发/接收模块之间的数据路径。统一平台 descriptor 的启用配置、当前身份权威、登记后的依赖图、同请求故障恢复和平台控制器停机门禁仍须接入；QA 集群的连接守卫不等同于已经完成该控制器门禁。整站、原私密资料、现场与商业验收、云端新候选及最终图文视频交付仍需继续。
