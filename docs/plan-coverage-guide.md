## 使用流程

1. 先上传并独立批准设备台账和测点定义，声明 `expected_interval_seconds`。已有上传与更正流程不变。
2. 企业管理员进入“企业模板”，选择“新建运行日历”。修改模板编码、设备编码和实际计划；JSON 中保留 `purpose: operation-calendar`、设备只读和独立人工终审策略。
3. 填写日历展示时区、明确带偏移的起止时间和连续 `RUN`（运行）/`STOP`（停产）区间，每段填写依据。保存草稿后提交冻结，由另一位有设备范围权限的终审员发布。保存/提交均不代表发布。
4. 在“数据质量工作台”选择“计划采样覆盖”，再选择“批准上传”或“设备采集”，填写设备编码与时间窗口。来源或检查方式切换会清空旧筛选和结果。

每台设备只有一个日历编码族；同族新版本不能改绑设备。修改已提交/已发布内容时，复制为更高版本重新独立审批，新版替换当前发布版，旧内容与审计保留。可按原模板包导出/导入；导入目标企业必须有相应批准设备，且导入后仍为草稿。运行日历不继承其他模板，必须完整声明。

## 时间与分母

日历最多366天、512个连续无重叠区间，必须完整覆盖声明范围。没有默认工作周或“未填写就停产”。`timeZone` 是有效展示时区，例如 `Asia/Shanghai`；每个时间必须明确 `Z` 或 `+08:00` 等偏移，实际时间点以偏移为准，不猜测夏令时重复或不存在的本地钟点。显式格式仍使用明确ISO时间JSON；循环班次使用新增作者配置及冻结展开，见循环日历说明。

查询最多31天、左闭右开 `[from,to)`。每个RUN段按原起点和当前批准间隔固定分槽，交叠查询窗口的部分槽计一个；RUN末尾不足完整间隔也计一个，并显示部分槽数量。STOP和日历外样本不填计划槽，但实际记录数量保留。不同查询窗口的边界槽可能交叠，因此不能直接把各次覆盖率相加或平均。

例如：运行3分钟、停产4分钟、再运行3分钟，声明60秒间隔，完整窗口分母为6个计划槽。一个槽内多条记录仍只覆盖一个槽；BAD记录可以填“已记录槽”，不能填“GOOD有效槽”。采样缺口与计划覆盖是分别展示的指标，原质量发现不会因配置日历而被删除或改写。

只有查询窗口完全在日历声明范围内、存在当前批准定义和正整数间隔、且计划槽大于零时，才输出完整覆盖百分比。缺少条件显示 `UNKNOWN`；全窗口声明STOP且定义/间隔齐全时显示 `NOT_APPLICABLE`，百分比为 `null`，不显示100%。计划内无数据且具备完整条件时，覆盖率为0%。

## 统计含义与来源

- **记录覆盖**：有至少一条窗口内记录的计划槽数 / 计划槽数。
- **GOOD有效覆盖**：槽内至少一条GOOD记录满足非空有限值、当前批准单位和物理录入范围；采集还须符合当前点表、映射、节点、来源及持久接收回执字段绑定。它不是设备健康、报警阈值、模型精度或质量放行结论。
- **重复记录**：计划槽内记录数减去已记录槽数。同一槽的好记录可以覆盖该槽，同时坏记录仍留在原质量视图中。
- **计划槽外记录**：未落入可建立计划槽的记录，包含停产、日历外，以及因间隔/日历缺失而无法分槽的记录；未知条件下不能把它直接解释为违规采集。

响应包含日历编码、版本、内容摘要、独立治理事件和声明范围，测点定义包含批准批次、原行和记录版本。历史窗口使用**当前**批准定义和当前发布日历重新评估，不是历史当时配置的重放，也不是已冻结报告。需要业务保留历史结论时，应保存当次响应及相应版本依据；完整历史配置重放仍待开发。

设备范围基于真实OIDC身份和当前批准台账。日历创建/编辑/提交/审批、列表、导出及幂等回执重放前均检查当前设备范围；不存在与不可见设备返回同样的空结果。原客户数据不自动补日历或定义，未配置时显示未知。

## API与执行边界

```text
GET /api/v1/data-management/coverage?deviceCode=DEV-01&from=...&to=...
GET /api/v1/telemetry/coverage?deviceCode=DEV-01&edgeId=...&tagCode=...&from=...&to=...
```

`deviceCode` 必填；可选 `tagCode/from/to/page/pageSize`，采集另支持 `edgeId`。不接受 `status`、租户覆盖、未知/重复参数，page最多1000000、pageSize最多100。时间默认最近24小时，截止最多超前5分钟。URL中 `+08:00` 的加号应编码为 `%2B`。

上传沿已验证只读业务工作区，使用有效批准记录及其更正，并验证完整审计后选取日历治理依据；因此完整上传工作区和大审计的既有资源边界仍存在。采集采用独立只读REPEATABLE READ：先验证完整业务canonical根，再读取当前批准定义、日历及治理事件，SQL对全窗口聚合，只传区间和结果，不生成数百万条预期槽或拉取全量遥测。沿用队列、任务预算和数据库超时，无新增DDL、依赖或默认额度提高。

遥测不在业务canonical根内；同快照和持久接收字段绑定不等于逐条重验历史HMAC或不可变归档。当前采集覆盖仅针对当前点表，点表外历史标签与源级拒收继续在“记录质量”中单列。SQL/来源/统计校验失败返回安全503，不返回部分覆盖率；身份/来源切换、迟到结果、取消和失败清除旧结果。
