## 固定依赖与顺序

`scripts/platform-dependency-controller-v6.mjs` 导出 `createPlatformDependenciesV6(config, {startupSignal})`，使用 `scripts/platform-dependency-config-v2.mjs` 的严格配置校验。

配置格式为 `format: 2`、`purpose: PLATFORM_DEPENDENCIES_V2`，其余根字段固定为 `workDirectory`、`postgres`、`identity`、`workflows`、`predictor`、`applicationManifestFile`。数据库、身份和工作流字段沿用原 V1 校验；不接受任意入口、命令、环境或外部 PID。

预测声明固定包含 `id`、`runtimeFile`、`workDirectory`、`port`。`runtimeFile` 使用既有 `PREDICTOR_SERVICE` 格式，绑定回环地址、实际端口及服务令牌。预测 ID 不能复用其他依赖或保留的 `applications` ID，端口不能与 SQL、身份、身份管理或工作流端口冲突，记录和运行文件不能放入 PGDATA 或包含 PGDATA。

当前应用清单按租户包含 PREDICTIVE 工作者，所以规则预测服务是必需依赖。创建任何服务前，预检读取每个实际预测工作者的包装文件和基础配置，核对类型、租户、`baseUrl` 与 `serviceToken`；必须和预测服务声明完全一致。预检不改写客户端地址、密码或历史配置。

| 阶段 | 顺序 |
| --- | --- |
| 启动 | 所有声明的 PG → 身份服务 → 工作流 → 规则预测服务 → 应用组 |
| 正常关闭 | 应用组 → 规则预测服务 → 工作流 → 身份服务 → PG 逆序 |

应用组内部继续使用现有九成员的实际创建、就绪、入口撤销和排空协议。预测服务使用既有 V1 生命周期适配器创建的实际 fork 句柄，绑定后才启动监听，停止时等待已接受请求和根进程、管道及 IPC 的真实终态。

## 调用方应保留的状态

创建函数返回控制器 API；调用方应在服务创建前保留它，并观察 `ready`、`status()`、`resources()` 和 `closed`。`ready` 失败不会免除资源退役义务；控制器会启动关闭流程，调用方仍需观察结果。

`close({requestId})` 只接受固定 UUID 请求，不接受 PID 或命令。首次停止选定编号后，重复调用必须保持同一编号；正在进行的停止共享同一个 Promise。实际完成的结果可以重复读取。

| 结果 | 含义与处理 |
| --- | --- |
| `CLOSED` | 本次创建的资源均已取得正常退役证明，且控制器没有记录异常。 |
| `BLOCKED` | 某个资源的停止预检或退役证明尚未满足；更早的依赖不会继续关闭。保留实际控制器 API 和原请求编号，查明并纠正被拒绝的输入或连接条件，再用同一编号重试。 |
| `FAILED` | 已证明本次资源全部退役，但启动、运行或关闭期间发生异常。不能当作平台正常停机或业务验收成功。 |

`closed` 只有在本次全部资源已证明退役时才完成；观察超时本身不能证明进程已退出。不要根据历史 PID 重建所有权，也不要通过启动另一个控制器覆盖仍存活的句柄。

已绑定的预测服务在应用组排空后才停止。若在预测进程创建后、绑定前取消，控制器可直接请求其正常退出，不需要为了关闭而启动监听。依赖意外退出会触发应用入口撤销；即使外部测试通过该依赖的正式 API 正常关闭了它，对仍期望它运行的平台控制器而言也属于异常，最终结果应记录 `FAILED`。
