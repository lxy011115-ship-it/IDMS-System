# 现场恢复：活跃事务与协议故障验证进度

本阶段继续完整方案A第6项，补充正式restore-target的数据事务故障证据。生产恢复代码沿用上一阶段版本；测试通过独立自有QA库、真实归档和正式CLI执行，不开放激活入口。

四个场景分别验证直属工具中断、独立持有的遗留工具，以及数据段和最终核验段的真实COMMIT完成消息丢失。

COPY中断先观察同一会话返回非零行数的服务端COPY完成消息，再截住下一COPY的CopyInResponse；从真实pg_stat_activity及pg_stat_progress_copy确认事务ID和active/ClientRead。这样能够证明被中断事务已有实际完成但未提交的数据，不依赖小批量COPY尚未刷新的当前表进度计数。

直属子进程场景记录本机实际观察到的原生进程状态。独立持有场景由监督者直接启动固定PG16真实psql，逻辑控制器仅通过IPC等待实际close；控制器被终止后，必须确认该psql及两个代理socket仍存活，再由下一正式恢复命令退休。该场景不冒称psql的物理父进程属于被终止控制器。

重试在重新APPLY前，独立只读核对旧COPY后端已不存在、34个物理表全部为空；数据SQL只生成一次，未提交段复用相同计划、参数、全部输入字节数与SHA。随后完整恢复35个关系的事实，并验证旧审计、业务、原件、点和回执保持、两迁移表受控重绑定、唯一目标核验审计及一次根revision增量。

COMMIT故障直接在协议层丢弃真实服务端CommandComplete(COMMIT)，不是在应用回调中模拟抛错。数据段要求psql实际非零退出，协调器按已提交库内阶段继续且data只APPLY一次。最终核验段要求原CLI连接失败、结果文件缺失而数据库已VERIFIED；下一正式CLI完整重验后补写同一结果，重复执行不再改写根、审计或序列。

代理绑定loopback、QA目标库、角色及application_name，有界解析；不记录认证、COPY或SQL协议正文。所有自有控制进程、代理socket、实际原生工具、匹配数据库后端确认终态后才清理目标和私密目录。原系统、未知进程和历史快照不接管。

依据：[PG16消息格式](https://www.postgresql.org/docs/16/protocol-message-formats.html)。文档说明协议含义；实际通过状态、进程终态和全量事实由本阶段验证JSON证明。

完成这些恢复侧故障门槛仍不等于第6项或商业验收完成。源pg_dump导出中途故障、FIELD关闭且业务停写的维护实例、当前OIDC/工作流现态与独立恢复终审、新注册、证据冻结与离线CLI全链，以及原核心受控部署继续。大库容量、跨宿主和Linux写后端也不由本阶段替代。

本阶段最终验证：四个真实场景全部完成并重复完整恢复；485项核心测试、230构件/脚本及类型检查通过；13生产恢复/工具文件与上一阶段公开SHA逐字一致。原运行、原角色、66契约及十轮双份历史快照重新核对。直属进程的实际观测状态与监督者独立持有的遗留状态分开报告；独立持有场景中的原生工具实际close已等待。公开进度与JSON两处逐字一致，仍为RESTORING、未部署/激活/商业验收。
