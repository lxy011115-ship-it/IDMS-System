# 恢复后的真实浏览器业务验证

本入口在独立创建的业务 PostgreSQL、外置 Keycloak 和物理恢复目标上执行。沿用后台恢复的前 20 项，再启动三个沙箱后台进程，用真实浏览器登录完成第 21 项。它不会接管原站或启用公网。

## 已验证结果

2026-10-23 的 Windows 个案 `bb2e7b60dfd0` 通过 21 项，清理错误为零。429 个执行来源（含 70 个页面资源）在开始与结束时保持相同。原先 537 个公开受管文件和原 314 个受控恢复来源未改。

真实 Keycloak 表单完成 S256 PKCE 登录。操作员保存治理模板草稿；分析员评估批准测点；另一位操作员独立复核并创建维修工单。分析员依次领取、开始、提交维修和复测证据，操作员独立终审关闭。工单依次为 ASSIGNED v2、IN_PROGRESS v3、AWAITING_APPROVAL v4、CLOSED v5，每一步流程均为 SYNCED。维修提交人与最终审核人不同。

关联证明要求实际回调会话、带 CSRF 的页面 POST 202、同命令 GET COMMITTED，以及真实工单状态与版本。后端测试会话没有代替这些页面动作。五项 API 负例单独使用明确标记的后端会话，不能当作 GUI 权限验证。当前预测是工程规则评估，不能解释成已验证的机器学习诊断或剩余寿命预测。

三类账号均完成业务读取；操作员可读对账工作区，分析员与只读账号的对账上下文实际为 403。实际会话刷新与四个工作区共享退出通过。首次操作员检查因尚未访问首页而失败；访问首页后再检查通过，失败记录保留。

正常清理后，独立只读检查确认 17 个自有 Node 子进程退役、4 个流程 JVM 正常停止、20 个连接池完成关闭且 JDBC 客户端归零；3 个 PostgreSQL 目录干净离线，7 个目标业务数据库及身份数据库目录移除。冻结源及归档保留。已在完成清理后请求关闭测试标签；随后发现残留错误标签，访问被浏览器协议策略拒绝，未确认其关闭。进程与数据库正常清理由独立检查证明。

## 运行方式

使用 `scripts/verify-runtime-cold-browser-positive-v1.mjs`，参数与既有后台恢复入口相同。需要独立 PostgreSQL 工具、JDK 21、Maven、Keycloak、已核验的公开批准模板来源和工作目录。运行会创建私密凭据与隔离数据库；不要提交 `work/` 或用原站目录代替。

前 20 项完成后打印 `CONTROLLED_COLD_BROWSER_READY`。只在该次打印的 origin 和 issuer 打开浏览器，用该次私密账号文件进行真实登录。标准输入可发送以下命令：

```
CHECK operator
CHECK analyst
CHECK reader
CHECK refresh
CHECK_WRITES
API_NEGATIVES
CHECK logout
COMPLETE
```

每类账号须访问首页上下文及治理、维修、预测页面，并访问对账页面确认允许或拒绝。写入证明还要求上述完整正向链。退出检查前应正常退出，再访问四个工作区确认未登录。`COMPLETE` 只有所有必需检查均通过才能完成；等待最终报告和父进程正常退出后，再运行：

```
node scripts/verify-runtime-cold-browser-positive-cleanup-v1.mjs <本次12位nonce>
```

文件命令模式须显式设置 `IDMS_CONTROLLED_COLD_BROWSER_FILE_COMMANDS=1`，并严格按 ready 文件的 owner 和递增 sequence 提交，不得覆盖已存在命令或结果。持有时间有限；中止使用 `ABORT` 并等待 finally 清理，不要通过关闭仍活动的标签或强杀进程跳过收尾。
