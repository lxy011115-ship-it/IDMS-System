# 批内输入与有效行的双流冷证明

原4010已完成受控升级及验证，实现标记为`coldInputProof=dual-stream-input-proof-v1`，并保留此前全部健康标记。启动和独立SQL/分页/CSV的冷证明不再构造整批rows/validRows数组；原完整canonical根、所有原件/审计/回执/批准事实、冻结输入SHA、治理与更正链仍须全部通过。schema、迁移checksum、默认容量及完整写事务保持。本阶段属于完整方案A的开发进展，生产验收仍关闭。

## 两条流和原摘要

每批先读取真实BatchMetadata及输入/选中行总数，检查全部物理行号。按选中数预留每项48字节后才分配manifest：32字节canonical行SHA256、8字节原SQL ordinal和8字节原输入位置，零ordinal标记尚未填入。

rows按原SQL ordinal递增流出，允许合法间隙及int64排序。每行同时重放原根与原冻结输入公式，并为选中行登记manifest；范围、重号、数量、企业/批次身份及对象形状必须通过。快照字段工厂与完整写入口共用，保留原canonical的undefined语义和Unicode转义。原件仍以49152字节分片校验总长、偏移和SHA；沿原canonical字段顺序重放，因此原件可能先于输入失败被读取，失败不会产出证明。

validRows从同一关系第二次读取，按有效ordinal连续1..N流出，逐行核对原SQL ordinal和SHA，确保同一输入被精确覆盖；原输入位置用于更正的同序等价规则。普通批次保留有效行选择和合法重排语义，不将更正要求强加给普通导入。规范化行、有效顺序和全局输入计数缺漏、重放、外来或替换均失败关闭。

更正期待按原输入逐行登记，仍保留冻结baseRows真实元数据，检查提交数、原行号、validRows与全部输入同序等价。随后完整事实/typed SQL和版本流核对实际前记录、前值、连续版本、设备编码和本批新值。即使重算全根、审计及输入SHA，伪造前记录也不能通过。

## 真实消费者与生命周期

共享治理入口接受明确metadata和已完成的FrozenInputEvidence。完整旧API由真实BatchBody适配，保留原校验条件、原件校验和惰性摘要。没有空数组填充的假BatchBody。

明确完整只读消费者才收集同两条流中的真实对象，两个数组来自独立行对象，完整证明通过后冻结返回；不在证明后重读另一份未绑定对象。完整GET、温缓存重建、维护和命令模型契约保持，容量仍按原规则计量。

manifest、瞬时行、完整收集对象、来源元数据及更正期待均有预算租用。有效行错误会排空已发出的PG语句；取消、SQL错误、预算拒绝、根后更正失败和成功都释放临时资源，不缓存失败或部分证明。完整证明后才允许读取结果。
