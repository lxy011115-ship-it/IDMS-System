# 原平台整库备份与隔离恢复（2026-11-05）

结论：原本机 PostgreSQL 16.10 集群已完成一次在线物理备份、原生文件/WAL 校验、以16.15在D盘独立目录实际恢复，以及整库加密冷备的再次还原。14个可连接非模板库的349张用户表逐行摘要一致。原C盘实例没有换版或停机；这项证据仍不等于整个平台灾备完成。

## 备份范围和来源

只读盘点发现，原集群除当前绑定的两个企业业务库、两个独立Flowable库、身份库和应用会话库，还存在七个历史控制或测试库。它们没有因名称而被删除。集群目录共16个数据库条目，包含两个模板库和`postgres`维护库。

使用已经认证的16.15客户端，通过原有SCRAM认证和复制协议执行`pg_basebackup`，未增加角色权限、修改HBA或创建持久复制槽。备份采用分散检查点、8 MB/s数据传输限速、SHA-256文件清单和流式WAL；临时复制槽实际释放。限速针对数据目录传输，流式WAL不受该参数限速。备份协议会产生检查点和备份相关WAL，不能称为对源实例完全没有内部写入。

原生`pg_verifybackup`成功验证7,008个清单文件及时间线1的WAL区间`10/51000028`至`10/5109CF70`。其本身不能替代实际恢复，因此继续执行了下述原生启动和SQL核对。工具原理及边界参见[PostgreSQL在线物理备份](https://www.postgresql.org/docs/16/app-pgbasebackup.html)和[备份校验](https://www.postgresql.org/docs/16/app-pgverifybackup.html)。

本次数据对应备份恢复点，原系统的后台采集恢复继续运行，后续审计会增长；没有把恢复点与原平台的后续状态混为一谈。

## 两次实际恢复

第一次从已验证的在线备份复制到独占新建的D盘目录。逐文件摘要先确认副本一致，再仅替换该副本的启动配置：独立回环端口、显式数据/配置/HBA路径、禁用复制及归档命令、禁用预加载库和后台工作进程、默认只读事务。原配置另行保留。没有在副本启动主站、身份、工作流、模型或采集应用。

16.15原生服务实际重放备份WAL，日志确认达到一致恢复状态。通过PID出生时间、可执行文件摘要、目录设备/文件ID、SQL报告路径/端口/版本及集群系统ID绑定该实例。物理克隆的系统ID与源实例相同，所以系统ID本身不能证明可以操作或删除该目录。

随后正常smart停库，使用既有AES-GCM整库冷备工具生成加密档案。完整认证及逐文件校验后，还原到第二个全新目录，以同一套16.15程序再次启动，并从新连接重新计算全部SQL事实。

保留的整库档案为469,651,743字节，包含7,029个文件和39个子目录。它是16.15实际恢复并正常停库后的加密恢复点，配置为上述隔离配置，要求保留已绑定的16.15程序。它不是原在线基础备份的逐字节副本，也不是可直接替换生产目录的部署包。

加密档案、独立密钥、原配置副本、在线备份清单及label、完整SQL摘要、原生恢复日志和进程/退出收据均保留本机私密目录。企业数据和密钥不上传GitHub。通过独立复核后，仅回收本次三个D盘明文中间目录，共21,068个文件、1,386,839,087逻辑字节；原C盘数据目录及历史库没有被清理。

## 观察失败及同操作续办

只读盘点最初假定集群仅有六个当前绑定库，实际发现七个额外库后中止；修正为保留并盘点所有可连接库，没有删除未知库。在线备份的首次预检查还因旧的合成集群冷备配置白名单不接受原生默认配置而拒绝，当时尚未派发备份。后续仅记录原配置摘要，在线备份不执行该配置；隔离启动使用独立配置，未放宽应用冷备规则。

首次原生恢复成功，但观察器将`inet`类型文本`127.0.0.1/32`与裸地址比较而中断。原启动助手已成功退出，副本仍在运行。保留失败脚本及收据后，使用`host(inet_server_addr())`取得地址，并以原启动意图、助手终态、目录身份、PID出生时间及SQL身份重新绑定同一个进程；没有再次启动、重新初始化或替换原备份。后续完整核对、两次正常退出和加密档案还原均成功。

## 尚未覆盖的交付门槛

本次补上原平台全部数据库的物理备份及隔离还原证据，范围明显超过此前的两个企业业务档案。仍未覆盖边缘SQLite缓存、AI网关回执、模型/运行配置和密钥的一致恢复点，也未验证恢复后的登录、会话撤销、工作流/AI外部效果关联与重复请求。不能据此承诺生产RPO/RTO或无损跨服务回退。

原Java进程的`jcmd help`实际没有`VM.exit`命令。仓库内的新生命周期控制器有专属启动条件，原平台当前启动方式未满足；本轮没有注入停机代理、启用管理端点或对原进程发停机信号。正式迁移仍须解决真实服务排空与正常停止、同版全平台隔离恢复、企业岗位签收、支持与备份政策，以及生产部署和域名HTTPS。详见[当前验收清单](prelaunch-acceptance-status-2026-11-05.md)。
