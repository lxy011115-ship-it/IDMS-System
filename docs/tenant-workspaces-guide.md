## 工作方式

PostgreSQL 模式下，读写回调显式接收 `{store, imports}` 企业工作区。启动时加载的聚合对象冻结后仅供服务配置、历史绑定和企业入口检查，后续业务不从该对象取最新数据。HTTP、上传/审批、权限与幂等、Flowable、AI、采集均使用当前回调工作区。

一次写入先取得目标企业数据库 `business_state` 独占锁，再读取最新完整状态；只克隆该企业形成命令工作区。成功后同企业边界检查、完整领域/原文件/审计校验和原子持久化仍执行。失败直接丢弃该工作区，避免用全企业回滚副本覆盖别的请求。回调返回值另行复制，调用者不能用返回引用改动下一次请求的数据。独立人工终审、预期版本与摘要、租约提交栅栏都保留。

进程内调度按根 Store 和企业键隔离。同企业读写仍排队，跨核心依靠数据库锁排序；不同企业可以在另一企业等待外部服务或 SQL 时继续。嵌套等待同企业命令会明确失败，避免自等待。任务失败不阻断后续队列，空闲企业键及时释放；关闭时等待已入队任务。

普通 GET 使用通过 MVCC 完整性证明的冻结企业工作区。缓存按根 Store/企业隔离，业务写入开始与结束仅使目标企业缓存失效；数组、嵌套对象和幂等 Map 的标准写方法均拒绝修改。新 SQL 数据中心/CSV 仍在独立一致快照中查询。存储故障、指纹变化、停用企业不允许返回旧缓存或执行新命令。

这里没有更换数据库布局：迁移版本仍为 4、实体布局 3、兼容 payload 2、认证库 schema 1，既有迁移校验和不变。file Demo 继续原快照事务。原文件、输入、追加事实、更正账本、审计和回执保护保持。

## 证据与复现

```powershell
npm test
npm run build
npm run workspaces:verify
npm run multi:verify
npm run workers:verify
npm run reads:verify
```

116 项单元测试、65 项运行文件及全部脚本/TypeScript 构建通过。工作区专项使用两个隔离企业库、两个测试进程、100 台设备、20,000 条测点记录和约 22 MB 原文件；原 JSON 包含合法空白填充，用于观察重复复制成本，不是大文件 HTTP 上传验收。

在 A 的真实数据库事务内暂停后，B 可以提交，A 的后续同企业命令仍等待。另一核心实际等待企业数据库锁后读取最新状态。异常回滚、跨企业实体污染拒绝、嵌套事务拒绝、停用企业锁后复核、只读 Map、返回引用隔离、12 路相同幂等请求只追加一次审计均检查。原冻结批次、迁移记录和原企业业务摘要保持。

性能参考冻结了改动前的写入协调和 PostgreSQL 仓储代码，运行在隔离 QA IPC 进程。每企业只测 3 次命令，先旧参考、后新实现；审计随命令正常增长。JSON SQL 字节是返回行编码量，克隆原文件字符数是 `structuredClone` 输入中的 Base64 字符累计量，均不是实际网络协议字节或分配内存。堆高水位是采样，maxRSS 包括该进程启动后的整个生命周期；不能据此制定生产 SLA。

精确数字见 `outputs/tenant-workspace-verification.json`。该证据区分两点：小企业写入不再复制另一企业的大文件；大企业自身仍完整读取/重建/校验目标状态。不能用前者的数据宣称后者或冷启动已解决。真实 OIDC、跨核心写竞争、更正、类型、质量、共享会话、Flowable/AI 接管、采集和导出另由相应回归证明。

## 平台升级

健康接口使用 `commandWorkspaces=explicit-tenant-workspace-v1` 识别本批运行时，后台任务标记仍为 `leased-fenced-outbox-v1`。本批没有 DDL 迁移；原平台升级需先业务加密备份/隔离恢复，再核对拥有的核心和启动器父链，受控重启并检查升级前同一 SID/CSRF、原查询结果和业务摘要。升级证据为 `outputs/live-workspace-upgrade-verification.json` 与 `outputs/workspace-upgrade-*-verification.json`，两份均已通过。原acme仍6批0工单、业务/导入摘要不变，升级后29表业务备份及隔离恢复通过；认证库/key仍不在该业务备份范围。

## 继续完成的工作
