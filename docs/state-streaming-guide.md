## 实际改动

领域读取改为一个 `UNION ALL` SQL statement，逐行传递状态、实体、批次、输入、文件、事实、审计、回执和工单镜像。它们来自同一个 MVCC 快照，保留既有 READ COMMITTED 锁后读取和 RR 读事务语义。Node 按关系类型和权威 ordinal 重建数组，不依赖 UNION 的返回顺序；原文件 Base64 单独作为文本列读取，避免嵌入整份聚合 JSON。

`runtime_state` 仍是原只读兼容视图，定义和历史迁移校验和保持。新读取与旧视图逐字段、原始文件、数组顺序及旧 payload_digest 对照。rows 与 validRows 的对象各自独立，保持旧 JSON 视图解析后的别名语义。跨企业行、文件/输入孤儿、批次保留字段、SQL 审计列和工单镜像不一致会拒绝读取。

SHA-256 改为分块输出原 canonical 字节流；对象键顺序、JSON 转义、Unicode 代理对、数值和历史 undefined 语义不变。JSON 数据比较直接检查结构和值，wire 规范化不再生成一份总量字符串。原文件 SHA-256、类型/映射冻结、审计、事实、更正和保存后 SQL 精确重建校验继续执行。未变化批次在 splitBatch 之前跳过，避免重复解码附件与匹配输入行。

`pg.Query` 保留标准回调、语句超时与客户端查询超时。逐行消费时清空其公开结果 rows 数组，驱动最多保留一条额外结果行；业务仍会保存重建所需的全部目标对象。行校验失败先记下错误并排空本次查询，再拒绝；不会从 row 事件抛成未捕获异常。真实语句超时、后端连接中断及行校验失败后的恢复已验证。

## 本机样本

隔离数据为 100 台设备、20,000 条测点、22,170,784 字节原文件。原 JSON 含合法空白填充；不是大文件 HTTP 上传验收。每组 3 条命令，先冻结旧仓储路径、后新路径，数据库缓存已热。加载阶段是新 Node 进程的 loadImports，不包括整个多服务平台启动。

| 指标 | 原完整 JSON 路径 | 逐行重建/分块摘要 |
| --- | ---: | ---: |
| 大企业写入 p50 | 2925.51 ms | 1167.25 ms |
| 完整验证读取及摘要返回 p50 | 1144.10 ms | 605.57 ms |
| 新进程加载验证 | 1539.84 ms | 1107.01 ms |
| 写入阶段观察堆高水位 | 约 1271 MiB | 约 175 MiB |
| 该进程生命周期 maxRSS | 约 1555 MiB | 约 491 MiB |

堆值是离散观察，maxRSS 包含此前启动和命令阶段，不能解释为单条命令独占内存，也不能据此制定生产 SLA。SQL 行 JSON 编码总量在三次大企业写入中从约 254.2 MB 增至 268.9 MB，原因包含逐行元数据；本批不宣称 SQL 传输量减少。它也不是协议字节量。观测计数工具自身逐块计算长度，避免再次制造一份总量 JSON 字符串。

三次写入仍有六次完整目标状态读取，附件与审计仍保留在启动对象或活动工作区中。这里减少的是巨型中间字符串、额外结果数组和无变化批次的重复处理，没有把完整状态成本隐藏成“常量内存”。
