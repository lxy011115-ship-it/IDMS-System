## 完整证明与轻量重建

普通PG GET仍处于原RR + SHARE事务中，先核对整个依赖集合的行版本、关系/数据库代际、视图和历史迁移。首次、变化、重启或无法证明时，仍完整校验canonical payload、文件SHA、审计链、映射/设备类型/更正冻结、事实与typed投影。只有先前已经完整核对且当前指纹一致的快照才复用证明，不能只凭revision。

有证明但缓存已淘汰时，轻量SQL只读取业务、批次元数据、输入和事实；不读取文件、审计、请求/命令回执或工单冗余镜像正文。按ordinal恢复顺序，输入/有效输入保持独立对象。完整实体SQL与前一版本逐字节相同，黄金摘要对照见 `read-sql-compatibility-verification.json`。冷校验继续用原完整路径。

## 原文件和审计提供器

正文提供器绑定当次SQLclient、企业、批次对象及事务生命周期，缓存中没有client或提供器。请求结束后不能继续查询已释放连接；结束时等待已发起的读取排空，拒绝迟到结果。

原文件下载先走原有批次范围授权，再在同一RR快照取长度/SHA，预留响应额度和 `4 × 原始字节 + 64 KiB` 的任务计划额度，才SELECT该批次bytea。返回前再次核对长度、绑定和SHA；直接发送Buffer，不把Base64或Buffer回填缓存。4倍是驱动/缓冲处理的逻辑估算，仍不是物理内存硬限。额度不足在文件正文查询前拒绝。

`GET /audit`按需逐行读取审计，先核对SQL列/事件绑定及全企业审计链，再执行原有可见范围过滤。`SERVER_FULL_TENANT_CHAIN`、`chainValid`与`partialView`语义保持；没有用筛选后的局部链冒充完整校验。驱动额外结果数组最多1行，验证错误排空后拒绝，不返回部分审计。接口仍返回完整可见历史，HTTP分页/分段继续后续完成。

文件Demo通过原内存快照适配提供器，保持原规则；本批主要改造PG运行路径。
