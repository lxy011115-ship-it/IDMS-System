# 主站共享会话与PKCE联合恢复验证（2026-11-05）

结论：实际主站入口、现有Keycloak 26.8.1和原共享会话库已在隔离恢复副本完成联合验证。沿用原密钥、数据库部署摘要、来源地址、加密scope/AAD，没有初始化新会话库或重封已有记录。含活动会话及待完成PKCE请求的整库检查点真正加密、还原后，原Cookie/CSRF继续有效，令牌完成真实续期，待完成登录正常完成且禁止重放。原平台未换版，完整平台及生产恢复仍未验收。

## 实际流程

1. 从保留的既有身份整库检查点1c1852b7-dec5-402f-9187-248a82505304还原新PG16.15目录。它包含真实原集群副本及此前仅在副本创建的合成登录账号。原密钥环逐字复制并核对摘要，原会话库的key_check及部署摘要核对通过。
2. 新JDK21.0.13+9的私有Keycloak以固定existing-store/validate、禁止初始化和自动补索引的配置启动。实际server/index.ts使用原企业数据库身份和共享PostgreSQL加密会话校验，没有演示身份或内存会话回退。
3. 主站A发起S256登录，真实身份端点返回授权码后，A通过创建者IPC完成排空并实际exit0。主站B重新启动后完成相同回调，返回已验证身份和HttpOnly/SameSite Cookie；同一回调重放401。认证后的备件汇总和导入列表读取200。
4. 缺失/错误CSRF和错误Origin返回403，重复SID返回401；伪造企业头未改变登录身份。负例前后14库全部public表事实保持。另发起一个新PKCE请求，与已登录会话一起保留在同一原加密会话库。
5. 正常停止B、身份服务及PG后，捕获整个测试集群的加密检查点。完整认证和逐文件摘要通过后，实际还原到第二个全新目录，再启动新的身份服务和主站C。
6. C接受原opaque SID，CSRF与绝对到期时间保持。真实身份令牌续期后，会话密文修订从1变2，新访问令牌摘要及到期时间更新，绝对登录期限不被延长。恢复出的另一条PKCE请求也正常完成，重放401。
7. 两条会话以有效CSRF退出后从共享库删除，原Cookie再读会话为未登录、再读备件为401。成功用例3个主站、2个身份JVM及2个PG均正常收尾；未对目标发送强制终止。

## 隔离网络与首次失败

会话加密绑定包含原端口、身份issuer和站点origin。为保留这些绑定，本机QA使用有明确允许名单的传输入口：应用仍读取原逻辑地址，数据库构造仅将既定应用身份路由到已验证的自有PG；身份HTTP仅路由到自有Keycloak。主站、JWT、数据库权限及加密校验代码保持原样，所有传输见证保留。测试没有访问原4010/8081端点，也没有通过新的namespace绕开原密钥校验。

首个用例的Host预检失败后被错误启动，实测Node24 fetch会覆盖本次测试所需Host，应用因此返回自身登录入口，断言拒绝继续；它不是产品登录故障。首次收尾又发现两个停止记录名称碰撞，主站和JVM已正常退出，随后通过有原生身份校验的独立续办将自有PG smart停止。首个续办在读取不含process的终态对象时失败于任何SQL/native操作前，修正为读取原能力身份后完成。所有失败和停止见证均保留，未覆盖已执行脚本。

新版采用真实Node HTTP通道，先实测Host及多条Set-Cookie可保留，再在新目录运行上述完整成功用例。这是显式QA端口映射，不是生产网络、浏览器交互或跨主机灾备实演。

## 数据库核验范围

整库冷备认证覆盖全部物理文件。主用例在服务停止后冻结、并在还原后逐一比对14个库的317张public表。复核发现，备件另有32张表位于idms_spares，不能把317张的SQL比对说成全部用户schema比对。

为此，从新检查点再次新建隔离PG，独立读取全部349张用户表，执行两企业规范业务、完整审计链、原始资料和备件全量校验；317张public表仍与冻结点完全相同。额外32张备件表的完整行事实及连续锚与保留的早期原整库检查点相同，用户schema清单、全局角色、成员关系及数据库目录也保持。备件当前为空，这不证明大容量或企业UAT。这里不声称冻结前已对全部349张表做过SQL事实比对。
