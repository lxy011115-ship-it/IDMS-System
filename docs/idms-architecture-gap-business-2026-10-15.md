# IDMS 企业设备预测性维护与智能数据管理

## 整体架构、功能缺陷与盈利模式建议书

版本：评审稿 1.2｜日期：2026-10-15｜适用：多类型设备数据管理优先、SaaS 与企业私有化

本报告基于现有项目代码、开发状态文档及本地验证记录。它是产品设计与差距评估，不是生产安全审计、现场算法评测或商业报价。价格、周期和收益案例均为规划假设，需经客户访谈、实际成本和试点确认。1.2版依据用户明确选择“多类型设备，先做数据管理”，替代1.1版以单设备族预测为首发的建议，并同步SQL读模型与业务库恢复的最新范围。引用既有验证记录，不表示本轮重新执行全套测试。本轮仅重新检查4010健康接口，确认OIDC、企业独立PostgreSQL和typed-sql-read-model路径；不等于全部依赖、生产安全及现场能力验收。本次仅更新分析与设计文档，不修改业务代码、不启用未验收功能。

## 一、结论与产品边界

将 IDMS 定位为“多类型设备数据管理与维护决策平台”。首发收费产品是可追溯的数据管理基础版，预测性维护是建立在合格数据之上的分设备族升级能力，而不是上线前提。初期手动上传，保留统一API；不要求客户先安装传感器，也不承诺通用寿命预测。

核心价值分为三层：把设备数据管好，把风险提前发现，把维修行动和效果闭环。软件可销售的基础是标准化数据模型、可复用设备模板和可核算的客户收益；真正的竞争壁垒是经授权积累的设备故障样本、现场适配经验和维护效果证据，不是看板数量或接入了多少大模型。

首批试点选择一家愿意提供既有设备台账、巡检和维修表的企业，同时覆盖至少两种实际设备类型。泵组、空压机、机床、电机可用于说明模型差异，不代表已完成这些设备的现场接入。首期验收设备编码、字段、测点单位、数据质量和追溯；数量、批次和保留期按实际样表及容量验证冻结。以后再从客户已有数据中选出适合做条件监测的设备族，单独约定故障模式和算法验收。

### 三种路线与取舍

| 路线 | 优点 | 局限 | 建议 |
| --- | --- | --- | --- |
| 多设备数据管理基础版 | 手动上传即可启动；统一台账、测点、质量、版本和追溯，复制成本可控 | 不能因此承诺预测能力，需以治理与实施效率形成差异 | 当前首发主线 |
| 数据平台＋设备族健康分析＋维修闭环 | 在基础版上逐设备族增购，可逐步验证维护价值 | 需要测点、工况、专家和现场验证 | 第二阶段升级路线 |
| 全制造平台＋通用 AI＋所有协议同时覆盖 | 产品展示范围广 | 交付与验证成本高，容易变成客户定制项目 | 暂不作为首发目标 |

### 能力分级与销售边界

| 等级 | 对客户提供什么 | 所需数据 | 能否承诺寿命预测 |
| --- | --- | --- | --- |
| L1 数据管理 | 资产台账、上传校验、趋势与维护履历 | 设备编码、历史表单、维修记录 | 不能 |
| L2 状态监测 | 数据新鲜度、阈值、健康趋势、异常检测 | 稳定测点、采样、量纲、工况 | 不能 |
| L3 故障模式预警 | 对指定故障模式输出预警和证据 | 故障标签、工况覆盖、离线与现场验证 | 只承诺已验收模式和边界 |
| L4 剩余寿命评估 | 指定部件 RUL 区间、适用条件和不确定性 | 足够的寿命/退化样本、删失信息、验证模型 | 仅适用已验证设备族，不能通用保证 |

单纯有几个月历史数据或一个故障周期，并不能保证满足 L3/L4。没有足够故障标签时，可先采用工程规则、健康基线和无监督异常检测；不得将异常分数或大模型自报置信度包装为真实故障概率。

## 二、总体系统架构

建议采用“边缘只读接入＋模块化业务核心＋独立分析服务＋受控 AI 助手＋统一治理”。SaaS 与私有化共享代码、接口、模板包与数据库迁移。

首期实际使用路径是“企业文件/JSON → 批次接入 → 字段标准化 → 校验/人工复核 → 独立终审 → 数据中心”。边缘采集、预测引擎和AI网关均是可替换附加服务，缺少它们不应阻断合规的手动数据管理；AI不可用时明确转人工，不显示自动审核通过。

```text
设备、传感器 / Excel、CSV、JSON / ERP、MES、EAM
                         ↓
边缘只读网关与统一上传 API：身份、缓存、补传、限流
                         ↓
数据治理：设备/测点映射、单位、时间、质量、去重、来源冻结
                         ↓
业务数据库 / 时序与特征库 / 原文件与波形对象存储
                         ↓
工程规则与预测服务 ← 工况、标签与模型注册 → AI/RAG 助手
                         ↓
告警聚合 → Flowable 工单 → 维修/复测 → 独立人工终审
                         ↓
故障标签、维护效果、ROI 与模型反馈

贯穿全链路：租户隔离、身份/数据权限、审计血缘、模板版本、运维
```

### 2.0 多设备共性与差异分层

共性核心管理企业、组织位置、资产身份、文件批次、审批、权限与审计；设备类型模板只声明扩展字段、测点、枚举和约束。企业覆盖项保存差异，设备实例填写参数与测点定义。已发布版本固定绑定历史，不能修改类型模板后重解释旧数据。当前只实现部分设备属性、每设备测点字典及维修字段模板，完整继承机制仍是目标设计。

同名测点不必同义：泵组的出口压力MPa和空压机的压力bar不能直接汇总。后续应增加量纲、安装位置、标定与工况定义，单位转换保存原值、转换规则和版本；当前只验证单位一致，不进行自动转换。温度、压力、累计运行小时等也不能套用统一振动阈值。质量GOOD表示数据可用，不表示设备健康。

界面以设备档案、接入批次、测点字典、数据查询、质量问题、维修履历和追溯为工作入口；健康与预测保留独立入口，并明确适用设备、样本条件与不可评估原因。数据管理不应强制运行预测，也不应把没有历史测点的资产标成健康或在线。

### 2.1 业务与服务边界

| 模块 | 核心职责 | 输出与边界 |
| --- | --- | --- |
| 资产与测点中心 | 企业/工厂/产线/设备/部件/测点；设备族与关键度 | 稳定资产 ID、测点字典、设备模板；设备编码变更不丢历史 |
| 统一数据接入 | 文件/JSON 批次、MQTT 遥测、连接器 | 暂存与接收回执；不直接触发关单或设备控制 |
| 数据治理 | 完整性、范围、单位、时钟、质量标志、重复/乱序/迟到 | 质量报告、隔离区、可批准批次、可信分析窗口 |
| 特征与健康分析 | 工况分组、基线、统计/频域特征、规则与模型推理 | 特征快照、健康等级、有效期、异常证据；坏数据不能产生健康结论 |
| 故障与维护策略 | FMEA、故障模式、告警合并、持续阈值、抑制、维护建议 | 风险事件、优先级、建议窗口；风险不等于已确认故障 |
| 维修与点检 | 计划、派工、任务、原因措施、备件、复测与验收 | 可执行工单、维修事实、终审记录、标签候选 |
| 工作流 | AI 中间节点、人工队列、超时升级、补偿 | 明确状态机；业务状态须与引擎回执确认 |
| AI 与知识中心 | 文档提取、设备资料检索、诊断说明、工单草拟与材料审阅 | 结构化建议与出处；不决定物理寿命、不执行最终责任动作 |
| 模板与集成 | 设备族模板、客户差异、版本、插件和外部 API | 配置交付；不使用客户专属源码分支 |
| 商业与运营 | 企业开通、模块授权、配额、计量、许可证、客户健康 | SaaS 控制面与私有化离线授权；不读取无授权客户业务数据 |

生产、质量、能耗可作为设备风险的上下文；首发不做完整订单排产、财务、采购或全功能 QMS，优先对接客户已有系统。

### 2.2 推荐工具及引入顺序

| 层 | 工具建议 | 当前与演进策略 |
| --- | --- | --- |
| Web 与移动端 | Vue 3、TypeScript、Element Plus、ECharts；响应式/PWA | 当前活跃页面是 public/manual.js；逐步统一组件，不将旧 Vue 示例当作已上线功能 |
| 业务核心 | 现有 Node.js/TypeScript 模块化核心 | 先强化领域边界、事务和持久化；Java 21/Spring Boot 为既定目标技术，按团队需要逐模块迁移，不把整体重写作为商用前提 |
| 流程服务 | Java 21、Spring Boot、Flowable | 已有维修流程集成，继续扩展 SLA/升级与其他审批 |
| 分析服务 | 现有独立预测进程；后续 Python、NumPy、SciPy、scikit-learn、MLflow | 先规则和基线，再按设备族引入算法；训练和在线推理解耦 |
| 数据库 | PostgreSQL、TimescaleDB | 独立企业业务库；时序表按企业和容量设计，不用业务 JSON 快照承载海量测点 |
| 文件与检索 | S3 兼容存储/MinIO、PostgreSQL 全文检索和 pgvector | 原文件与波形独立存储；数据量达到需要后再引入 OpenSearch |
| 接入与消息 | MQTT，Mosquitto 或 EMQX；OPC UA；后续 Modbus/S7 | 初期复用现有本机集成；是否选商业版及许可证需评估 |
| 异步任务 | PostgreSQL 任务表＋事务 outbox | 达到吞吐或解耦需求后再引入 Kafka/Redpanda，避免初期基础设施过重 |
| AI 网关 | 本地或云模型的可替换适配器、结构校验、权限过滤 RAG | 保留本地模型能力；小模型质量与部署成本必须实测，不能等同工业诊断模型 |
| 身份与运维 | Keycloak、OpenTelemetry、Prometheus、Grafana；按需 Redis | 生产 TLS/MFA、共享会话、日志脱敏、密钥保管、备份恢复必须补齐 |
| 交付 | Compose 试点；规模化再评估 Kubernetes | 同一安装和升级路径，发布前完成依赖许可证/SBOM/安全审查 |

所有开源组件、模型权重及嵌入式商业分发方式均应核查具体版本许可证；不能笼统认为“开源即可无条件打包销售”。

### 2.3 SaaS 与私有化部署

SaaS 控制面保存租户路由、套餐、许可证、计量与平台版本，不保存设备业务明细。数据面每企业独立业务数据库、独立数据库账号和流程数据边界；时序、对象存储、知识索引、缓存和队列也必须具备服务端强制隔离。用户不能通过请求参数选择其他企业数据库。

私有化部署相同服务，但单企业路由；支持离线许可证、离线升级包、备份/恢复和本地模型。集团内多个工厂通常属于同一企业租户，再用工厂/产线/设备数据范围控制访问，不能把 SaaS 租户隔离与集团组织管理混为一谈。

OT 现场网络与 IT 应用网络分区，边缘节点优先只向平台发起受控出站连接；独立设备证书、精确 MQTT ACL、TLS/mTLS、证书轮换与吊销。首版不提供 PLC 写入或启停控制。未来控制功能须单独立项，不能仅加一个 AI 工具接口。

## 三、数据架构与追溯设计

### 3.1 标准数据模型

| 数据域 | 建议实体 | 关键字段/约束 |
| --- | --- | --- |
| 资产 | asset、component、measurement_point、operating_mode | tenant/site/asset ID、设备族、部件位置、量纲、采样策略、有效版本 |
| 接入 | import_batch、source_file、ingestion_event、validation_error | 原文件摘要、来源身份、行号/事件 ID、源时间/接收时间、映射版本、幂等键 |
| 时序 | measurement、waveform_reference、feature_snapshot | value/unit/quality、event_time、sequence、工况、标定/算法版本、原始证据引用 |
| 健康 | health_snapshot、risk_event、alarm_episode | 有效窗口、数据覆盖率、规则/模型版本、证据摘要、失效时间、合并状态 |
| 维护 | maintenance_plan、work_order、repair_action、verification | 原因、措施、工时、备件、维修人、复测证据和独立审批 |
| 标签 | failure_label、label_review、maintenance_outcome | 部件/故障模式、确认依据、发生区间、是否误报、删失情况和评审版本 |
| 治理 | model_version、template_release、plugin_package、audit_event | 制品/数据摘要、发布审批、版本依赖、签名与审计血缘 |

核心关系：企业 → 工厂 → 产线 → 设备 → 部件 → 测点 → 原始记录/特征 → 风险事件 → 工单 → 维修/复测 → 独立审批 → 故障标签。所有关系使用不可变内部 ID，业务编码可版本化。

### 3.2 质量与更正原则

1. 保留原值、标准化值、单位转换、来源时间与接收时间，不能静默改写原始数字。
2. 重复事件幂等去重；同 ID 不同内容隔离为冲突；迟到数据采用事件时间和有界重算，不改写已签发判断的输入。
3. 数据缺失、过期、坏质量、时钟漂移或工况未知显示“不可评估”，不能沿用旧结果显示健康。
4. 人工上传业务批次须独立人工批准后才进入正式分析；可信设备遥测经机器质量门入库，无须每条人工审批，但关键维护动作仍需终审。
5. 更正创建新记录版本，引用旧版本并触发受影响指标重算；原文件、原审批和历史判断保留。
6. 模板、知识、规则、模型与特征版本固定绑定；新版本不追改历史工单。只回放有授权、可获得的真实输入。

### 3.3 容量与存储分工

标量遥测进入 TimescaleDB，业务和审批进入 PostgreSQL，原文件/照片/波形进入对象存储，特征表保留原始波形引用；知识向量只存授权文档片段与出处。

容量示例：100 台设备 × 每台 10 个标量测点 × 1 Hz = 每日 8,640 万点。若每点按 100 字节作估算，则原始逻辑量约 8.64 GB/日，尚未计索引、副本、WAL、备份与压缩。该数字是容量推演，不是实测吞吐。

振动波形不能等同标量。三轴、25.6 kHz、每样本每轴 4 字节，连续采集约 26.54 GB/台/日，尚未计格式开销。因此建议边缘提取 RMS、峭度、频带能量等特征，定时短片段与异常触发片段上传原始波形。实际采样率、抗混叠、传感器安装和分析特征须由设备专家确定。

保留策略先按客户合同确定，再做压测：近期特征供快速查询，历史按小时/日聚合，原始波形分级归档。不能随意删除将来复核所需证据；审计保留与业务删除要求需单独制定政策。

### 3.4 审计边界

每次操作记录企业、对象、操作者、时间、输入摘要、规则/模型/知识/模板版本、前后版本、关联 ID、审批与接口结果。高频数据以接收批次摘要、清单和 Merkle 根等方式按需证明完整性，避免每个采样值复制进业务审计。

哈希链只能发现部分篡改；应用管理员、数据库超级用户、归档保管者必须职责分离，使用独立权限、外部时间/摘要锚点和不可变归档。当前应用签名记录也不自动等同法律意义上的第三方电子签章。

### 3.5 首发数据管理闭环与验收

首发最小闭环为：组织与资产编码确认 → 设备台账批准 → 测点字典批准 → 选择标准模板或已发布映射 → 上传预览与逐行校验 → 独立人工终审 → 查询/导出与原文件追溯。没有自定义测点需求时，设备台账和维修履历仍可独立使用；不能为了通过验收补造测点、故障或预测结果。

数据管理应分批完成企业表头映射、版本化更正、数据质量工作台、受权限约束的导出及细粒度数据范围。更正不等于普通编辑：需新批次引用旧记录版本，冻结差异和旧摘要、独立审批、同事务追加及按当前有效版本重算；保留原始文件和所有旧结果。完整更正流程尚未实现，当前相同业务ID不同内容仍拒绝覆盖。

试点验收必须包括两种设备自定义字段/测点并存、不同单位不混用、未批准数据不进入统计、未知设备/测点逐行报错、重复与冲突处理、自审与跨企业阻断、映射升级不改历史、任意查询结果定位至原批次/行号/审批人。前述未来能力未落地前逐项标记未通过；不得用本机小样本测试代替生产性能或客户验收。配置化80%、实施4–8周均为待验证目标，不是现有承诺。

## 四、预测算法与 AI 工作流

### 4.1 双引擎分工

工程/预测引擎负责时序窗口、信号特征、阈值、健康评分、异常检测及经验证的故障/RUL 模型。大模型负责读取授权设备资料、解释已有证据、草拟措施、审阅材料和检索相似案例。大模型不能编造传感器值、故障标签、诊断概率或寿命结论。

冷启动顺序：厂商/专家规则 → 按设备与工况的基线 → 无监督异常检测 → 指定故障分类 → 有条件的 RUL。不同故障模式可停留在不同等级，不要求所有设备都上深度学习。

模型发布流程：冻结数据集与标签 → 按设备和时间隔离训练/验证/测试 → 与规则基线比较 → 专家复核 → 影子运行 → 小范围启用 → 漂移/误报监控 → 人工批准回滚。不能随机拆分相邻重叠时间窗后声称泛化，也不能将维修人填写的“可能故障”自动当作真标签。

### 4.2 自动化与最终责任

目标链路：输入冻结 → 确定性校验 → 授权知识检索 → AI 结构化判断 → 独立结构/证据/策略校验 → 低风险中间节点自动流转 → 最终批准包 → 独立人工批准 → 执行动作与反馈。

只有经过流程级评测和授权的中间步骤才自动执行。AI 故障、提示注入、无证据、冲突、未校准低可靠输出或高风险时立即转人工，禁止默认为通过。应保留人工接管能力，而不是强求“除了最后一步，任何异常也必须由 AI 通过”。

最终关单、质量放行、知识/模板/模型/插件发布、关键外部回写、权限提升及数据删除必须人工批准；创建/提交/执行人不可自审，叠加角色也不能绕过。危险异常先通知、隔离或按既有安全规程处理，不应等待 AI 作答才发出报警。

批准包至少包含设备与部件、风险摘要、数据质量、原始证据链接、分析窗口、模型/规则版本、AI 审阅范围、建议、维修/复测结果和前后版本。审批过程不允许对变更后内容沿用旧签名。

### 4.3 预测价值如何验收

按“故障事件”而非单个采样点计算精确率、召回率；故障观察不充分时明确漏报率未知。同步记录每设备每月误报次数、提前预警时间分布、有效预警比例、人工接管率、检测延迟和工况覆盖率。

合并同一次故障的重复报警，区分设备停机、计划维护和传感器故障。只有提前量足以安排维护的预警才有经营价值。RUL 还须披露误差、区间覆盖、适用工况和不可评估范围，不能只展示单一准确率。

所有阈值、容忍误报数和提前量需按设备风险与维修窗口在试点合同中冻结；稀有故障无法在短试点中充分验证时，只验收数据与闭环，不宣称已证明预测性能。

## 五、当前系统功能缺陷与风险优先级

### 5.1 已有基础与证据范围

项目已有七类 CSV/XLSX/JSON 上传（含测点定义）、多类型设备台账、自定义测点字典、独立批准、来源追溯、维修工单及工程规则分析；本机 PostgreSQL、Keycloak/OIDC、Flowable 和真实本地 AI 网关已有集成验证记录。数据中心已改为设备/测点/记录领域表与SQL分页；原业务快照仍负责审批与写入，不能声称全领域规范化。OPC UA→边缘缓存→MQTT→数据库链路验证的是模拟设备，不是客户真实产线。AI 网关为 SHADOW 且只处理有界抽样摘要，不能表示全量语义审核或生产自动中审已经验收。

当前运行日志显示本机平台及只读模拟采集已启动。运行日志或健康检查仅证明有限的运行状态，不能验证全部依赖、模型精度和故障恢复。较早开发状态文档中的模板/插件“仅元数据”描述已部分过时，以本节的范围和模板治理指南为准。

## 六、模板、插件与接口产品化

配置分四层：平台安全不变量 → 行业/设备族模板 → 企业覆盖项 → 工厂实例参数。企业覆盖项不能关闭独立终审、租户隔离、审计或只读采集约束。

模板内容包含资产/测点定义、单位/采样、工况、特征、阈值、故障模式、表单、维修 SOP、权限和看板。发布后内容不可变；修订形成新版本，经过兼容检查、差异预览、独立审批和灰度。历史记录绑定创建时版本；回滚默认影响新实例，已运行流程采取显式迁移而非静默替换。

插件必须声明版本、平台兼容、制品摘要、网络目标、数据权限、资源上限、签名密钥 ID 与依赖。平台维护信任库与吊销，认证员独立审批；使用受限进程/容器或可行的沙箱，不能把插件直接加载到拥有全部租户数据的核心进程。有效签名仅证明来源/完整性，不代表无漏洞或获得业务授权。

接口保留 /api/v1，覆盖资产、上传、遥测、健康、告警、工单、审批查询、报表和审计。Webhook 采用签名、重试与死信；外部写回通过审批授权的 outbox 执行。OAuth 服务身份只获必要查询/上传权限；最终人工批准不向机器身份开放。所有写入绑定租户、请求摘要、幂等键、关联 ID 和预期版本；客户端不能覆盖审批人与审计字段。

## 七、盈利模式与建议定价

### 7.1 核心收费模型

基础版优先采用“年度平台订阅＋资产规模档＋存储/保留期额度＋一次性数据实施”。资产档按受管理台账计，不把尚未监测的设备算成预测服务；包含合理协作用户数。升级到监测版后再按实际受监控关键设备与数据频率计费，AI采用含用量额度的可选包。不建议只按用户收费，也不建议只按原始测点收费。连接器、超额容量、额外保留、算力和现场服务单列报价及预警上限。

以下为人民币未税定价实验区间，不是市场调研结论或既有能力报价；硬件、税费、差旅、专线、算力及第三方授权另计。高级套餐只能在对应功能验收后销售。

| 产品/服务 | 建议实验价格 | 交付边界 |
| --- | --- | --- |
| 数据管理付费试点 | 1–3 万元/次 | 单工厂、多类型设备，约定样表、字段映射数量、数据量和独立审批/追溯验收；预计4–6周须经样表评估，不含预测精度与硬件承诺 |
| 数据管理基础版 | 2–5 万元/工厂/年 | 手动上传、资产/测点/维修履历、基础报表/追溯；按验收后的资产档、容量/保留、模板数与支持范围报价；未实现的映射/更正不得计作已交付 |
| 后续预测专项 PoC | 3–8 万元/次 | 单工厂、单设备族、10–30 台、约 6–10 周；观察期可能延长，数据不足不承诺预测验收，可约定转年费抵扣 |
| 健康监测专业版 | 8–20 万元/工厂/年 | 例如 50 台关键设备的监测/告警/维修闭环；约定采样、有效测点、数据量和连接器范围；不含未验收 RUL |
| 集团企业版 | 20–60 万元/年起 | 按工厂/关键资产规模、接口、数据保留与 SLA 评估；跨工厂与高级治理按已交付范围授权 |
| 私有化 | 30–100 万元初始项目区间 | 拆分软件许可、部署实施、适配及模型；年维保可试行软件许可部分的 15%–20%，不按全部硬件金额计算 |
| 专项连接器/设备模型 | 标准包或单独项目报价 | 限定协议、品牌、点表、故障模式、测试范围和维护责任 |

AI 建议采用含用量额度的业务分析包，并对超量费用预警，不以“无限 AI”获客。硬件/网关可与设备商合作采购或租赁，但须单列保修、返修与现场维护，不能让硬件售后吞噬软件毛利。

### 7.2 收入组合和单位经济

持续收入来自订阅、模型包、维保、托管监测和认证标准连接器；实施收费覆盖设备盘点、数据清洗、配置、培训与 UAT。伙伴分销佣金、设备专家费用和售后投入均计入实际客户成本。

基础版测算例（非实际业绩）：年订阅3万元、年度直接服务成本0.9万元时，经常性毛利2.1万元、毛利率70%；首次数据实施收费1.5万元、直接成本1.2万元，则首年收入4.5万元、毛利2.4万元、混合毛利率约53.3%。实施中逐列改表、无限清洗和无限客户定制会迅速侵蚀毛利，合同应限定样表与映射数量、清洗责任和变更费用。此处未扣研发、销售、管理及税费。

监测升级版测算例（非实际业绩）：单客户年订阅 12 万元，年度可归属交付成本 3.6 万元（云/算力、技术支持、伙伴分成等）时，订阅毛利 8.4 万元、毛利率 70%。若首次实施收 5 万元、实施成本 4 万元，首年总毛利为 9.4 万元，收入 17 万元，混合毛利率约 55.3%。仍未扣销售、研发、管理、税费，也不代表净利润。

若另假设获客成本 6 万元，以月度经常性毛利 0.7 万元计算，获客回收期约 8.6 个月；需用真实续约、收款周期、客户流失和实施超支替换假设。不能将首年项目收入全部计入 ARR。

### 7.3 客户 ROI 与效果分成

客户年度净收益 = 经确认的停机损失减少＋维修/巡检人工节省＋备件与质量收益－新增传感器/算力/实施/订阅/维护成本。停机单位损失尽量采用贡献毛利或经财务确认的损失口径，不能直接把产值当利润；产线瓶颈、设备利用率和补产能力会改变收益。

基础版先按数据整理、查找资料、报表核对和审计准备工时衡量，不把未验证的停机避免算进收益。例如每月经双方确认节省60小时，人工全成本100元/小时，则年价值7.2万元；假设首年订阅3万元、实施1.5万元及客户新增内部成本0.6万元，总成本5.1万元，净收益2.1万元、ROI约41.2%。若只是释放工时而未减少支出，应称“可用工时价值”，不宣称现金节省；需要客户基线和使用记录确认。

示例：客户确认可归因减少停机 40 小时/年，按 8,000 元/小时计为 32 万元；其他不重复收益 4 万元；软件年费 12 万元、初次实施 5 万元、硬件 6 万元、新增年度运营 1 万元。首年收益 36 万元、成本 24 万元、净收益 12 万元、ROI 50%。若缺乏可归因证据，此项收益应视为待验证，不能先计入销售承诺。

效果分成只作可选增值：双方预先约定基线、对照、停机归因、避免双重计算及第三方复核，确认后收取约定费用。不推荐仅靠效果分成承担所有客户的数据和不可控经营风险。

### 7.4 获客、续费与合同

首期从仍以Excel管理多类型设备、资料分散且有审计或维护履历需求的企业切入，可通过维修服务商、设备商、工业园区及实施伙伴获客。路径为“样表诊断 → 多设备数据付费试点 → 数据基础版年订阅 → 更多资产/工厂及接口 → 已验证设备族监测增购”。用受治理的字段映射和模板减少清洗与上线成本，不要求客户先买传感器或预测包。

基础版续费依据是台账覆盖、上传成功率、数据问题关闭、查找/报表工时、追溯可用性和运维可靠性；有监测增购后再增加有效预警、工单闭环、误报和维护效果报告。指标同时展示问题与未覆盖范围，不只展示绿色比例。

合同需明确数据归属、是否允许跨客户训练、知识与日志出域、模型责任边界、故障范围、SLA/恢复职责、费用超额、升级支持版本、退出时导出/删除与数据保留。未经明确授权，不汇总客户敏感故障数据训练共享模型；软件不替代客户安全联锁、法定检测和最终维护责任。

## 八、阶段实施与验收路径

以下为在现有基础上的规划顺序，不是承诺完成周期。工期需结合代码整改、真实设备可用性、故障观察周期和团队能力细化，阶段可部分并行，但验收门槛不能跳过。

| 阶段 | 参考窗口 | 重点交付 | 退出条件 |
| --- | --- | --- | --- |
| A 数据产品底座与商用阻断整改 | 4–6周起，评估后排期 | 映射、更正、数据质量、领域写入、对象存储；生产认证、数据范围、分权与跨服务恢复 | 数据功能分项验收，P0关闭；隔离/不可自审/恢复/升级及目标负载测试通过 |
| B 多设备数据付费试点 | 4–6周，取决于客户样表与清洗工作 | 至少两种实际设备类型、台账/测点/履历、上传接口、审批、查询与追溯 | 客户UAT；按约定数据量/覆盖/质量/工时价值验收，不要求出现故障或证明预测精度 |
| C 标准产品复制 | 6–10 周 | 设备类型模板与受治理映射、配置、接口、安装升级、许可证/计量、伙伴手册 | 第二家客户不改核心源码；升级不改历史；交付和成本可重复 |
| D 经验证的预测模型 | 数据门槛达到后持续迭代 | 模型注册、离线/影子/灰度、工况覆盖、漂移/回滚 | 对指定故障模式达成事件级指标；RUL 单独验收 |

参考配置为产品/设备专家、后端与数据开发、前端、测试/运维和现场实施共约 6–8 人，可兼岗但审批/安全复核保持独立。先解决现场数据与验证资源，再决定增加算法和基础设施人力。

### 验收底线

- 原始数据、特征、模型、建议、工单、维修与终审可串联追溯；重试不重复建单，迟到/坏数据不能伪造新健康结果。
- 人工/API 上传权限与设备范围生效；跨企业数据库、文件、索引、缓存、队列及日志均不能越权。
- AI 失效、提示注入、无证据和不符合结构的结果均转人工，不能绕过最终审批。
- 未通过信任、制品、扫描与隔离验证的插件不得运行；角色/模板变化不能关闭安全不变量。
- 对有明确负载条件的常用页面设 P95＜3 秒、关键告警处理链设 P95＜5 秒等目标；人工上传和离线设备不纳入实时保证。预测延迟另计采样窗口与分析周期。
- 建议 RPO 15 分钟、RTO 4 小时，须通过整套恢复演练证明；不是当前已实现 SLA。
- 预测评测按设备和事件隔离，公开故障样本量、工况覆盖、误报/漏报可测边界与不可评估情况。

### 下一轮需要企业准备的资料

首期必需：两种以上设备的现有台账与代表性Excel/CSV（可先脱敏）、字段解释/单位/时区、稳定来源记录ID、组织/设备编码、需保存的维修/巡检表、上传人和独立终审人、数据范围/保留期、样表清洗责任、验收负责人及目标容量。客户编码若含中文或空格，先建立标准编码对照，不能因为有表头映射就跳过编码校验。

后续按需：传感器/PLC型号和只读点表、采样频率/量纲/同步、工况、故障/备件标签、维护SOP及停机成本。以上不是初期数据管理试点的强制采购前提。

初期继续手动上传时，优先准备设备、维修、状态区间、测点的标准样表。只有汇总日报而没有测点或波形时，将首期范围限定为数据管理、维护分析与条件监测，避免以寿命预测签约。

## 九、决策建议

确定“多设备数据管理基础版”为首个可收费产品：统一台账与测点、企业样表接入、数据质量、版本更正、权限审批和可信追溯构成主价值；接口与行业模板为标准扩展，AI审阅/知识助手为有额度的可选增值。健康监测和真实故障模型按设备族完成验证后独立增购。

当前优先级是数据接入与质量、P0安全/持久化/恢复、真实多设备数据试点、模板复制及交付成本验证。下一批建议先做受独立发布治理的字段映射，随后版本化更正、数据权限和容量归档。将“减少手工整理与查找时间、设备资料可追溯”作为首期可验证收益；将“100%自动审核、全设备预测精度、绝对零故障”排除在承诺之外。本文是方向与评审规格，不代表这些缺口已实现；整体商用目标仍在进行。
