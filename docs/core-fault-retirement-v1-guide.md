# 核心故障退役与同请求重试

配置漂移会使服务退役停在 `BLOCKED`。修复原配置字节后，调用方应能立即使用原 `requestId` 重试，并等待本次实际创建的应用、JVM 和 PostgreSQL 全部退出。控制器 V5 在阻塞日志完成、旧关闭操作释放后才公布 `BLOCKED`，使状态与重试能力一致。

入口为 `scripts/platform-dependency-controller-v5.mjs` 的 `createPlatformDependenciesV5`。配置仍按 `platform-dependency-config-v1.mjs` 校验，先返回控制器句柄，再异步启动。`api.ready`、`api.status()`、`api.close({requestId})` 和 `api.closed` 分别提供就绪、当前状态、当前停止操作及最终退役结果。重试必须保留已选定的请求编号；已完成的组件不会再次发送停止操作。

应用适配层 V2 只接受其 WeakMap 留存的实际创建句柄。配置漂移导致应用自行退出时，原始未证实的终态记录保留；原字节恢复后另写退役重新核验记录，核对原根进程终态、登记所有者、哈希链和每个成员。故障资源全部退出后仍返回 `FAILED`，不能据此称正常服务关闭。工作流 V2 只释放尚未接受停止意图的失败预检，已经接受的操作保持原有幂等约束。

## 已验证范围

Windows 案例包含原 34 项核心/恢复/启动取消检查，并新增工作流配置漂移、应用清单漂移与恢复、工作流意外退出，共 37 项；36 项单位检查及独立清理均实际通过。配置漂移检查直接在观察到持久 `BLOCKED` 后恢复原字节并立即重试，没有通过等待旧操作结束来规避竞争。

新增三个故障案例实际创建并退役 15 个核心组件，含 27 个应用成员。独立审计区分正常与故意异常的应用退出，核对配置恢复、原句柄、同请求编号、入口撤销及 PostgreSQL 排空。实际数量、原生报告和独立清理摘要见 [Windows 验证记录](validation/core-fault-retirement-windows-v1.json)。

V10 的故障夹具假设错误和 V11 的真实关闭竞争失败保持为历史输入；当前入口使用 V12 原生验证、V13 独立检查器及 Windows V7 受限适配层。历史 V4 控制器供证据复核，当前故障路径使用 V5。
