# 写入后逐行一致性核对

更新：2026-10-16。继续完整方案A的大数据写路径与资源待办。业务迁移4、实体3、payload2和认证schema1保持，本批没有新增DDL或改变历史摘要。

## 已解决的具体问题

登录审计虽只追加一条事件，仍通过完整企业写事务。前批100设备、20,000测点、22,170,784字节原件、12,500附加审计的夹具，在默认512MiB任务预算下返回503/MEMORY_BUDGET，事务正确回滚。本批独立重现并测得：写后重建开始前已计费约385.4MiB，第二次完整重建继续累计，触及512MiB后拒绝。

现在写后使用同一条完整来源SQL逐行核对，不再组装第二个完整payload。相同诊断数据以默认容量完成真实Keycloak PKCE登录并创建共享会话，行回调采样任务峰值417,342,867字节；独立SQL兼容视图的完整canonical摘要与持久状态相同。默认上限保持536,870,912字节。资源权重是应用逻辑账本，采样不等于RSS、整个进程峰值或完整响应生命周期峰值。

独立原生业务/故障专项的登录和上传峰值采样分别为417,492,867及417,521,901字节，数据值和事件文案与诊断样本略有不同。两个专项都使用默认容量，不再需要前批审计分页专项的临时1GiB任务配置。

## 事务顺序

PG写入继续先获取企业business_state行锁，完整读取并验证旧payload，复制隔离Workspace，执行权限、领域、幂等和独立审批逻辑，规范化wire数据，再执行原writeEntities及typed/revision投影。

新增写后核对器读取与旧完整实体读取相同的UNION分支，只有查询标记不同。单个SQL语句提供一致快照。全部行核对成功后，仍用原canonicalDigest更新revision/payload_digest并提交。失败即回滚；登录审计写后失败不会创建SID。普通上传、审批、工作流和其他PG命令共用这一步。

首次完整读取、隔离工作区和wire规范化仍存在，SQL仍传输所有来源行与原件文本。此次减少写后数据图驻留，未宣称SQL总流量或全量验证CPU已消除。

## 每类来源的核对

| 来源 | 必须满足 |
| --- | --- |
| 状态头 | 唯一企业、schema3、原revision和原完整payload摘要保持，直到最终更新 |
| 业务实体 | 集合、ordinal、ID及完整body逐项相等 |
| 导入批次 | ordinal、批次ID及全部元数据相等，无正文伪装元数据 |
| 原始文件 | 批次绑定、SHA列与完整规范Base64相等；预期文件此前已校验SHA |
| 输入/有效输入 | 原行ordinal/body相等；validOrdinal唯一、完整覆盖并按有效行序逐项相等 |
| 批准事实 | ordinal、批次和全部来源字段/body相等 |
| 导入/命令回执 | ordinal、请求键和完整回执相等 |
| 审计 | 每个历史事件及hash/previousHash列相等，实际SQL序号与预期链严格同序，允许回滚留下的合法序号间隙 |
| 冗余工单 | 工单ID/body与规范业务实体逐项相等 |

不假设驱动返回行有序。覆盖位图拒绝缺行和重复，引用索引拒绝孤立/未知/跨企业或错ID数据。每条旧审计、旧文件和授权范围外的历史也参与，不能只核对本次新增内容。

预期wire payload已由原validateTenantPayload验证完整审计链、冻结模板映射/设备类型和原件SHA；SQL全量来源与该payload逐项相等，并保持审计实际顺序。因此既有完整性要求保留。历史canonical、完整实体SQL、兼容视图和迁移/认证结构字节未变。

## 内存和失败处理

核对器只新增引用索引、覆盖位图和审计int64顺序数组。索引按规模计算并在分配前预留；瞬时SQL行使用可归还租用，下一行到来时释放前一行。成功、验证失败、SQL错误或额度不足都会清理索引和行租用。驱动额外rows数组至多1行，发现错误后仍排空查询再归还连接。

索引随行数增长，文件正文仍是一条完整Base64行；新增保留量由索引和最大行决定，不是总内存恒定。更大的旧payload或单文件仍可能超过预算，此时继续拒绝并回滚。启动/旧数据全量验证、完整写工作区/wire副本、投影读取、同步CPU、输入事实分段和组件增量证明仍待后续推进。文件Demo仍采用原原子快照路径。
