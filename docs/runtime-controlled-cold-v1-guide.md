# 持久维护控制下的 R4 冷恢复

本层沿用已封存的活动 SQL 写入门与永久 ACL 退休源，在 PGDATA 外保存阶段、原清单、目录哈希、会话/租约期限及当前身份权威。它不以调用方提交的布尔值作为恢复准入证明，不按固定库数或角色数放行。原运行站点仍需正式接管与部署，不应直接对原 PGDATA 套用测试脚本。

## 阶段和接口

`createRuntimeColdControlV1` 要求既有多库维护操作已经 CLOSED。它实查全部活动门的原 operation/revision、原 catalog binding、退休源永久撤权、大对象权限、实际全库与角色清单，并核正常 JVM 停止回执和零剩余 SQL 客户端。控制文件必须位于 PGDATA 外。当前身份数据库必须独立于业务集群。

控制记录采用私有 SQLite WAL/FULL。信任描述固定 control ID 和源事实 SHA；控制维护账户和文件写入者受信任，不承诺抵抗恶意超级用户或整个控制目录与 trust 一起回滚。

| 阶段 | 行为 |
| --- | --- |
| PREPARED | 固定活动门、退休源、实际角色/数据库、会话/租约到期、验证器源码和 JVM 回执 |
| SQL_FROZEN | 所有登记角色 NOLOGIN/连接限额0，登记数据库连接限额0，实际其他 SQL 客户端为0 |
| CAPTURED | 源 PostgreSQL 正常关闭后，完整 PGDATA 加密封装；镜像关联同一控制 ID、源事实 SHA 和维护操作 |
| RESTORED | 完整认证与文件校验后恢复到新目录；不自动开放或启动应用 |
| ADMITTING | 在当前身份权威互斥下验证期限、源离线、目标/原目录/冻结权限，并开放门与轮换密码 |
| ADMITTED | 原目录与权限核对通过，固定本代运行配置和身份权威，才允许新应用入口 READY |

`RuntimeColdControlV1.freeze()` 幂等核验角色冻结结果；`capture()` 可识别同控制操作已发布的认证镜像，不能覆盖不同镜像。`restore()` 只恢复新目录，不覆盖既有目录。恢复中断留下的部分目录需进一步恢复审计，本层不会自动删除或猜测成功。

## 真实期限

控制器使用原共享认证存储的密钥见证解密全部 SESSION，核加密行绑定、会话寿命和 JWT exp 一致，固定 JWT 最晚到期。读取被当前运行版本使用的验证器源码，固定 `clockTolerance` 与源码 SHA，并将宽限加入等待期限。不能只等待数据库中会话记录的八小时寿命，也不能靠备份恰好耗时较久来替代期限检查。

实际登记库的 `lease_until` 列提供租约最晚到期。准入同时检查这些实际表中没有 `lease_until > clock_timestamp()` 的租约，避免仅凭控制端时间判断数据库租约。会话与登录请求的 lookup hash 进入本代关闭清单；不把恢复出来的旧 Cookie、旧 PKCE 回调或旧租约当作新授权。

## 准入与凭据

源目录必须保持正常关闭，源控制块与捕获时一致。目标必须是本操作恢复的新目录、原 system ID 和 OID、原结构及冻结权限；恢复后不建立新的目录基线。

开放 SQL 门期间仍保持角色 NOLOGIN。所有原 LOGIN 角色使用新随机数据库密码，角色与数据库连接权限在同一 PostgreSQL 事务中恢复到原值。密码不会写入公共 manifest；私有凭据文件属于可信维护侧。角色 OID、表所有权、权限、业务密钥、job key、逻辑服务绑定和原数据保持。

新配置生成器复制私有 JSON 引用图，只改变对应 SQL 密码，保持同一认证文件的共享路径，处理单个 `*File` 和数组 `*Files` 引用。原配置字节不修改。工作流重新创建 SQL/reader/admin 句柄，使用新配置启动新的受管 JVM，不复用已经 end 的 pg.Client。

这些接口的重复准入检查在应用启动前验证；运行中重新准入、完整控制器故障矩阵及跨主机互斥仍需继续。SQL 密码轮换不等于所有 HTTP 服务令牌都已轮换，后者与既有业务绑定的迁移仍需单独处理。

## 应用入口

新的站点和对账 worker CLI 接受受控运行配置，读取 PGDATA 外 ADMITTED 记录和原维护操作，并验证当前签名身份权威。新维护操作或权威变化会拒绝旧入口继续放行。入口没有 SQL bootstrap 密码或身份数据库维护密码。

恢复前 SESSION 一律不能授权 API；URL 编码或重复 Cookie 不能绕过。页面及明确的新登录入口仍可使用，旧 Cookie 被丢弃；捕获前的登录 state 不能重新消费。新登录的 Cookie 和当前权限可正常使用。此规则避免用户因旧 Cookie 留在浏览器而无法重新登录。

已恢复的 RUNNING 任务需要实际租约到期，并按原队列协议重新检查授权。旧会话关闭后任务等待新明确授权；不要删除旧任务、重建原指纹或自动把原人的授权重新解释为当前授权。

## 验证和未完成范围

`node scripts/verify-runtime-controlled-cold-r4-v1.mjs` 创建全新的业务、身份集群及真实 R4/Keycloak/Flowable 服务，执行真实整簇捕获/恢复、期限/当前权威、密码与配置代际、旧会话/登录/租约拒绝和新明确授权提交。

`node scripts/verify-runtime-controlled-cold-cleanup-v1.mjs <nonce>` 只读核验源/目标/身份 PG 已关闭、正常 JVM 退出、目标测试库目录移除以及清理回执。源冻结数据、加密镜像和私密证据离线保留；不能宣称这些副本已全部删除。

原站 owner 的可信移交、全部后台与入口的生产登记、捕获/恢复中断的完整矩阵、所有服务凭据、HA/PITR、Linux/云部署和浏览器完整验收仍继续。此技术指南不代替最终中文图文用户手册或演示视频。
