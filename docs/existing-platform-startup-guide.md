# 已有平台普通启动

适用：已经完成初始化、保留原配置及数据的Windows本地平台。日常启动只运行已有部署；首次安装、数据库迁移和生产服务监督仍是独立维护工作。

## 日常使用

在项目根目录双击“启动IDMS本地网站.cmd”或“启动IDMS.cmd”，也可运行：

```powershell
npm run platform:start
```

两个当前CMD、npm以及`scripts/start-platform.mjs`、v4兼容入口使用同一个协调器。v2/v3为明确标记的历史初始化材料，不是当前启动入口。

看到`STARTED`后打开 http://127.0.0.1:4010/?view=overview ，从“使用企业账号登录”进入已有身份服务。启动器不保存或输出登录密码，不恢复被撤销的角色，不修复停用账号。

`STARTED`表示各服务契约确认，并不代表整体就绪或生产放行。`/api/v1/ready`还会检查采集缓存、样本及所有必需依赖。2026-10-31本机恢复时HTML、身份及受限详情可用，9项前端资源逐字节一致，但已有模拟采集缓存10000条、确认0条，整体返回503 `TELEMETRY_BUFFER_FULL`；缓存被保留，没有清空或扩大容量掩盖问题。

## 一次性登记已有部署

登记引用现有原生程序、同一物理PGDATA、私密配置、共享会话密钥、工作流JAR、模型清单及显式就绪策略，不复制口令或模型，不连接空白部署。

先通过显式构建准备支持普通模式的工作流JAR：

```powershell
npm run workflow:build:existing
```

该命令使用已安装的JDK21/Maven3.9.11及本机缓存，显式离线构建，并记录源码和JAR摘要。它不连接数据库。旧JAR、构建后修改的源码或不匹配收据会使登记失败。

选择并核对就绪策略，先只读预检：

```powershell
npm run platform:adopt -- --readiness .local/runtime-readiness.json
```

输出`READ_ONLY_PROPOSAL`后，显式创建一个不存在的新登记文件：

```powershell
npm run platform:adopt -- --readiness .local/runtime-readiness.json --write
```

成功为`EXISTING_PLATFORM_REGISTERED`。默认两个历史运行路径若是同一物理数据目录，会合并识别；发现两套不同数据时拒绝自动选择，需通过`--runtime-root`指定已核对目标。不搬移、复制或初始化PGDATA。

登记文件位于`.local/existing-platform.json`，包含私密路径及部署摘要，应保留在本机。`--write`不覆盖已有登记。升级JAR或配置导致`BOUND_INPUT_CHANGED`时需要管理员核对后明确更新运行绑定，不能删掉检查或自动采用当前文件；本版没有自动重新登记命令。

## 普通启动具体保证

- 全部有界配置、端点、企业/身份/密钥用途、现有SQLite结构、构建收据及文件摘要先通过静态预检，再启动首个服务；缺失时不补建配置或秘密。
- 不执行bootstrap、initdb、迁移、GRANT、会话setup、MQTT密码/ACL生成、workflow/AI setup、下载模型或构建JAR。
- PG使用原工具及原数据；Windows通过`pg_ctl`保留厂商的受限令牌启动行为。陈旧PID由厂商正常启动判断；不删除锁、不resetwal。
- 身份启动前在只读事务核对既有realm、版本、表/约束/索引及237项变更记录的内容摘要；再运行固定26.8.1的optimized、validate、禁空库初始化及禁自动补索引模式，无启动失败后自动重建或重启。仅厂商禁初始化参数仍可能创建Liquibase记账表，因此前置只读拒绝不可省略。
- 工作流默认`runtime`：验证既有扩展表、Flowable7.2.0结构、企业、流程key/版本及BPMN完整字节；不CREATE或部署新定义。`IDMS_WORKFLOW_STARTUP_MODE=initialize`仅为显式初始化维护模式，普通协调器清除继承覆盖并固定为runtime。
- AI及边缘服务在普通模式只打开已有SQLite库并核对结构与来源；不自动建表。正常会话、回执、采集消息、缓存和WAL恢复等运行写入仍可能发生。
- 主站MQTT订阅确认后才启动/复用模拟源和采集边缘；不清空缓存，不向现场设备写数据。

## 分阶段记录与异常

私密`.local/platform-startup/runs/<run-id>/`保留阶段、PID/出生/可执行绑定、运行源码摘要、复用标志、退出观察及前后结构/权限摘要；`latest.json`定位最近一次运行。重复正常启动会复用已绑定且契约匹配的服务，不启动第二套。仅端口可达不足以证明身份。运行源码已变化时拒绝复用原Node服务，需在明确正常停机/升级流程处理；不会把磁盘新代码当作原进程已加载的新版本。

| 状态/代码 | 含义及处理 |
| --- | --- |
| `PREFLIGHT_REFUSED` | 静态输入未通过，启动数为0；核对现有文件，勿重复初始化 |
| `PARTIAL_START` | 已启动/复用部分依赖，后续阶段未通过；保留已启动服务并核对同一运行记录 |
| `STARTUP_UNCONFIRMED` / `LAUNCH_UNCONFIRMED` | 记录或交接无法确认；可能仍有进程，不当作已退出或再次启动依据 |
| `COORDINATOR_ALREADY_RUNNING` | 同一协调器仍存活，等待其当前记录 |
| `COORDINATOR_STALE_REVIEW` / `COORDINATOR_PID_REUSED` | 锁的拥有者已终止或PID被复用；需人工核对，不自动删锁或杀进程 |
| `OCCUPIED_SERVICE_UNVERIFIED` | 端口或服务身份不能证实，不替换现有进程 |
| `LATE_READY` / `UNCONFIRMED` | 原观察迟到成功或仍未确认；不自动启动替代进程，不以超时宣布结束 |
| `RUN_HISTORY_LIMIT_REVIEW` | 达到32个运行目录上限，需按实际终态整理归档；不自动删除记录 |

日志和底层错误仅在私密目录。普通服务日志持续排空、单份最多保留2MiB，超出部分丢弃且在终态记录数量；PG由厂商交接的私密日志在确认拥有的监视下限制体积。有限日志不是完整审计备份。观察失败不串联强杀依赖，关闭启动窗口不会自动结束已复用的服务。显式停止仍需按确认拥有的进程和厂商正常停止方式处理，本版不提供“一键强制停止”。
