# 核心服务启动取消验证

Windows 隔离案例 `432266bc3d3e` 实际完成 34 项检查，原生进程和独立检查均退出 0。核心组合含两个 PostgreSQL、Keycloak、Flowable 和九成员应用组；原有两租户会话及工单保留，新维修命令经实际 Flowable 同步。独立 SQL 客户端阻止最终 PG 停机，释放后同一请求正常完成。

新增三个真实启动取消阶段：第一个 PG 创建后使用 AbortSignal；身份 JVM 创建后显式关闭；应用部分启动后显式关闭。分别正常退役 1、3、5 个已创建组件，没有创建后续组件或记录完整 READY。应用取消案例实际产生一个成员，其父进程、结果文件、挑战摘要、停止请求与正常退出均已核对。

整个案例独立核验了三个 PG 目录干净离线、七个业务数据库移除、九次核心及清理 PG 进程退役、四个身份服务正常停止、六个工作流停止及 32 个池关闭、21 个根 Node 和 50 个应用成员退役。故障测试中的成员退役不统一称为正常；新增取消案例和核心正常案例各自有明确正常证明。

保留首次服务创建前的输入发现失败。独立检查首次将新增取消工作流混入原五工作流组，寻找旧案例专用 JDBC 文件而退出 1；修正检查器将其交给新增取消资源审计，重新读取同一个已结束案例后退出 0。没有重写冻结输入、补造 JDBC 文件或重新启动服务。888 项输入在成功检查时保持，之后两份 CI 定义按明确摘要更新。

工程验证入口：Windows 使用固定受限 token 入口 `powershell -NoProfile -File scripts/verify-platform-core-windows-v4.ps1`；独立检查使用 `node scripts/verify-runtime-application-suite-cleanup-v10.mjs <案例nonce>`。这些是生成隔离资料的 QA 命令，需要已核验的本机运行依赖及公开批准模板源，不能当生产安装器。Linux 由 Core dependency lifecycle verification 执行同一 34 项案例及修正检查器，结果以实际发布提交为准。

该案例使用公开批准模板和显式后台会话。完整故障矩阵、全部按配置启用的依赖登记、原私有数据受控迁移、生产/现场验收仍未完成。最终图文说明和旁白字幕实操视频尚未制作。
