# 恢复终审：外部现态核验

继续完整方案A现场第6项，实现供后续恢复计划使用的当前OIDC与工作流读取适配器，以及专用工作流只读快照端点。当前尚未接入目标恢复计划提交、权威审批审计或激活，不能把观察JSON当作批准。现有只读维护入口和13个恢复生产文件保持原字节。

人工令牌先经过现有冻结签名/issuer/audience/客户端/企业校验，再用专用client_credentials读取账号实际查询当前用户、有效realm角色、管理范围、realm/client失效时间及活跃sid。主体和sid按有界opaque标识处理，本机26.8.1实测sid不是UUID。作者/审批分别要求当前业务提交/发布权限和全企业范围，审批人与作者不同；运维角色不能叠加成业务终审。依据见 [Keycloak官方API](https://www.keycloak.org/docs-api/26.8.1/rest-api/index.html)，以实际服务结果为准。

真实PKCE取得作者和独立审批人令牌；撤销角色、禁用用户、变更企业/范围、撤销会话后，旧JWT仍通过冻结签名校验，但新现态检查全部拒绝。实际专用读取service account调用管理用户写接口403，用户保持启用；读取器不接收个人admin密码。两次读取之间真实撤权也拒绝。

新GET /v1/recovery-state使用独立读取token与稳定authority ID，不接受业务writer凭据回退，读取token调用原命令401。实际READ ONLY REPEATABLE READ事务核对全部case、历史/活动流程、任务、最后命令回执、证据/提交人、固定v1定义和全部命令摘要。编译变量只读原始列中的短字符串与布尔，拒绝附件/未知类型，不反序列化任意变量。恢复工单需SYNCED且精确对应，未知、缺失或已推进均拒绝。

真实Flowable/独立PG覆盖初始受派、未领取、领取、开始、提交、退回、重提与关闭后的历史态。全部工作流表在观察前后逐表散列相同；实际观察网络仅包含GET /v1/recovery-state。故障覆盖旧版本、错authority/定义、孤立引擎流程、运行/历史变量不一致、额外case、服务不可用；两次读间微秒级修改真实命令账本时间也拒绝。QA显式撤销自有注入，不由观察器修复。超大/畸形HTTP响应与真实DB合成513行越界拒绝单独标记，不充当512真实流程或大库容量验收。

前后双读的身份/完整工作流摘要必须一致，整个窗口最多30秒；观察短期有效，approvalGranted与activationGranted始终false，后续审批提交前仍需重新现查，不能声称跨服务原子提交。上限512case、16384历史任务、8192命令、16MiB命令扫描、3MiB响应。

Java新服务构建到独立目录并真实运行；使用不含恢复配置的旧配置重启自有实例后，原业务命令仍成功，读取入口不回退。真实进程close、代理关闭、QA数据库/角色/用户/客户端清理完成后才保存通过证据。485核心单元、248构件/脚本语法与类型及实际Java编译通过；原两个jar仍匹配最初基线，原4016 PID10432和创建时刻保持、两企业状态GET通过。原4010/PG/Keycloak未重启或切换；66契约与十轮双份快照保持。

本阶段为终审前置外态基础，尚未把任意输入工单变为受核对恢复目标的权威输入。下一步在原操作锁与完整目标核验下实现恢复计划提交、不同主体独立审批和唯一事务审计，再发布新维护锚点、重新注册、激活与全链。第6/7项、TLS/服务账号部署、大库/跨宿主/Linux及完整商业验收继续；无新最终冻结快照，完整目标ACTIVE。
