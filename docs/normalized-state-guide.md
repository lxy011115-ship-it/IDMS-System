# 领域实体存储与跨实例事务

当前数据库迁移为v4，领域实体布局仍为v3；v4仅增加后台任务领取字段，历史迁移校验和保留。部署与双核心接管见[后台任务指南](outbox-worker-ha-guide.md)。下文v3描述指领域实体布局及当时迁移里程碑。

更新：2026-10-16。原本机平台已完成 v3 迁移并恢复运行：http://127.0.0.1:4010/?view=data-center 。完整商用方案 A 仍在推进。

## 已改变的行为

两个独立核心进程连接同一企业库时，写请求会先取得企业事务锁并读取最新提交，再检查职责、数据范围、预期版本和幂等回执。另一个实例提交后，无需重启旧实例来恢复写入。同一记录版本的并发更正或模板编辑只有一个成功，过期请求返回409；相同身份、路径、幂等键和内容只创建一次。

GET请求在本机队列中取得企业共享锁后加载最新领域数据，避免与异步写入交错，并保持内存校验与SQL查询对应同一提交。不同企业有独立数据库及状态锁，不做跨企业分布式事务。

锁的实现参考 PostgreSQL 16 的 [行级锁说明](https://www.postgresql.org/docs/16/explicit-locking.html)：使用 READ COMMITTED，在读取工作数据前取得状态行的 FOR UPDATE / FOR SHARE 锁。长网络操作仍放在出站任务投递阶段；读取连接状态等网络请求可能延长共享锁持有时间，尚需生产性能优化。

## 存储结构

| 数据 | v3事实来源 |
|---|---|
| 企业、设备、报警、审批、模板、插件、健康快照、预测告警、维修建议、模型、工单 | 各自的 `business_*` 实体表，稳定顺序/主键、版本/状态生成列及必要索引；版本化扩展字段保留JSONB |
| 上传批次状态和审批/校验元数据 | `business_import_batches`，仅更新变化批次 |
| 冻结输入和有效候选行 | `business_import_input_rows`，逐行保存，禁止修改/删除 |
| 原文件 | `business_import_files` 的bytea和SHA-256，禁止修改/删除 |
| 上传请求和通用命令回执 | `business_import_requests`、`business_command_receipts`，追加写入 |
| 已批准原事实、更正、审计 | 原有领域表、`managed_record_revisions`、`audit_ledger`继续追加，不改写历史 |
| 当前提交版本和完整性摘要 | `business_state`，用于事务锁和重建校验 |
| 迁移前完整快照 | `migration_snapshot_v2`只读归档，保留原始值作为迁移证据 |
| 原名称`runtime_state` | 从领域行、文件、事实、审计、回执计算的只读视图，兼容已有只读核验和恢复工具；无写入转发规则 |

业务写入比较事务加载的原值，只更新变化实体并追加新数据。原文件、输入、回执和未变化实体不会因其他业务操作而重写；真实测试比较其xmin证明这一点。提交前从SQL重建结果并逐项比对，防止漏写后误报成功。

运行快照的线格式仍是version 2；数据库迁移版本是3，两者含义不同。`runtime_state`视图使用DISTINCT阻止自动更新，同时应用仅有SELECT权限；依据 PostgreSQL 16 的 [视图可更新规则](https://www.postgresql.org/docs/16/sql-createview.html)。旧代码不能继续把整个企业JSON写回该视图。

这是领域实体分表和增量写入，尚未把每项业务扩展属性拆成专用标量列。当前事务仍会读取完整企业工作数据、文件和审计并计算完整性摘要；大企业的加载、内存、锁竞争和专项SQL查询需要继续优化和压测。

## 迁移与恢复

独立部署命令仍为`npm run postgres:migrate`。v1和v2的原DDL/权限校验和已冻结；v3增加新的迁移记录，不能修改历史记录绕过检查。迁移前停止已确认属于平台的核心及其业务连接，对每个企业完成加密备份和隔离恢复验证。迁移在企业事务中校验原数据、回填实体、归档旧快照、建立只读视图并授予最小权限；企业之间不具备跨库原子提交。

本次原acme与sandbox均按此流程升级。停机前保存独立受限摘要，迁移后先离线比对完整数据，再启动平台做真实登录及只读页面验证。原acme仍6批、0工单，原业务/导入数据、事实表、审计前缀、v1/v2迁移记录和归档快照均保留。升级后acme的29张公共表已再次实际加密备份并隔离恢复。

`npm run database:normalized:live:verify`核对本次已保存的迁移证据；其`--capture`模式只用于首次v2停机升级前，并拒绝覆盖证据。密钥、连接配置、原始备份和迁移摘要位于受限`.local`，不得复制到公开交付目录。恢复始终使用新建隔离库，不覆盖原库；回退需按真实备份和服务依赖明确安排，不能把业务账号升为超级用户。

## 采集与异步任务

核心和本机broker探针使用各自MQTT客户端ID，用户认证及topic ACL继续生效；本机broker允许同一平台账号多个连接，避免两个核心互相顶掉。两个订阅者可能收到同一事件，企业事务、事件回执和已存在点值检查保证只提交一次，签名ACK在数据库提交后发送。边缘仍只读；真实现场证书/点表尚未验收。

Flowable及AI出站任务继续与业务实体、审计和幂等处于同一个企业事务。回执应用前重新读取当前命令状态；网络丢包、重复回执、核心回滚/重启均保留原请求。AI冻结输入统一采用`batchInputDigest`，包含类型、映射和更正来源；类型台账和更正已用真实本地模型验证，不再按旧摘要公式误判冲突。AI仍为SHADOW，最终批准由独立人员负责。
