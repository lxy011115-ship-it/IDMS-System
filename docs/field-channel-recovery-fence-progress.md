# 现场恢复围栏：运行时拦截阶段

2026-10-17。第6项已实现恢复身份与运行时拦截，并完成真实SQL和OIDC/OPC UA/SQLite/mTLS联合验证。完整归档、原子恢复控制写入及实际数据库恢复尚未完成。本阶段测试明确注入控制文件状态，没有把状态切换当作已恢复数据库。原4010及原企业未部署或迁移。

## 已实现

新增数据库外的私密恢复控制文件。其内容包括企业、部署ID、激活ID、实际数据库连接绑定摘要、ACTIVE/RESTORING状态、操作ID、前激活ID及变更时刻。严格校验字段、UUID、状态和大小，拒绝跨目录、错误企业、未来时刻、缺失或损坏文件。连接绑定覆盖host/port/database/app-user，不包含密码。

正式v2传输配置现在须使用 `idms-field-platform-config-v2`，每个tenant显式指定相对 `recoveryFile`。其他签发键和channel字段沿用原配置。加载ACTIVE控制文件后生成 `idms-field-registry-v2` 快照，公共恢复身份只包含部署ID、激活ID和数据库绑定摘要。既有registryDigest将恢复身份带入租约、当前核对、事件、ACK及streamId；设备profile、审批、请求键、事件键和签发键可以保持不变。

保留v1历史与无正式传输的开发读取配置。v1平台注册配置不能接正式v2传输；出现v2注册历史后不能再降级成v1。控制文件不随数据库备份回滚，亦不能手工回滚为旧ACTIVE身份。初始配置与恢复写入工具将在完整恢复流程中补齐；当前不提供可绕过恢复核验的通用“切ACTIVE”命令。

运行实例持有启动时的确切控制身份，但不会把它当永久允许缓存。启动验证实际PG连接；机器签发、当前核对和正式接收在事务前/关键末端及返回签名前重新读取控制文件。文件不再匹配或进入RESTORING，旧实例返回503而不签许可。接收器定期核对并关闭旧MQTT、等待实际任务排空及释放其PG接收会话；旧内存配置不会在新ACTIVE身份发布后重新接管。当前范围校验仍先于人类视图的围栏错误。

## 已验证的失效语义

- 484项单元、200项运行构件及脚本语法、server/predictor TypeScript检查通过。覆盖完整恢复身份、连接摘要、严格字段/状态/路径、每次重读、绑定不符、同配置换激活身份产生新注册和新流、防降级。
- 真实PG验证错误数据库绑定在注册观察之前拒绝启动，RESTORING阻止新实例启动且不修改根；旧内存实例在RESTORING及新ACTIVE下均不能签发或返回允许核对。
- 在根写入后的最后提交检查处保持真实事务，再改变恢复文件：整笔点/回执/审计/根回滚，无业务确认。
- 在最后检查之后保持真正COMMIT，再改变文件：旧库可能已经提交，返回签名前的再核对仍会拒绝，不返回成功ACK。新激活实例拒绝该旧STORED重放且不查询旧回执，原已提交回执保持。此情况不声称提交后还能回滚。
- 真实OIDC/Chrome独立审批、最小角色PG、SDK原生加密OPC UA、SQLite及mTLS：保持原生读取后进入RESTORING，读取被取消并实际排空，旧接收器真正关闭并释放所有权。
- 实际数据库绑定、平台注册文件字节、全部OPC/MQTT/机器请求/事件/签发密钥和profile/审批不变，只换恢复激活身份。旧平台注册实例继续拒绝；新实例可以运行，注册摘要和streamId不同，新实例对旧租约返回可验证的签名DENY。
- 保留一份真正由PG提交后签发、尚未应用于边缘队列的旧STORED。旧签名仍可作历史密码学验证，但旧SDK许可已撤销，不能清除旧队列；新流也不能被旧ACK清除。旧pending原文/摘要保持。
- 新激活下重发旧已存事件，在查询旧回执之前拒绝，原点不改；新流两点正常提交并确认。该QA共3点，新流pending0/确认2，旧流保留pending2。
- 正式CLI进程回归及完整工作台范围/身份/导出/七读取故障/预算/取消/暂停回归通过。原v1机器HTTP签发兼容通过，所有现场QA Write/Call为零。

运行时联合入口为 `scripts/verify-field-workspace.mjs`，启用 `IDMS_FIELD_QA_MTLS_PROFILE=1`、`IDMS_FIELD_QA_FORMAL_EVENTS=1`、`IDMS_FIELD_QA_TRANSACTIONAL_INTAKE=1`、`IDMS_FIELD_QA_RECOVERY_FENCE=1`。SQL故障入口为 `scripts/verify-field-intake-sql.mjs`。恢复文件由自有fixture直接写入，验证结论仅覆盖运行时门槛，不覆盖原子写入、真实归档或灾备激活。

## 后续恢复工作

恢复控制工具还需独占操作锁、原子替换与实际flush、崩溃后保持RESTORING、单调静默期及恢复/批准绑定。新激活前须让已签短状态完整过期；禁止依据旧控制文件的时间戳缩短等待。数据库根一致性不能证明备份之后没有撤权，激活还须独立终审恢复计划并核对当前审批和外部身份/流程状态。

新备份需独立版本，在同一RR快照下覆盖public和idms_field精确schema、权限、迁移、所有表事实及点/回执/审计绑定，并认证加密。当前旧备份工具的dump可能携带其他schema，但清单和恢复验证只核对public，不能作为现场模块恢复证明。

新隔离恢复目标使用独立owner/app/backup角色，避免源、目标共享可写权限。恢复先证明原始行事实，再仅在受控阶段重绑定部署迁移身份与权限；业务、输入、审计、点及回执原文保持，最终通过旧基础验证器和现场模块验证器。激活计划绑定备份、恢复操作、新数据库/激活身份、完整根和精确当前审批引用；维护实例关闭FIELD和普通业务写入，未独立批准始终保持RESTORING。这些流程和实际回滚恢复测试仍需实现。
