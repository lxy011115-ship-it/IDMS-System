## 请求和任务如何处理

HTTP 请求先取得进程额度，完成真实 OIDC 身份解析后才绑定企业额度。身份头不能覆盖签名企业声明。健康检查不访问身份或数据库，在任务满额和排空期间仍可响应。静态文件、登录与 API 共用全局额度，登录尚未取得企业身份时仅占全局额度。

业务工作区采用全进程有界调度，同企业同时执行 1 项；独立的数据中心 SQL 使用另一调度器。一个企业等待数据库或网络时，调度器能启动其他企业的任务。同企业维持提交顺序，跨核心仍依靠数据库锁后重读；本批限额按单核心进程执行，不是集群总配额。

企业额度满返回 429，进程/内存预算满或排队过期返回 503，附 `Retry-After: 1` 和错误 code。接收正文超时返回 408，正文过大返回 413。错误响应自身限定长度；客户端应退避并保留原幂等键，不应自动换键。权限、职责分离、人工独立终审和原校验规则保持。

请求断开会移除尚未开始的队列项，不执行其回调。已经开始的事务继续按原提交/回滚规则完成，正文额度保留到处理结束；客户端可用同一幂等键取回已提交结果。写请求先预留响应额度，再保存和提交，避免业务提交后才因额度不足返回失败。响应额度持有至 finish/close，正文与 HTTP 槽须同时等到处理结束及响应结束才归还。关闭服务拒绝新任务，并等待已接收任务完成或按等待期限退出。

## 默认策略

| 项目 | 每核心默认值 |
| --- | ---: |
| HTTP 同时请求 / 单企业 | 64 / 32 |
| TCP 连接上限 / 头部上限 | 128 / 16 KiB |
| 业务活动 / 等待 / 单企业等待 | 2 / 32 / 16 |
| SQL 活动 / 单企业活动 | 4 / 2 |
| SQL 等待 / 单企业等待 | 32 / 16 |
| 队列等待期限 | 30 秒 |
| 接收正文总期限 | 15 秒 |
| 正文解析总预算 | 512 MiB |
| 每 JSON / 每文件解析预留 | 8 / 416 MiB |
| 响应编码预算 | 256 MiB |
| 每任务 / 所有任务预算 | 512 MiB / 1 GiB |
| 启动保留对象预算 | 512 MiB |
| 缓存总额 / 单条 / 条数 | 256 MiB / 128 MiB / 16 |
| 缓存空闲淘汰 | 60 秒 |
| 上述类别共享逻辑总额 | 2 GiB |

API 原正文限制仍为 JSON 1 MiB、multipart 文件请求 10 MiB + 64 KiB，XLSX 展开 50 MiB、单元格/行数等限制保持。解析预留覆盖同时存在的缓冲区和解析对象的估算空间，并不扩大可上传文件大小。全局共享预算不足时可能早于 HTTP 槽上限拒绝。

可在启动前设置 `IDMS_CAPACITY_CONFIG` 为本机 JSON 文件的绝对路径，局部覆盖 `server/capacity.ts` 的默认字段；示例：

```json
{"http":32,"tenantHttp":16,"workPending":16,"tenantWorkPending":8,"sqlPending":16,"tenantSqlPending":8}
```

所有值必须为正安全整数，未知字段、零/负值、超过上限及互相矛盾的策略会阻止启动。文件最大 64 KiB。没有通过 HTTP 动态调参或暴露内部指标的接口。多核心部署需分别配置，并在代理、数据库和容器层另行设定容量。

## 内存账本与缓存

每任务按字符串、对象、数组和 Map 的保守权重计账，逐行重建、工作区克隆与 wire 规范化纳入任务预算；超额抛出错误并回滚。启动聚合对象冻结并单独保留额度，直到 owner 回收或进程退出。SQL 投影、数据库驱动和 JSON 编码仍有先分配的对象；低层维护工具和部分后台领取数据也未逐项计账，因此这些权重是应用的逻辑准入预算，不能视为精确堆/RSS测量或容器硬限制。

普通 GET 工作区使用有权重、条数、单条上限的 LRU 缓存，定时清理空闲项；缓存命中会计入借用任务额度。超大项或缓存预算不足时不缓存，读取仍可在任务额度内完成。每次读取仍先验证来源快照指纹，变化后完整核验；淘汰后重新重建并校验，不复用失去校验的对象。关闭时清空缓存并归还额度。

PG 的 socket 可能在启动时创建。逐行查询的 row 和完成回调显式绑定提交时的异步上下文，避免后续请求误用已经释放的启动账本；单元用过期启动 socket 上下文复现并验证，真实 2 万测点读取也通过。

## 验证与边界

运行 `npm run capacity:verify`，创建独立双企业 QA 数据库、三个核心和临时真实 Keycloak 用户，不向原企业写入合成业务。验证全局及企业 HTTP/SQL/业务限额、其他企业继续、健康可用、排队断连和过期不执行、已开始断连只提交一次并幂等取回、未收正文前拒绝、正文期限和归还、LRU/TTL 重建、响应/任务预算不足原子回滚、同键重试和独立终审、排空及缓存/请求/任务额度归还。证据为 `outputs/capacity-verification.json`；单元 130 项、运行文件 69 项及全部脚本语法/TypeScript 构建通过。

上一批状态流测试的时延与 RSS 对比属于启用本批计账前的历史样本，不能当作本批性能收益。本批未给出生产吞吐、SLA 或 OOM 保证。仍需按需文件/审计正文、分段组件摘要、同步 CPU 隔离、真正流式导出、更大数据与长时间负载、跨核心总配额、数据库及上游 HA、生产安全与跨服务恢复等完整方案 A 待办。
