# 当前状态映射中的现场准入

统一站点使用当前 state_map 数据库。旧 FieldPlatformService 使用 public 业务表，不能直接登记到统一平台并声称现场数据已经接入当前站点。本阶段把原现场审批规则的结果编译进当前状态映射，并随治理命令的候选分支一起原子发布。现场租约、事务接收、当前身份权威和控制器接线仍须继续完成。

维护编译器 `compileFieldAdmissionMapV1` 直接调用既有 `fieldAdmissionDecision`，收集现场政策、来源政策、批准审计与设备/测点导入的有效时间边界。运行读取使用当前根的成员证明，只访问现场索引、树节点和决定文档；恢复精确查询时钟，不重建整个企业历史。未知测点使用单独的拒绝决定。索引必须匹配企业、公开配置摘要、规则版本及当前治理控制锚点。治理状态为 UPDATING 或 PAUSED 时，在加载现场决定前拒绝准入。

`GovernanceConsoleCommandServiceV5` 和对应 V5 worker 复用原命令格式、权限规则、队列租约、独立心跳及 SQL 写入围栏。V5 规划器将现场索引与业务、审计、来源治理和新控制锚点放入同一候选分支。新 worker 尚未接入统一平台配置。启用现场宿主前，必须排空旧规划器已接受的任务并完成匹配当前锚点的索引准备；旧索引不自动重建或信任。

验证命令：

```sh
node --test tests/field-admission-map-v1.test.mjs
node node_modules/typescript/bin/tsc -p server/tsconfig.json --noEmit --allowImportingTsExtensions
node scripts/verify-field-admission-map-v1.mjs <PostgreSQL-16-bin>
node scripts/verify-field-admission-map-cleanup-v1.mjs <本次12位nonce>
```

原生验证仅创建自有的全新本机 PostgreSQL 集群和企业库。实际状态映射、治理队列和最终封存的 SQL 写入围栏共用该数据库。创建、提交、不同身份审核三条命令的每个暂存批次均检查候选隔离和当前准入撤回；审核发布后，新决定与控制锚点同时生效。重放原命令及关闭围栏后的写入均不能改变当前根。所有自有连接、心跳和 PostgreSQL 正常退役。

独立检查器不开数据库、不重启集群，重新验证原生执行时保存的当前根成员证明，将发布前后决定与原规则逐字段比较，核验六个暂存批次、两个独立模型身份、重放与围栏前后的根、源码摘要，以及 PostgreSQL 干净离线状态。它还实际拒绝一份被改动的成员证明。私密负载、账户、原始证明和日志仅保留在本地 work，公开摘要不包含其内容。

Windows 已通过七项纯规则测试、七项原生检查及独立检查，后端类型检查通过。根目录前端类型检查因本机缺少 `vite/client` 声明未通过，不能据后端检查声明全站构建通过。Linux 使用本次独立 workflow 核验，最终状态见相应 GitHub 作业与后续公开摘要。

本阶段使用公开 QA 模型的作者和审核者，SQL 围栏使用明确标注的 QA 权威状态；没有执行真实 OIDC 登录或人工 UI 审批，也没有把现场签发/接收、MQTT、恢复准入与统一控制器接在一起。上一阶段的真实边缘数据链路证据保留，但其旧业务表不等同于本阶段当前状态映射。不能把局部成功报告为完整系统、生产部署或全部依赖登记完成。原核心 V20 历史迁移失败的 SQLSTATE 仍未知，后续成功不能替代根因调查。

继续完成现场注册、租约、事务回执和测点写入当前状态映射，再绑定当前身份权威、恢复准入、登记 PG 和控制器逆序排空。保持 `idms.xin` 未备案仅部署准备的限制；最终同版本中文可编辑说明、真实截图和旁白字幕实操视频仍须交付。
